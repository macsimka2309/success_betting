# Модель данных текущей реализации

## Границы описания

Baseline 18.11.2026 восстановлен по миграциям 001–029 и использующему их коду.
Это ожидаемая схема при последовательном применении этих файлов, а не выгрузка
production. Миграции при документировании не запускались. Незакоммиченные
миграции включены в обзор; факт их установки неизвестен.

Полный DDL — в [migrations](../migrations/). Ниже описаны смысл, зерно строки,
ключи и существенные связи. Ссылка по идентификатору в коде не всегда является
FOREIGN KEY в SQL: такие связи явно названы логическими.

## Футбольное ядро

Источник основных таблиц — [001_initial_schema.sql](../migrations/001_initial_schema.sql),
отслеживание лиг — [002](../migrations/002_leagues_tracking.sql), основной счёт —
[003](../migrations/003_ml_features.sql), таймы — [004](../migrations/004_statistics_halves.sql).

| Таблица | Зерно / ключ | Связи и назначение |
|---|---|---|
| leagues | league_id API | Название, страна, тип, legacy_code; is_tracked управляет обычным сбором |
| league_seasons | league_id + season | FK на leagues; даты сезона и nullable-флаги покрытия |
| teams / players | team_id / player_id API | Справочники участников |
| fixtures | fixture_id API | FK на лигу и две команды; season без составного FK на league_seasons; kickoff, статус, основной/итоговый/перерывный счёт |
| fixture_events | event_id; UNIQUE event_key | FK на матч, команду, игрока и ассистента; минута, добавленная минута, тип и детали |
| fixture_statistics | fixture_id + team_id | FK на матч/команду; показатели всего матча, NULL при отсутствии |
| fixture_statistics_halves | fixture_id + team_id + half | Статистика тайма 1 или 2; см. DDL 004 |
| fixture_lineups | fixture_id + team_id | FK на матч/команду; схема и тренер, отдельной таблицы тренеров нет |
| fixture_lineup_players | fixture_id + team_id + player_id | Составной FK на lineup, FK на игрока; старт/скамейка, позиция |
| injuries | fixture_id + player_id | FK на матч, игрока, команду и лигу; тип и причина |

```text
leagues --> league_seasons
   |
   v
fixtures <-- teams
   |
   +--> fixture_events <-- players
   +--> fixture_statistics
   +--> fixture_statistics_halves
   +--> fixture_lineups --> fixture_lineup_players <-- players
   +--> injuries <-- players
   +--> odds_snapshots --> odds_values
   +--> ml_match_features
```

Футбольные ID следуют пространству API-Football. `event_key` создаётся из
fixture/minute/extra/team/type/detail/player функцией [event_key](../src/common/keys.py).
Повтор одинакового события обновляет строку; изменение полей самого ключа
может выглядеть как новое событие. Политика удаления исправленных событий
отдельно не реализована этим ключом.

`ft90_home/away` используются для счёта основного времени, особенно AET/PEN.
Пустые значения не равны нулю. Наличие двух строк статистики не доказывает
заполненность каждого показателя. Общая запись использует
[ON CONFLICT](../src/common/db.py), а не полную замену всего набора матча.

## Коэффициенты

| Таблица | Ключ | Связи |
|---|---|---|
| bookmakers | bookmaker_id | Справочник букмекеров |
| bet_types | bet_type_id | Справочник рынков |
| odds_snapshots | snapshot_id; UNIQUE(fixture_id, taken_at) | FK fixtures; время снимка и время обновления источника |
| odds_values | snapshot_id + bookmaker_id + bet_type_id + value | FK на снимок/букмекера/рынок; числовой odd |

`value` хранит исходную строку вроде `Home` или `Over 2.5`; её интерпретируют
потребители. Для значений штатный сбор выбирает Pinnacle/1xBet, хотя справочник
bookmakers может пополняться другими букмекерами ответа. Live-коэффициенты
задания `live-odds` архивируются как API-наблюдения, не смешиваются этим заданием
с prematch-таблицами. Источник: [run_odds / run_live_odds](../src/jobs/collect.py).

## Состояние сбора и происхождение

Источники: [001](../migrations/001_initial_schema.sql), [004](../migrations/004_statistics_halves.sql),
[019](../migrations/019_collection_reliability.sql), [collection_run](../src/jobs/collect.py).

| Таблица | Зерно | Состояния / связи |
|---|---|---|
| collection_runs | run_id | running, success, failed, quota_exceeded; job_name, времена, счётчики |
| fixture_fetch_state | fixture_id, FK fixtures | Старые отметки fetched_at и счётчики попыток по видам данных |
| fixture_fetch_results | fixture_id + kind, FK fixtures | loaded, empty, partial, error, exhausted; attempts, checked_at, next_retry_at |
| api_observations | observation_id, FK collection_runs | endpoint, params, requested_at, observed_at, полный JSON успешного ответа |
| schema_migrations | version | Реестр применений; создаётся собственным [мигратором](../src/db/migrate.py) |

Два слоя состояния загрузки сосуществуют. `exhausted` означает завершение
попыток, не отсутствие поддержки источником. Архив append-only по используемому
пути записи; это не SQL-запрет UPDATE/DELETE. Кэш JSON на диске может
перезаписываться и очищается отдельно; он не заменяет архив. Автоматическая
ретенция api_observations не найдена. Ключи HTTP-заголовков не записываются
архиватором; содержимое внешнего payload остаётся данными провайдера.

## Признаки и исследовательские результаты

`ml_match_features` — физическая таблица, одна строка на fixture_id с FK fixtures.
Содержит время вычисления, идентификаторы, основной счёт/цели, линии, форму,
статистические агрегаты, H2H, травмы, контекст лиги, Эло и eval-коэффициенты.
Имена/типы групп колонок определены в [feature_columns.py](../src/common/feature_columns.py),
DDL — в [003](../migrations/003_ml_features.sql). Признаки обучения выбираются
отдельно в [model/features.py](../src/model/features.py): наличие цели в таблице
не означает использование как признака или наличие модели для неё.

В той же таблице находятся будущие матчи с NULL-целями. `computed_at` — время
перезаписи, не идентификатор версии. Полный и инкрементальный режимы используют
пакетный upsert, без атомарной смены версии всей таблицы. `--incremental` с общим
max(kickoff_at) имеет ограничение, описанное как U-02 в [архитектуре](architecture.md).

`ml_team_elo_state`: PK(team_id, league_id), FK league_id и as_of_fixture_id;
team_id здесь не объявлен FK на teams. Сохраняется итоговый рейтинг для будущих
признаков. Актуальность относительно последнего сбора требует проверки запусков.

`goal_after_cutoff_scan_results` хранит результаты исследовательских прогонов,
порогов, целей и разделений. DDL: [005](../migrations/005_goal_after_cutoff_scan_results.sql)
и [006](../migrations/006_goal_scan_drop_cards_split_subst.sql). Это не журнал
исполненных ставок. Модели joblib, metrics.json, parquet и CSV находятся вне БД.

API-срез имеет FK на run и два api_observations: статистику и контекст. Его

команд из разных провайдеров. Диспетчер выбирает пригодный источник отдельно.

## Идентичность и очередь доставки

Источник — [027_unified_live_alerts.sql](../migrations/027_unified_live_alerts.sql).

| Таблица | Ключ / связи | Смысл |
|---|---|---|
| live_alert_dispatch_config | singleton=true | Флаг enabled; миграция создаёт выключенным |
| live_alert_context | source + source_event_id | Время, статус, минута, present и теги формата |
| live_alert_matches | alert_match_id; self-FK merged_into | Общая идентичность; sent_at и uncertain_at |
| live_alert_aliases | source + source_event_id; FK alert_match_id | Источники одной идентичности |
| live_alert_outbox | PK/FK alert_match_id; UNIQUE alert_id | payload, state, attempts, lease, следующий повтор, message_id |

`live_alert_identity` и `live_alert_link` — функции PostgreSQL под общей advisory
блокировкой. Связь источников объединяет идентичности, сохраняет память доставки
и просрочивает дублирующие задания. Триггер сопоставления использует ту же блокировку.
`alert_id` outbox использует последовательность старых оповещений, но не является
FK на live_alerts_sent: Fonbet-only может не иметь старой строки.

Состояния outbox: pending, sending, sent, retry, expired, uncertain,
identity_ambiguous. Это доставка, не исход матча и не статус ставки.
`uncertain` не разрешается автоматически; полного операторского процесса в коде нет.

## Оповещения, ставки и диалог

`live_alerts_sent` эволюционирует миграциями 007–018, 020, 022. Актуальные
уникальности: alert_id и (fixture_id, category). Исторический PK fixture_id снят
миграцией 010. FK на fixtures нет. Хранятся снимок карточки, категории,
stats_source, outcome, конечный счёт и число голов после 75.
Outcome: pending/hit/miss/void/no_data. [alert_hit_rate](../migrations/015_live_alerts_also_categories.sql)
разворачивает основную и дополнительные категории: сумма категорий не обязательно
равна числу уникальных матчей. `live_ht_possession` — временная память старых правил,
не архив наблюдений; очищается кодом по возрасту.

`bets`: PK bet_id, nullable FK alert_id → live_alerts_sent, логический fixture_id
без FK, market/line/odds/stake, даты, status/profit и счёт. Миграции:
[009](../migrations/009_bets_registry.sql), [013](../migrations/013_bets_market_tm.sql),
[021](../migrations/021_bets_without_fixture.sql), [024](../migrations/024_bets_fonbet_coupon.sql),
[029](../migrations/029_bets_freebet.sql). `fonbet_coupon_id` имеет частичный
UNIQUE при NOT NULL; `is_freebet` — отдельный флаг.

Без fixture_id ограничение требует рассчитанную ставку, отсутствие alert_id
и непустые manual_home_name/manual_away_name. Статусы: open/won/half_won/push/
half_lost/lost/void. День отчёта определяется COALESCE(kickoff_at, created_at)
в Europe/Moscow, а день отбора новых купонов — временем размещения.
Profit нормализован к условным единицам и не моделирует денежные правила бонуса.

`bot_dialogs`: PK chat_id, step, JSON payload, last_update_id, updated_at.
Сохраняет диалог после перезапуска. Telegram update_id защищает от повторной
обработки обновления, но не запрещает владельцу создать другую ставку на тот же матч.

## Баскетбол и временная семантика

Схема `basketball` из [016](../migrations/016_basketball_schema.sql) содержит leagues,
league_seasons, teams, players, games, team_game_stats, player_game_stats,
fetch_state, bookmakers, bet_types, odds_snapshots, odds_values. Это отдельное
пространство ID, не футбольные fixtures. Сбор использует общий журнал collection_runs.
Фактическое выделение в другую БД этим репозиторием не подтверждается.

Время событий хранится преимущественно TIMESTAMPTZ; код преобразует API-время
в UTC. `match_date` — отдельная календарная дата, не точный фильтр «ещё не началось».
requested_at/observed_at/context_observed_at/taken_at/computed_at имеют разные
значения; `updated_at` не продлевает свежесть наблюдения. Метки времени и минуты
провайдера не гарантируют точную физическую секунду матча.

При документировании FK и сценарии сверены статически. Проверки миграций
[test_migrate.py](../tests/test_migrate.py), источников
[test_live_source_matching.py](../tests/test_live_source_matching.py), нормализации
[test_fonbet_goal_normalization.py](../tests/test_fonbet_goal_normalization.py)
существуют, но в этом baseline не запускались.

## Отслеживание новых сигналов

Таблицы изменения `add-alert-reminder-and-post-signal-goals` создаются миграциями 030–036.

- `live_signal_config`: независимые `tracking_enabled` и `reminders_enabled`, оба по умолчанию false; `activated_at` обязателен для включения и сохраняется при повторном включении; `version` фиксируется в новых сигналах.
- `live_signal_tracking`: исходный `signal_id`/`alert_id`, canonical `alert_match_id`, message ID, `first_sent_at`, `confirmed_at`, `delivery_started_at`, точность времени, неизменяемый исходный контекст JSON и признак `goals_enabled`. Таблица также содержит долговечное расписание и полноту для `signal_results` worker.
- `live_signal_reminders` хранит одну строку на исходный сигнал с состоянием доставки, lease, попытками и причиной. `first_decision` хранит первый определимый результат `half_pressure`, источник, ID матча, опрос и наблюдение, времена запроса и получения, минуту и решение. Контекст доставки сохраняется отдельно. Состояние sent требует message ID и sent_at.
- `live_signal_goal_observations`, `live_signal_goals`, `live_signal_goal_relations`: схема исходных снимков, нормализованных событий и отношения к сигналу. Сбор и сопоставление выполняются адаптерами `signal_goals.py` и хранилищем `signal_goal_store.py`. Два гола одной минуты не обязаны иметь один event key.
- `live_signal_check_attempts`: журнал этапов перепроверки.

Время Telegram имеет точность секунды (`telegram_second`); если транспорт вернул только ID, используется интервал от начала отправки до подтверждения (`delivery_interval`). Наблюдавшийся до отправки счёт хранится внутри `first_context` и не объявляется точным счётом на момент доставки.

Миграция аддитивна и не создаёт tracking задним числом. Старые `live_alerts_sent.outcome`, `goals_after_75`, `alert_hit_rate` и snapshots сохраняются. FK на canonical identity не позволяет откатывать миграцию 027, пока установлен зависимый слой 030. В production откат функциональности должен выключать флаги/задания с сохранением данных; destructive down-файл предназначен для свежей/тестовой установки.

Проверки: `tests/test_signal_tracking_schema.py`, `tests/test_signal_enrollment.py`, регрессии `tests/test_alert_dispatch.py`; используются только disposable PostgreSQL и mock Telegram.

Миграция 031 расширяет `live_alert_context` полями `poll_id`, `requested_at`, `completed_at`, `period`, `added_minute`. Архивы без времени начала опроса не вызывают reminder. Миграция 032 сохраняет связь tracking с каноническим матчем при объединении и отменяет лишние напоминания. Для тестового отката миграции 036–030 снимаются в обратном порядке.

### События и граница сигнала

`signal_goal_store.save_timeline()` хранит исходный payload и нормализованный снимок в `live_signal_goal_observations`. Полный новый снимок деактивирует прежние текущие события источника, сохраняя их и raw историю; частичный ответ этого не делает. Event key использует provider ID либо устойчивый внутренний UUID; fingerprint текущего снимка не является идентичностью гола. Минута не служит единственным ключом. После canonical merge новая полная загрузка заменяет active-набор всей семьи алиасов.

`live_signal_goal_relations` хранит `before`, `after` либо `order_unknown` относительно исходного сообщения. Для минутной точности учитываются интервал минуты и задержка между наблюдением и подтверждением отправки; одинаковая минута и недостаточно точная граница остаются неизвестными. `order_unknown` выводится как «порядок относительно сигнала не установлен» и не прибавляется к подтверждённым голам после сигнала. Полнота timeline не означает определённости порядка. Старая `goals_after_75` не меняется.

Проверки: `tests/test_fonbet_timeline.py`, `tests/test_signal_goals.py`, `tests/test_signal_goal_store.py` (повтор, два гола одной минуты, merge, частичный ответ, отмена VAR, конфликт, неопределённость порядка).

Для анализа использовать `live_signal_goals_selected`: это проекция выбранного источника на действующий канонический сигнал через отношения. Она не суммирует API/Fonbet и исключает superseded/void сигналы. `live_signal_goals` хранит записи каждого источника для аудита, поэтому прямое суммирование всех его строк across sources некорректно. Фильтр `relation='after'` даёт подтверждённые голы после первого сообщения; `order_unknown` показывается отдельно вместе с полнотой.

### Устойчивая идентичность после review

Миграция 033 добавляет `live_signal_goal_versions` (история нормализованных версий по goal_id/observation_id) и `live_signal_goal_pending` (наблюдения с неоднозначными кандидатами). Новые события без provider ID получают внутренний UUID event_key; вычисленный счёт не определяет ID. Совпадение по известному счёту и команде/периоду позволяет сохранить goal_id при исправлении минуты. При частичном ответе совпадение минуты и известных признаков сохраняет прежние поля, если новые отсутствуют.

Сопоставление сначала резервирует однозначные пары по всему наблюдению. После идентификаторов источника проверяются группы голов Fonbet одной стороны, периода, базовой и добавленной минут. В этих группах учитываются тип гола и подтверждённая последовательность. При расширении группы с одного гола однозначное совпадение по типу получает приоритет перед совпадением счёта. Для проверки последовательности используется порядок событий в двух проверенных снимках с одинаковым числом голов в группе. Если ранее пропущенный гол меняет накопленный счёт, однозначные пары сохраняют ID и получают новые версии.

Для остальных событий используются совпадение стороны, периода, обеих минут и известного счёта, затем признаки непрерывности. Поэтому подтверждённая правка времени первого гола может перенести его на минуту второго с сохранением обоих ID.

Перед поиском спорных переносов проверенный таймлайн закрепляет свободные взаимно однозначные пары по стороне, периоду, обеим минутам и типу. Если меняется накопленный счёт, новая версия записывается на прежнем ID. Спорные строки другого эпизода могут остаться в pending одновременно с таким обновлением.

В группе на одной отметке конфликт типа может оставить на сверке один гол и сохранить однозначную пару соседнего гола. При проверенном порядке и уникальном согласованном типе счёт соседнего гола обновляется на прежнем ID. Неустановленное соответствие хранится со списком кандидатов.

При конфликте счёта или известного типа гола Fonbet в неполном ответе спорное наблюдение сохраняется в pending вместе с кандидатами и причиной. Совпадение счёта и отметки времени само по себе не подтверждает смену типа даже для одиночного гола. Однозначная связь по ID события источника позволяет применить коррекцию. При переносе минуты учитываются совместимые кандидаты из других спорных групп той же стороны и периода. Возможная версия существующего события остаётся в pending до подтверждения соответствия, а отдельно подтверждённый гол получает свой ID. Известные поля и активность спорных прежних голов сохраняются. Сопоставление проводится под канонической блокировкой. Полный достоверный результат с однозначной идентификацией позволяет менять активность событий с сохранением аудита.

Порядок снимков сверяется по времени наблюдения и архивному ID. Более свежий снимок, из которого уже применены изменения, защищает проекцию, даже если другие события этого снимка остаются спорными. Запоздавшие снимки сохраняются для аудита. Повтор уже обработанного наблюдения сохраняет действующую ревизию. При отмене или восстановлении в истории сохраняются архивный ID и состояние `active`.

Для статусов Fonbet сравнивается время исходного наблюдения того же события в семье канонического матча. Подтверждённый браузерный `2H` учитывается даже при пустом списке голов. Для терминального ответа браузера также учитывается более свежий проверенный штатный `2H`. При обратном порядке или конфликте на одной отметке позднее полученный ответ сохраняет состояние наблюдения и напоминания. Браузерный снимок остаётся в аудите как `superseded_observation`. Время наблюдения, подтвердившего окончание, хранится в `end_context.observed_at`. Оно вместе с хронологией применённого протокола защищает результат от запоздавшего прерывания.

Последний подтверждённый браузерный `2H` того же события Fonbet используется также при проверке окна напоминания. Минута выше 75 после времени исходного сигнала закрывает ожидание с причиной `outside_window`, если более свежий проверенный штатный контекст этого события ещё не уточнил часы. Правило действует для подтверждённых алиасов и сохраняет исходное решение по триггеру в `first_decision`.

Поиск точного повтора охватывает канонический матч и все объединённые с ним ID. Используются источник, ID события источника, исходное время и хеш содержимого. Повтор возвращает уже существующий архивный ID. При нескольких совпадениях в истории используется самый ранний ID, а действующая ссылка гола сохраняется. Другой ID события источника или отличающееся содержимое образует отдельное наблюдение даже при равном времени.

### Источник сигнала и раздельные очереди

Миграция 035 фиксирует `first_source` и `first_source_event_id` в строке `live_signal_tracking`. Очередь голов использует только подключённые при первой отправке сигналы Fonbet. При merge право на обработку сохраняет самый ранний исходный сигнал. Старыми считаются строки без закреплённого источника. Новых задач по ним не создаётся, а ожидающие повторы версии 1 закрываются с причиной `policy_changed`. История исходных сигналов, голов и попыток сохраняется.

`live_phase` отражает обычный режим, концовку или недоступную карточку. `last_live_slot` фиксируется перед обращением к браузеру в концовке. `last_live_observation_id` указывает на последний пригодный снимок с минутой, добавленным временем и событиями. `missed_live_slots` учитывает пропуски и перенесённые слоты. `last_attempt_at` и `last_poll_at` фиксируют фактическое обращение. `deferred_reason` объясняет перенос до обращения. Минутные слоты и переносы не расходуют `review_day` и `primary_attempts`. Архивная ссылка `pending_api_observation_id` из версии 1 сохраняется для аудита.

События Fonbet версии 2 хранятся в порядке сторон источника. `live_signal_goals_selected` выравнивает стороны и счёт через подтверждённое сопоставление при чтении, поэтому присоединение API-алиаса не меняет `goal_id`. Признак `source_detail` помогает сопоставить частичный автогол при отсутствии зачтённой стороны. Если точного соответствия нет, наблюдение попадает в `live_signal_goal_pending`. Частичный ответ обновляет историю с сохранением статуса отмены. Реактивация требует более свежего полного согласованного результата.

Миграция 036 добавляет `live_api_reminder_observations`. Таблица связывает валидированное наблюдение статистики API с его контекстом по ID исходного архива. При чтении открытой очереди сервис дополняет явные связи однозначными парами из архива до 036. Для такой пары проверяются исходный матч и команды, принадлежность к одному штатному запуску и действующий предел 30 секунд между наблюдениями.

У статистики без явной связи сначала определяется последний успешный ответ `/fixtures?live=all` перед началом запроса статистики. Если матч в нём отсутствует, дублируется или имеет несовместимые данные, эта запись статистики исключается из решения о повторе. Проверенные явные связи сохраняют приоритет. Снимок 75 служит источником архивных ID. Диспетчер использует только прошедшие проверку пары API и для хронологии первого решения, и для подтверждения перед отправкой.

Текущий контекст API проверяется отдельно по `live_alert_context.poll_id`. Перед доставкой и закрытием по минуте или статусу диспетчер сверяет исходный live-ответ, единственную запись матча, времена, фазу и часы. Статистику из более раннего ответа того же запуска можно использовать с проверенным текущим контекстом тех же команд. Дубликат в текущем ответе оставляет открытое напоминание в ожидании до пригодного контекста или истечения срока. Достоверная историческая пара сохраняет первое решение.

Диспетчер сверяет домашнюю и гостевую команды по данным исходного сигнала, привязке API-алиаса к карточке матча или проверяемой архивной паре ранее принятого первого решения. Сверка действует при отборе первого решения, перед отправкой и при закрытии по минуте или статусу. При неподтверждённой или несовместимой паре ожидание сохраняется до пригодного опроса или истечения срока.

Архив Fonbet связывается по ID штатного опроса, времени начала и тому же матчу. SQL-функция расчёта голов второго тайма общая для снимка 75 и архивных наблюдений Fonbet. `first_decision` записывается один раз и содержит ID статистики и контекста. Ранее закрытые напоминания и история наблюдений сохраняются.

`result_due_at` содержит исходный срок текущей послематчевой проверки. `next_attempt_at` задаёт ближайший допустимый запуск. Внутренний перенос сохраняет `result_due_at`. При миграции исходный срок восстанавливается из этапа и времени последнего фактического обращения. Если данных не хватает, признак `result_due_from_admission` указывает на использование прежнего времени допуска.
