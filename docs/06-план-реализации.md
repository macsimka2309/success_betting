# План реализации

Порядок работ от пустого репозитория до работающего ежедневного сбора.
Основание: `docs/01-требования.md`, `docs/02-архитектура.md`,
`docs/03-модель-данных.md`, `docs/04-инфраструктура.md`.

## Принципы

- этапы идут по возрастанию риска: сначала то, что проверяется локально,
  затем то, что меняет сервер;
- каждый этап заканчивается проверкой, результат которой можно предъявить;
- этап не начинается, пока предыдущий не проверен;
- перед каждым изменением на сервере — отдельное согласование (`CLAUDE.md`).

## Этап 1. Каркас и первая миграция

**Цель.** Схема из `docs/03` существует в базе, создана миграцией.

**Работы.**
1. Зависимости проекта: `psycopg` (драйвер PostgreSQL), `pytest`, `pandas`
   и `pyarrow` (нужны только для переноса из parquet). Файл `requirements.txt`.
2. Подключение к базе из переменной окружения `DATABASE_URL`, `.env.example`.
3. Скрипт применения миграций: читает `migrations/*.sql`, применяет
   неприменённые по порядку, отмечает в `schema_migrations`, идёт в одной
   транзакции на файл.
4. Миграция `001_initial_schema.sql` — 15 таблиц, ключи, индексы, внешние ключи.
   Обратная миграция `001_initial_schema.down.sql`.
5. Справочники `bookmakers` и `bet_types` миграцией **не наполняются**:
   эндпоинты `/odds/bets` и `/odds/bookmakers` оказались нестабильны
   (23.09.2026 — устойчивые таймауты), а подставлять идентификаторы
   по памяти недопустимо. Обе таблицы заполняются при сборе котировок:
   шаг сбора делает upsert перед записью значений. Плюс решения — справочник
   не устаревает при появлении новых букмекеров и рынков.

**Проверка.** Миграция применяется на **локальной** базе в Docker, не на
сервере. Повторный запуск не делает ничего. Обратная миграция удаляет таблицы.
Тест на временной базе: применение, откат, повторное применение.

**Риск.** Низкий: сервер не затрагивается.

## Этап 2. Перенос накопленных данных (ФТ-8)

**Цель.** Данные из parquet лежат в базе, число строк сверено.

**Предварительно:** спецификация `specs/перенос-из-parquet.md`.

**Работы.**
1. Сопоставление кодов лиг прежнего проекта (`E0`, `F2`) с `league_id` API
   по файлу `apifootball_leagues.json`. Лиги без соответствия — в отчёт,
   не в базу.
2. Загрузка по порядку: лиги → команды → игроки → матчи → события →
   статистика. Порядок продиктован внешними ключами.
3. Запись пакетами с `ON CONFLICT DO UPDATE`; прерванный перенос
   продолжается с места остановки.
4. Приведение типов: проценты и xG из строк в числа, даты в UTC,
   сборка `event_key`.
5. Отчёт: сколько строк прочитано, записано, пропущено и почему.

**Проверка.** Число строк в базе сверяется с parquet по каждому набору.
Выборочная сверка десяти матчей по всем полям. Повторный запуск не меняет
число строк.

**Риск.** Средний: объём 4 млн строк. Выполняется сначала на локальной базе,
на сервер переносится после сверки.

## Этап 3. Клиент API

**Цель.** Обращения к API-Football идут через один компонент, соблюдающий
лимиты.

**Работы.**
1. Клиент: ключ из окружения, кэш ответов на диск, учёт заголовков лимита,
   повтор при сетевой ошибке с нарастающей паузой, остановка при исчерпании
   лимита, счётчик израсходованных запросов.
2. Разбор ответов в строки таблиц — отдельно от загрузки (стадия 2, ADR-2).
3. Очистка кэша старше 30 дней.

**Проверка.** Тесты на подменённых ответах, без обращения к сети: остановка
по лимиту, повтор при ошибке, чтение из кэша вместо запроса.

**Риск.** Низкий. Логика во многом повторяет проверенную
`scripts/legacy/download_apifootball.py`.

## Этап 4. Шаги сбора

**Цель.** Каждый шаг из `docs/02` работает и записывает в журнал.

**Предварительно:** спецификация `specs/ежедневный-сбор.md`.

**Работы.** По шагам: каталог лиг → матчи → травмы → коэффициенты →
события → статистика → составы. Каждый шаг: запись в `collection_runs`,
обновление `fixture_fetch_state`, уважение флагов покрытия и лимита.

Коэффициенты: фильтр по букмекерам (1xBet, Pinnacle), снимок с отметкой
времени.

**Проверка.** Каждый шаг запускается вручную на одной лиге, результат
сверяется с ответом API. Тесты разбора на сохранённых ответах.

**Риск.** Низкий: расходуется квота API, данные пишутся в локальную базу.

## Этап 4б. Дозагрузка пропущенного периода (ФТ-11)

**Цель.** Закрыть разрыв: события с 21.07.2026, статистика с 08.07.2026,
составы за тот же период. Около 76 000 запросов.

**Спецификация:** `specs/дозагрузка-пропущенного.md` (утверждена 25.09.2026;
горизонт — разрыв с 08.07.2026, окно свежих — 3 дня). Реализация выкачена
на сервер 25.09.2026; первый запуск с дозагрузкой — ежедневный сбор 26.09.2026
в 09:00 MSK. Отчёт очереди на сервере при выкатке: разрыв — 18 093 события,
5 010 статистики, 17 807 составов (40 910 запросов, около 8 суток).

**Работы.**
1. Окно свежих матчей (3 дня) в шагах 5–7: ежедневный сбор больше не берёт
   всю историю.
2. Шаг дозагрузки на остатке лимита: раунды по 50 матчей на набор, порядок
   от новых к старым, горизонт `--backfill-since` (по умолчанию 2026-07-08).
3. Отчёт о ходе дозагрузки (`--job backfill-report`), только чтение.
4. Перезапрос расписания за 18.09.2026 и 22.09.2026 выполнен ежедневным
   шагом «матчи» (24–25.09.2026, все активные сезоны).

**Проверка.** Отчёт о полноте (ФТ-7) показывает сокращение числа матчей
без данных от запуска к запуску. Ежедневный сбор при этом не задерживается.

**Срок.** Ориентировочно две недели фоновой работы при остатке 5 000–6 000
запросов в сутки. Точный срок зависит от нагрузки ежедневного сбора.

**Риск.** Низкий. Главное — не дать дозагрузке съесть лимит, нужный свежим
данным; за этим следит бюджет из пункта 2.

## Этап 5. Развёртывание на сервере

**Статус: выполнен 24.09.2026** (шаги 1–7). Остаётся подтвердить первый
автоматический запуск по cron (коэффициенты в 15:00 MSK) и через сутки —
ежедневный сбор в 09:00 MSK. Подробности состояния — `docs/04`.

**Цель.** Система живёт на сервере и запускается по расписанию.

**Каждый пункт согласуется отдельно.**

**Работы.**
0. Предусловие (аудит 24.09.2026): на сервере нет пакета `python3.12-venv`;
   без него `python3 -m venv` не работает — нужен `apt install`.
1. Каталог `/opt/apps/football-collector/`, виртуальное окружение, код
   (копируется с ноутбука через rsync; репозитория на удалённом хостинге нет).
2. Файл окружения с ключом API и строкой подключения, права `600`.
3. Применение миграций на серверной базе.
4. Перенос накопленных данных (этап 2) на серверную базу: parquet
   (~85 МБ) копируются на сервер и загружаются тем же скриптом
   `import_parquet` локально на сервере — без сетевых задержек и без
   отдельной процедуры дамп/восстановление; сверка `--verify` там же.
5. Задания cron в отдельном `/etc/cron.d/football-collector` (не в crontab
   `deploy`, где живут задания соседа): ежедневный сбор, коэффициенты
   в 00:00 и 12:00 UTC, каталог раз в неделю, очистка кэша. Время — см.
   `docs/04`, «Расхождения», пункт 1а (`CRON_TZ` не поддерживается).

**Проверка.** Ручной запуск каждого шага на сервере до включения расписания.
Через сутки — проверка журнала запусков и числа новых строк.

**Риск.** Высокий: изменения на production. Перед пунктами 3 и 4 — резервная
копия базы.

## Этап 8. Препроцессинг для модели

**Статус: выполнен 30.09.2026.** Миграция применена на production,
разовая дозагрузка `ft90` проведена, первый полный пересчёт признаков
и рейтинга Эло на серверной базе успешно завершён (запущен с ноутбука
через SSH-туннель — см. ниже).

**Сделано.**
1. Миграция `003_ml_features`: `fixtures.ft90_home/ft90_away`; таблицы
   `ml_match_features` (312 колонок, сгенерированы из
   `src/common/feature_columns.py` — единственного источника правды),
   `ml_team_elo_state`. Применена на production 30.09.2026 после резервной
   копии; проверено 312 колонок, задания сбора продолжили работать без сбоев.
2. `run_ft90_backfill` в `src/jobs/collect.py` — разовая дозагрузка
   `score.fulltime` для уже собранных `AET`/`PEN`-матчей; шаг «матчи»
   заполняет его для новых матчей без единого лишнего запроса. Прогнана
   на сервере в два захода (упёрлась в дневную квоту API); остаток —
   в штатном ежедневном сборе, в постоянный cron не добавлялась
   (разовая задача).
3. `src/jobs/build_features.py`: все ДП-0…ДП-14 из спецификации; полный
   пересчёт и `--incremental`.
4. 119 тестов проекта, из них ~35 в `tests/test_build_features.py`:
   формулы линий и форы без пуша, отсечение по времени, границы сезона,
   Эло на ручном пересчёте, личные встречи, идемпотентность полного
   пересчёта, инкрементальная запись, устойчивость записи к обрыву
   соединения. Все проходят.
5. **Оптимизация памяти** (по итогам первого прогона на сервере, где рост
   потребления памяти на безсвоповом 3.9 ГБ сервере потребовал остановки
   процесса): батчинг скользящих метрик через `groupby().transform()`
   (`_shifted_rolling_batch` — 54→6 и 66→6 тяжёлых вызовов для формы
   и статистики соответственно), устранение self-join в
   `compute_statistics_features` за счёт `opponent_id` в длинном формате.
   `compute_form` на 275 000 строк: >2 мин → 32 с. Пиковое потребление
   памяти на полном прогоне (~3.8 ГБ) всё равно осталось близко к пределу
   сервера — решено не увеличивать память сервера, а считать признаки
   с ноутбука через уже существующий SSH-туннель к серверной базе (без
   нагрузки на сервер).
6. **Устойчивая к обрывам запись.** SSH-туннель обрывал одно долгоживущее
   соединение несколько раз за время записи (30–60 минут). Переписано на
   переподключение на каждый пакет (2000 строк) с повтором пакета при
   ошибке (`write_features_resilient`, `write_elo_state_resilient`) —
   не вся передача целиком. Запись состояния Эло дополнительно переведена
   с запроса на пару команда-лига на один пакетный upsert (иначе прогон
   занимал бы часы вместо минуты).
7. Найдена и исправлена ошибка целостности: `write_features` не сохраняла
   исходный хронологический порядок записи (внутренняя пересортировка
   в `compute_league_lines`), из-за чего частичная запись могла оставить
   несплошное покрытие по датам и `--incremental` мог молча пропустить
   более ранние матчи. Исправлено (сортировка по `kickoff_at, fixture_id`
   перед записью), полный (не инкрементальный) пересчёт выполнен заново
   для гарантии целостности.
8. Первый полный пересчёт на production (30.09.2026): `ml_match_features`
   — 981 268 строк, `ml_team_elo_state` — 25 981 пара команда-лига.
   Распределение исходов (H/D/A: 434 893/238 182/308 193) и покрытие
   линий (линия лиги — у всех строк, линия команды — у 76%, ограничено
   `MIN_TEAM_MATCHES`) соответствуют ожидаемому. Покрытие признаков
   статистики матчей — 14.1%, ожидаемо низкое: растёт по мере закрытия
   разрыва дозагрузки (этап 4б).

9. Инференс на будущие матчи (`--upcoming`, ДП-9а, 30.09.2026):
   `build_upcoming()` не читает всю историю, а только текущий сезон
   затронутых лиг, конкретные пары команд (H2H) и уже сохранённое
   состояние Эло — на два порядка меньше данных (~7 тыс. строк вместо
   981 тыс. на горизонте 2 дня), поэтому безопасно по памяти прямо на
   сервере (298 МБ, 43 с — против ~3.8 ГБ у полного пересчёта). Cron
   `deploy/run_build_features.sh upcoming` — ежедневно, 09:30 MSK
   (30 минут после ежедневного сбора).

**Осталось.**
10. Задание cron: полный пересчёт раз в неделю, пока не закроется разрыв
    дозагрузки (этап 4б), затем можно реже. Инкрементальный пересчёт —
    по потребности.
11. Повторный пересчёт после существенного продвижения дозагрузки
    статистики матчей (сейчас 14.1% покрытия).

**Риск.** Низкий: только чтение сырых таблиц и запись в новые, миграция
аддитивна (`ALTER TABLE ADD COLUMN`, новые таблицы), откат проверен,
запись идемпотентна (`ON CONFLICT DO UPDATE`).

## Этап 9. Международные турниры сверх клубных лиг

**Статус: выполнен 01.10.2026.** Флаг включён, список матчей загружен,
дозагрузка статистики/событий/составов идёт фоном.

**Контекст.** Все 782 отслеживаемые лиги (`is_tracked`) — клубные
внутренние чемпионаты, перенесённые из legacy-проекта
(`migrations/002_leagues_tracking.sql`: `WHERE legacy_code IS NOT NULL`).
Международные турниры (сборные, континентальные клубные кубки) в охват
никогда не входили — не решение «против», а унаследованная граница,
которую никто раньше не фиксировал явно (`docs/00` её не описывал).

**Решение (01.10.2026).** Добавлены 10 турниров, самых популярных у
букмекеров: ЧМ (1), Евро (4), Лига чемпионов УЕФА (2), отбор ЧМ по всем
6 конфедерациям + межконтинентальный плей-офф (29, 30, 31, 32, 33, 34, 37).
Остальные 170 международных турниров каталога (континентальные клубные —
Либертадорес, Кубки Африки/Азии, молодёжные и женские турниры и т.д.) —
осознанно не включены, следующая очередь по решению владельца.

**Почему не полный список и не вся история.** 180 международных турниров
в каталоге (`type='Cup', country='World'`) — в основном молодёжные,
женские и региональные отборочные; включать все разом бессмысленно и
дорого. Даже узкий список по 1-3 актуальным циклам каждого турнира — уже
2 241 матч (посчитано напрямую через API, не оценкой), что при ~3 запросах
на матч (статистика+события+составы) — около 6 700 запросов.

**Бюджет.** Выделен отдельный, прежде не занятый остаток: 7 500 (лимит
тарифа) − 7 150 (существующие шаги) = 350/сутки. Новый временный шаг
`international-backfill` (`src/jobs/collect.py`) получил 300/сутки из
этого остатка — не уменьшает бюджет ни ежедневного сбора, ни клубной
дозагрузки (этап 4б). Ожидаемый срок — около 3 недель (к концу октября
2026), после чего строка `0 10 * * *` в `/etc/cron.d/football-collector`
снимается вручную (не входит в постоянное расписание, как и `ft90-backfill`
в своё время).

**Сделано.**
1. `src/jobs/collect.py`: `run_international_fixtures` (разовая загрузка
   списка матчей по явно заданным парам лига-сезон — минуя проверку
   «активного окна» `_target_league_seasons`, которая отфильтровала бы
   завершившиеся годы назад сезоны вроде ЧМ-2022/Евро-2020) и
   `run_international_backfill` (та же механика раундов по `chunk`, что
   у `run_backfill`, но `_pending_fixtures` получила параметр `league_ids`,
   чтобы не расходовать выделенный бюджет на обычную клубную дозагрузку).
2. `UPDATE leagues SET is_tracked = true` для 10 league_id — выполнено на
   production, обратимо (простой `UPDATE`, не миграция схемы).
3. `python -m src.jobs.collect --job international-fixtures` — выполнено,
   2 241 матч записан (14 запросов).
4. Cron `international-backfill 300` — установлен в
   `/etc/cron.d/football-collector`, первый ручной прогон проверен
   (100/100/100 по событиям/статистике/составам, 300 запросов).
5. 2 новых теста (`tests/test_collect.py`): игнорирование активного окна
   сезона, изоляция бюджета от клубных лиг.

**Для признаков модели (`build_features.py`).** У разреженных турниров
(например, межконтинентальный плей-офф ЧМ — 4 матча за цикл) признаки вроде
`league_total_line` почти всегда останутся `NULL` из-за `MIN_LEAGUE_MATCHES=20`
(ДП-2) — ожидаемо, та же логика, что у тонких клубных лиг. Рейтинг Эло
(ДП-8, сквозной по сезонам) накапливается нормально.

**Риск.** Низкий: только добавление данных, без изменения схемы.
Единственный риск — конкуренция за бюджет API, если оценка срока (3 недели)
окажется заниженной; отслеживается через `fixture_fetch_state` вручную
(аналога `--job backfill-report` для этих лиг пока нет).

## Порядок и зависимости

```
Этап 1 ──► Этап 2 ──┐
                     ├──► Этап 5 ──► Этап 6 ──► Этап 7
Этап 3 ──► Этап 4 ──┘        │
                             └──► Этап 4б (фоном, недели две)
```

Этапы 1–2 и 3–4 независимы. Этап 5 требует оба. Этап 4б идёт фоном после
развёртывания и не блокирует остальные.

## Оценка объёма работ

| Этап | Объём кода | Основная сложность |

## Что делается вне плана

- витрины и производные показатели — после того, как определится применение
  данных (`docs/00`);
- веб-интерфейс, оповещения в мессенджеры, внешний мониторинг;
- перенос ML-пайплайна из проекта `download_football`.
