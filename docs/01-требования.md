# Требования

Документ описывает, что система обязана делать. Как именно это реализовано —
в `docs/02-архитектура.md` и спецификациях `/specs`.

Приоритеты: **(О)** обязательно для запуска, **(Ж)** желательно, можно позже.

## Функциональные требования

### ФТ-1. Наборы данных (О)

Система хранит семь наборов данных из API-Football:

| Набор | Единица строки | Источник (endpoint) |
|---|---|---|
| Лиги | лига | `/leagues` |
| Матчи | матч | `/fixtures` |
| События | событие в матче | `/fixtures/events` |
| Статистика | команда в матче | `/fixtures/statistics` |
| Составы | игрок в заявке на матч | `/fixtures/lineups` |
| Травмы | травма игрока | `/injuries` |
| Коэффициенты | исход у букмекера | `/odds` |

Данные сохраняются максимально близко к источнику. Производные и расчётные
показатели на этом этапе не вычисляются и не хранятся.

### ФТ-2. Ежедневный сбор (О)

Сбор основных наборов запускается автоматически раз в сутки на сервере
и забирает:

- матчи, завершившиеся с прошлого запуска, с результатом и статусом;
- события, статистику и составы этих матчей;
- матчи ближайших дней (расписание), по мере появления;
- актуальные травмы.

Коэффициенты собираются отдельным запуском **дважды в сутки, в 00:00 и 12:00
UTC**, по предстоящим матчам. Два снимка в сутки дают видимое движение линии.

Все отметки времени в системе и в базе хранятся в UTC. Сервер работает в UTC.

Запуск вручную тоже возможен и даёт тот же результат.

### ФТ-3. Повторный запуск без дублей (О)

Повторный запуск за тот же период не создаёт дублирующих строк и не теряет уже
собранное. Изменившиеся данные (уточнённый счёт, перенос матча, смена статуса)
обновляются. Ранее сохранённые данные не удаляются, если источник перестал их
отдавать.

### ФТ-4. Возобновление после сбоя (О)

Сбор состоит из шагов, которые можно повторять по отдельности. Обрыв сети,
ошибка API или падение процесса не требуют начинать сутки заново: следующий
запуск подхватывает работу с места обрыва.

### ФТ-5. Соблюдение лимита API (О)

Тариф — Pro, **7 500 запросов в сутки**. Система знает лимит и останавливается,
не исчерпав его полностью. Остаток резервируется на повторные попытки.
При получении ошибки лимита сбор завершается управляемо, а не аварийно.

Порядок сбора задан приоритетом: сначала дешёвые запросы, покрывающие много
матчей сразу (матчи, травмы, коэффициенты), затем дорогие — по одному запросу
на матч (события, статистика, составы).

Расчётная нагрузка по данным за последний год (137 385 матчей). Она состоит
из постоянной части (расписание, травмы, коэффициенты) и переменной — по три
запроса на завершённый матч (события, статистика, составы):

| Часть | Запросов в сутки | Основание |
|---|---:|---|
| Матчи | ~480 | 477 активных сезонов отслеживаемых лиг |
| Травмы | ~15 | покрытие есть у 14 активных сезонов |
| Коэффициенты | ~85 | 3 дня × ~14 страниц × 2 снимка |
| **Постоянная часть** | **~575** | |

| День | Матчей | Запросов | Доля лимита | Остаток на дозагрузку |
|---|---:|---:|---|---:|
| Обычный | 168 | ~1 080 | 14% | ~5 900 |
| Средний | 376 | ~1 700 | 23% | ~5 300 |
| Тяжёлые выходные | 1 325 | ~4 550 | 61% | ~2 450 |
| Пиковый | 1 711 | ~5 700 | 76% | ~1 300 |

Остаток считается от рабочего бюджета 7 000 запросов (резерв 500 до лимита
тарифа).

**Проверено на сервере 24.09.2026:** шаг «матчи» потратил ровно 477 запросов
(как и предсказано по каталогу), обработал 101 933 матча за 16,5 минут.
Время шага определяют записи в базу (по транзакции на матч), а не запросы
к API; для суточного окна в несколько часов (НФТ-4) этого достаточно.

**Исправление от 24.09.2026.** Первая версия таблицы не учитывала постоянную
часть. Наивная реализация запрашивала расписание по всем лигам каталога
и всем сезонам с прошлого года — 1 855 запросов в сутки, из них около 75%
впустую: на лиги вне охвата и на завершившиеся сезоны, результаты которых
уже не меняются. Поэтому сбор ограничен отслеживаемыми лигами (`is_tracked`,
ФТ-9) и активными сезонами: с 30 дней до начала и до 7 дней после конца.

Запросы не отправляются в лиги, где источник не отдаёт нужный набор: покрытие
известно из каталога лиг. Это экономия без потери данных — статистика есть
лишь у части матчей (133 799 из 1 092 857 в накопленных данных).

### ФТ-6. Журнал запусков (О)

Каждый запуск сбора фиксируется в базе: время начала и конца, результат,
число обработанных матчей, число израсходованных запросов, текст ошибки при
неудаче. По журналу видно, работал ли сбор вчера и чем закончился.

### ФТ-7. Отчёт о полноте данных (Ж)

Владелец может узнать, за какие лиги и даты данные собраны полностью,
а где есть пропуски: матчи без статистики, без событий, без составов.

### ФТ-8. Первичный перенос из parquet (О)

Разовая загрузка накопленных данных: 1 239 лиг, 1 092 857 матчей,
2 711 817 событий, 267 598 строк статистики. Перенос можно прервать
и продолжить, повторный запуск не создаёт дублей. После переноса число строк
в базе сверяется с числом строк в файлах, результат сверки предъявляется.

### ФТ-9. Охват лиг и глубина истории (О)

Все наборы данных собираются по **всем 782 лигам**; расчёт лимита это
позволяет. Состав лиг хранится в базе — флаг `leagues.is_tracked`; каталог
знает 1 246 лиг, но собираются только отмеченные. Добавить лигу в охват —
значит поставить флаг, без правки кода. Глубина истории тоже задаётся
настройкой. Значения по умолчанию соответствуют накопленным данным: 782 лиги,
сезоны с 2018 года.

### ФТ-10. Коэффициенты: охват и хранение (О)

Сохраняются котировки **двух букмекеров: 1xBet и Pinnacle**, по всем рынкам,
которые источник отдаёт для них. Ответы остальных букмекеров приходят в том же
ответе API и отбрасываются при разборе.

Выбор: 1xBet даёт наибольшую глубину рынков (до 82), Pinnacle — эталонную
по точности линию при небольшом числе рынков (15). Число запросов от выбора
не зависит: все букмекеры приходят одним ответом. Экономится только объём
хранения — примерно в 16 раз против всех 33 букмекеров.

Список букмекеров задаётся настройкой. Сырые ответы сохраняются в кэше
целиком, поэтому при расширении списка данные за последние 30 дней можно
разобрать заново без запросов к API.

Каждый снимок линии хранится отдельно, с отметкой времени. Значения не
перезаписываются: по истории снимков видно, как менялась оценка букмекеров.

### ФТ-11. Дозагрузка пропущенного периода (О)

Сбор данных прерывался: матчи и результаты собраны по 22.09.2026, а события
и статистика — только по 21.07.2026 и 08.07.2026 соответственно. Составы
и коэффициенты не собирались никогда.

Система обязана уметь **дозагружать данные за прошедший период**, а не только
за вчерашний день:

- находить матчи, по которым набор данных отсутствует, хотя источник его
  отдаёт (по флагам покрытия в `league_seasons`);
- запрашивать недостающее в порядке от новых дат к старым;
- укладываться в остаток суточного лимита после обычного ежедневного сбора;
- продолжаться со следующего запуска, пока пропусков не останется.

Объём пропущенного на 23.09.2026:

| Набор | Данные по | Матчей без данных | Запросов |
|---|---|---:|---:|
| Матчи | 22.09.2026 | — | — |
| События | 21.07.2026 | 25 301 | 25 301 |
| Статистика | 08.07.2026 | 25 319 | 25 319 |
| Составы | не собирались | 25 300 (оценка) | ~25 300 |

Итого около 76 000 запросов. При свободном остатке 5 000–6 000 запросов
в сутки дозагрузка занимает ориентировочно две недели непрерывной работы.

Дозагрузка не должна мешать ежедневному сбору: она расходует только тот
остаток лимита, который не потребовался свежим данным.

Отдельно отмечено: за 18.09.2026 матчей нет вовсе, а за 22.09.2026 их всего 9
при обычных сотнях. Расписание за эти даты нужно перезапросить, а не считать
собранным.

## Нефункциональные требования

### НФТ-1. Надёжность (О)

Сбой одного набора данных не останавливает сбор остальных. Частично собранные
данные сохраняются, а не откатываются целиком.

### НФТ-2. Сохранность данных (О)

Ежедневное резервное копирование базы. Восстановление из копии проверено
на практике хотя бы один раз. Хранение копий — не менее 14 дней.

### НФТ-3. Безопасность (О)

База недоступна из интернета. Пароль базы и ключ API хранятся вне Git,
в переменных окружения. Секреты не попадают в логи и вывод скриптов.
Подробности — в `docs/05-безопасность.md`.

### НФТ-4. Производительность (О)

Ежедневный сбор укладывается в несколько часов и не мешает работе соседнего
приложения на том же сервере. Первичный перенос — не более нескольких часов.

### НФТ-5. Объём хранения (О)

Рост базы прогнозируется и контролируется. При исчерпании свободного места
владелец получает предупреждение заранее, а не по факту отказа записи.

### НФТ-6. Наблюдаемость (О)

Логи сбора сохраняются на сервере и доступны для разбора. По ним понятно,
какой шаг выполнялся, сколько запросов потрачено и какая ошибка произошла.

### НФТ-7. Воспроизводимость (О)

Схема базы создаётся только миграциями из репозитория. Развёртывание с нуля
на чистом сервере описано и выполнимо по документации.

### НФТ-8. Тестируемость (О)

Логика записи в базу покрыта тестами, которые не обращаются к внешнему API
и не работают с production-базой.

## Ограничения

- Веб-интерфейса, API наружу и уведомлений в мессенджеры на этом этапе нет.
- Расчёт ML-признаков и обучение моделей в объём не входят.
- Система рассчитана на одного пользователя; разграничение прав не требуется.
