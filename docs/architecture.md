# Архитектура существующей системы

## Область и достоверность

Baseline от 18.11.2026 описывает локальную рабочую папку `success_betting`.
На момент анализа HEAD — `4401c3d`; папка содержит изменённые и неотслеживаемые
файлы, включая Fonbet, диспетчер и миграции 020–029. Одного этого коммита
недостаточно для воспроизведения описанного продукта. GitHub заново не проверялся.

Основание — исходный код, миграции, тесты и файлы развёртывания. Процессы, БД,
внешние API, браузер и Telegram при документировании не запускались. Тесты
приложения не выполнялись. Состояние production, применённые миграции, объёмы
данных и качество моделей не подтверждены. OpenSpec validation проверяет формат
спецификаций, а не исполнение приложения. Секреты и `.env` не исследовались.

**Реализация** означает наличие кода; **процесс** — инструкцию человеку/ассистенту;
**ограничение** — наблюдаемое свойство без обещания исправления; **неизвестно** —
необходимость решения владельца или отдельной проверки исполнения.
SHALL в спецификациях фиксирует восстановленный контракт текущей реализации,
а не разрешение на разработку и не одобрение обнаруженных дефектов.

Старые [контекст](00-контекст-проекта.md), [архитектура](02-архитектура.md)
и [спецификации](../specs/README.md) сохранены как история решений. Их записи
о релизах не заменяют текущую проверку серверов.

## Продукт и границы

Владелец накапливает футбольные данные, исследует закономерности, обучает модели,
получает live-сигналы и ведёт реестр ставок. Бот ограничивает доступ chat_id.
Собственного HTTP-сервиса и публичного frontend в `src/` нет. Fonbet читается
браузером; размещение ставок не реализовано в исследованном рабочем пути.
Арбитры не выделены в отдельную сущность или pipeline. [Авторизация](../specs/авторизация.md)
в старых specs — шаблон, не возможность продукта.

Live-правила не вызывают модели. ML выдаёт файловые прогнозы; проверка новостями
выполняется по [инструкции ассистента](../.claude/skills/proverka-stavok/SKILL.md).
Баскетбол остаётся в коде, несмотря на [план выделения](../specs/вынос-баскетбола-в-отдельный-проект.md).

Зависимости закреплены в [requirements.txt](../requirements.txt): Python/psycopg,

Node.js/CommonJS, Playwright/Chromium: [package.json](../tools/fonbet_sync/package.json),
[Dockerfile](../tools/fonbet_sync/Dockerfile). Инфраструктурные документы указывают
PostgreSQL 17; установленная версия сервера в этом baseline не проверена.

Это набор фоновых процессов и постоянный Telegram-бот с общей БД. Отдельного
брокера нет: outbox находится в PostgreSQL. Python использует psycopg, часть
Fonbet-инструментов — `psql` через `sudo docker exec` с привязкой к контейнеру.
`collection_run` и разбор статистики в `collect.py` используются также live
и баскетболом. `telegram_api.py` импортирует `_curl_quote` из `live_alerts.py`;
диспетчер использует его кнопки и запись совместимости. Это существующая связанность.

`scripts/legacy/` — прежние сборщики и эксперименты, не штатный путь `src/`.
[Изолированный Fonbet-пилот](../tools/fonbet_live/experiments/isolated/README.md)
не включён в штатные файлы расписания; его baseline-копии не являются вторым
актуальным production-сборщиком.

## Жизненные циклы

### Исторические данные и модели

`daily`: матчи → травмы → свежие события → статистика/таймы → составы.
При `--build-upcoming` и успешных свежих шагах строятся будущие признаки,
затем история получает остаток бюджета. Коэффициенты запускаются отдельно.
Пустой/частичный ответ по матчу не равен транспортной ошибке всего шага.
`loaded` подтверждает структуру ответа, а не наличие всех показателей.

`ml_match_features` → train/val/test → baseline/LightGBM → joblib/metrics.
`predict` читает ту же таблицу, выбирает Pinnacle с fallback на 1xBet и пишет
parquet. Реализованы модели 1X2 и тотала лиги; другие цели в таблице сами по себе
не означают наличие моделей. Версии датасета, модели и прогноза не связаны
единым неизменяемым идентификатором.

### Live-наблюдение и отправка

Последний срез 65–75 не доказывает текущее состояние матча: диспетчер отдельно
проверяет свежий контекст. Карточка использует данные одного источника.
Пригодный API имеет приоритет, включая отрицательный результат правила.
Аналитическая combined view имеет иной контракт: API при наличии строки,
без обязательной проверки оперативной свежести.

По коду активна `half_pressure`: второй тайм, 65–75 включительно, 6+ ударов
у команды или 8+ суммарно; TTL статистики и контекста — 120 секунд.
Fonbet raw-удары сохраняются, производное представление добавляет голы второго
тайма при известном счёте перерыва. Сопоставление учитывает перестановку сторон.

`live_alert_dispatch_config.enabled=true` подавляет прямую API-отправку после
сбора. При false остаётся прежний путь `live_alerts`. Его `dry-run` не отменяет
запись наблюдений. Значение флага в production неизвестно.

```text
candidate --> pending / identity_ambiguous
pending / retry --> recheck --> sending --> sent
                                  |
                                  +--> definite failure --> retry
                                  +--> unknown delivery --> uncertain
pending / retry --> stale / no trigger / merged identity --> expired
```

`sending` фиксируется до сетевого запроса; прерванная отправка после истечения
аренды становится `uncertain`. Подтверждённый успех сохраняет message_id.
API-ID позволяет записать совместимую `live_alerts_sent`; у Fonbet-only без ID
нет кнопок открытой ставки. Это не exactly-once: неопределённость блокирует
слепой повтор ценой возможной недоставки.

### Реестр и результаты

Бот хранит диалог и last_update_id; ставка и завершение диалога фиксируются
в одной транзакции. Новая ставка — 1 условная единица. API-расчёт использует
основной счёт и четвертные тоталы. Импорт Fonbet блокирует запись реестра,
проверяет номер купона и поддерживает более узкий набор линий. Рассчитанная
ставка без API-ID допустима, открытая — нет. Старые оповещения оцениваются
по событиям голов после 75-й минуты, независимо от факта ставки.

## Повторы и голы после первого сигнала

После подтверждения Telegram диспетчер в одной транзакции записывает исходное сообщение, источник и ID матча у источника. Подтверждённое объединение алиасов сохраняет режим самого раннего сообщения. Если ответ Telegram потерян, lease переходит в `uncertain` без автоматической повторной отправки.

Оба источника используют действующий `half_pressure` для одного повтора в окне 65–75. Диспетчер фиксирует первое определимое решение в порядке сохранённых штатных опросов исходного источника после первого сообщения. Отрицательное решение закрывает ожидание, даже если следующий снимок положительный. Перед доставкой отдельно проверяются свежесть данных, актуальное окно и триггер. При отсутствии данных ожидание истекает через 20 минут от подтверждения первого сообщения. Связи между статистикой API и её контекстом сохраняются также для наблюдений, уступивших снимку 75. При обновлении открытой очереди сервис дополняет их однозначными парами из локального архива API.

API-Football завершает работу по сигналу вместе с очередью повтора. Fonbet продолжает собирать события независимо от доставки повтора. `football-signal-results.timer` запускает DB-проверку каждую минуту на секунде 45. До 89-й минуты, при недоступной карточке и на послематчевом этапе действуют пятиминутные циклы. Свежий контекст второго тайма от 89-й минуты переводит матч в минутный режим, включая добавленное время. Одна браузерная попытка за цикл использует общие неблокирующие блокировки и лимит памяти. Минутный worker запрашивает «Ход матча» у Fonbet без целевых запросов API или чтения статистики ударов.

Явный конец основного времени или переход к дополнительным таймам открывает послематчевую очередь. Исчезновение карточки сохраняет последнее наблюдение и переводит матч на пятиминутную проверку статуса. После подтверждения конца первичная загрузка назначается в пределах часа при доступном источнике, затем выполняется обязательная проверка через сутки и до семи дополнительных при неполноте. Каждая следующая суточная попытка отсчитывается от фактического опроса. Перенос из-за ресурсов меняет время допуска, сохраняя исходный срок и счётчик. На штатном пятиминутном запуске допущенные проверки, которые ждут от исходного срока не меньше пяти минут, получают приоритет в порядке этого срока. Между штатными запусками обслуживается концовка.

При сопоставлении голов учитываются базовая и добавленная минуты. Целостная последовательность live-счёта подтверждает отдельные события на 90+2 и 90+6 до сверки итогового списка. Для полноты результата нужны явное окончание и независимый счёт основного времени того же матча. Явные колонки первого и второго таймов из «Завершенных» используются после сверки ID и сторон. При расхождении либо отсутствующих данных сохраняются история, состояние неполноты и причина. Порядок гола относительно первого сообщения хранится отдельно, а `goals_after_75` по-прежнему отсчитывается от фиксированной 75-й минуты.

Локальный переход на версию 2 останавливает несовместимые задачи версии 1, сохраняя их наблюдения. Новые сигналы создаются после активации соответствующих флагов. SQL-диагностика показывает режим, фазу, пропуски слотов, последний пригодный live-снимок и оставшиеся проверки.
