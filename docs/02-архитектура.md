# Архитектура

Документ описывает, из каких частей состоит система и почему выбраны именно
такие решения. Требования — в `docs/01-требования.md`, схема базы —
в `docs/03-модель-данных.md`.

## Общая картина

Система состоит из четырёх частей:

```
  API-Football  ──►  Сборщик (Python, cron)  ──►  PostgreSQL 17 (Docker)
                            │                            │
                            ▼                            ▼
                     Кэш сырых ответов            Резервные копии
```

1. **Сборщик** — набор Python-скриптов, запускаемых по расписанию через cron.
2. **Кэш сырых ответов** — JSON-ответы API, сохранённые на диск как есть.
3. **База** — PostgreSQL 17 в Docker-контейнере на том же сервере.
4. **Резервное копирование** — ежедневный `pg_dump` по расписанию.

Всё работает на одном сервере. Веб-сервиса, очередей и внешних интерфейсов нет.

## Поток данных

Сбор идёт в две стадии, между ними — файл с сырым ответом:

**Стадия 1. Загрузка.** Скрипт спрашивает API и кладёт ответ в кэш на диск
без разбора и без изменений.

**Стадия 2. Разбор и запись.** Отдельный шаг читает файлы из кэша, раскладывает
их по таблицам и пишет в базу.

Разделение даёт три вещи. Повторный разбор не тратит лимит API: если в схеме
нашлась ошибка, данные перекладываются из кэша заново, без единого запроса.
Ошибка разбора не теряет уже оплаченный ответ. И сырой ответ остаётся
доказательством того, что именно прислал источник.

Кэш — это ровно тот механизм, что уже работает в `scripts/legacy`, и он
оправдал себя: миллион матчей собран без повторной оплаты запросов.

## Порядок шагов сбора

Шаги независимы и выполняются по очереди, от дешёвых к дорогим:

| № | Шаг | Стоимость | Частота |
|---|---|---|---|
| 1 | Каталог лиг и покрытие | ~6 запросов | раз в неделю |
| 2 | Матчи по лигам и сезонам | 1 запрос на лигу-сезон | ежедневно |
| 3 | Травмы | 1 запрос на лигу-сезон | ежедневно |
| 4 | Коэффициенты | 1 запрос на 10 матчей | дважды в сутки, отдельным запуском |
| 5 | События завершённых матчей | 1 запрос на матч | ежедневно |
| 6 | Статистика завершённых матчей | 1 запрос на матч | ежедневно |
| 7 | Составы | 1 запрос на матч | ежедневно |

| 8 | Дозагрузка пропущенного | остаток лимита | ежедневно, после шагов 1–7 |

Шаги 5–7 идут последними намеренно: если лимит закончится, потеряется самое
дорогое и наименее срочное, а расписание и результаты уже будут в базе.

Шаг 8 — тот же код, что и шаги 5–7, но с другой выборкой матчей: не «вчерашние»,
а «любые, где данных нет, а источник их отдаёт», от новых дат к старым.
Отдельного механизма он не требует: `fixture_fetch_state` уже хранит, что по
матчу собрано, а счётчики попыток не дают бесконечно долбиться в матчи,
по которым источник молчит (ФТ-11).

Ограничитель: шаг 8 получает бюджет запросов, равный остатку суток за вычетом
резерва. Свежие данные всегда важнее исторических.

## Принятые решения (ADR)

### ADR-1. Хранилище — PostgreSQL

**Решение.** PostgreSQL 17 в Docker-контейнере.

**Почему.** Данные реляционные по своей природе: матч принадлежит лиге, событие
принадлежит матчу. Нужны ограничения целостности и защита от дублей —
в PostgreSQL это `UNIQUE` и `ON CONFLICT`, то есть требование ФТ-3 выполняется
самой базой, а не аккуратностью кода. Объём (около 4 млн строк) для неё мал.

**Альтернативы.** Оставить parquet-файлы — отвергнуто: нет защиты от дублей,
нет запросов по произвольным условиям, файлы легко рассинхронизировать.
ClickHouse — избыточен на таких объёмах и хуже в частых точечных обновлениях.
SQLite — не рассчитан на одновременную запись и не даёт сетевого доступа.

**Последствия.** Нужен контейнер, миграции и резервные копии. Статус: принято,
контейнер развёрнут.

### ADR-2. Сырые ответы хранятся в файлах, а не в базе

**Решение.** Кэш JSON-ответов лежит на диске сервера.

**Почему.** Файлы не раздувают базу и не попадают в резервные копии, где
занимали бы место без пользы: восстановить их можно повторным запросом, а
дампы должны оставаться компактными.

**Последствия.** За местом на диске нужно следить. Кэш хранится **30 дней**,
более старые ответы удаляются по расписанию. Этого достаточно, чтобы повторно
разобрать недавние данные при ошибке в схеме; за более старыми при
необходимости можно сходить в API заново.

### ADR-3. Расписание через cron, без планировщика

**Решение.** Запуск по cron на сервере.

**Почему.** Задач немного, зависимостей между ними почти нет, запуск редкий.
Airflow или подобный планировщик потребовал бы отдельного сервиса и памяти,
которой на сервере с 4 ГБ и соседним приложением немного. Cron уже есть в
системе и не требует обслуживания.

**Последствия.** Нет готовой панели наблюдения и автоматических повторов.
Компенсируется журналом запусков в базе (ФТ-6) и тем, что шаги возобновляемы.

### ADR-4. Схема повторяет источник

**Решение.** Таблицы повторяют структуру ответов API. Производные показатели
не вычисляются и не хранятся.

**Почему.** Как данные будут использоваться, ещё не решено (`docs/00`). Любой
расчёт, заложенный в схему сейчас, — это догадка, которая с высокой
вероятностью окажется неудобной позже. Сырые данные позволяют посчитать что
угодно потом; обратное неверно.

**Последствия.** Запросы к данным будут сложнее, чем к заранее подготовленным
витринам. Когда применение определится, витрины добавятся отдельными
таблицами или представлениями, не ломая базовые.

### ADR-5. Естественные ключи источника

**Решение.** Первичные ключи — идентификаторы API-Football (`fixture_id`,
`league_id`, `team_id`), а не собственные суррогатные.

**Почему.** Это то, что делает повторный сбор безопасным: запись с тем же
`fixture_id` обновляется, а не дублируется. Свои ключи потребовали бы
сопоставления с внешними, то есть лишнего слоя и лишних ошибок.

**Риск.** Если источник переиспользует идентификатор, данные перезапишутся.
За восемь сезонов накопленных данных такого не наблюдалось.

### ADR-6. Доступ к базе только с сервера

**Решение.** Порт базы слушает только `127.0.0.1`. С ноутбука — через SSH-туннель.

**Почему.** База с открытым в интернет портом — постоянная мишень для перебора
паролей. Туннель даёт тот же доступ, но за аутентификацией по SSH-ключу.

**Последствия.** Для работы с базой с ноутбука нужно поднять туннель.
Статус: принято, реализовано.

### ADR-7. Миграции простыми SQL-файлами

**Решение.** Нумерованные `.sql`-файлы в `migrations/`, применяются по порядку,
применённые отмечаются в служебной таблице.

**Почему.** Схема меняется редко, проект на одного человека, Python-моделей
(ORM) в проекте нет. Alembic оправдан там, где схема описана в коде; здесь
он добавил бы зависимость и слой абстракции ради нескольких файлов.

**Последствия.** Откат пишется вручную отдельным файлом. Инструмент применения
миграций — небольшой собственный скрипт (около 50 строк).

**Альтернатива.** Если со временем появится ORM, переход на Alembic возможен:
существующая схема принимается за исходное состояние.

## Структура репозитория

```
src/            код сборщика и записи в базу
  api/          клиент API-Football: лимиты, повторы, кэш
  db/           подключение, запись, применение миграций
  jobs/         шаги сбора, вызываемые по расписанию
migrations/     нумерованные SQL-миграции
scripts/        точки входа для cron и разовых задач
  legacy/       прежние скрипты проекта download_football (справочно)
tests/          тесты
docs/           документация
specs/          спецификации
```

`scripts/legacy/` не участвует в работе системы и хранится как справочный
материал: там отработаны обход лимитов, кэш и разбор ответов API.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Сетевая ошибка, таймаут | повтор с нарастающей паузой, затем шаг пропускается |
| Лимит запросов исчерпан | сбор останавливается штатно, факт пишется в журнал |
| Ошибка разбора ответа | ответ остаётся в кэше, матч помечается для повтора |
| База недоступна | запуск завершается с ошибкой, сырые ответы сохранены |
| Источник не отдал данные | не ошибка; отсутствие фиксируется, повтор по расписанию |

Общий принцип: сбой одного шага не отменяет результаты предыдущих (НФТ-1).

## Что сознательно не делается

- Веб-интерфейс и API наружу.
- Потоковая обработка и обновление в реальном времени: сбор фоновый.
- Контейнеризация самого сборщика: он запускается как обычный процесс
  в виртуальном окружении Python. Контейнер добавил бы сложности без выгоды
  для одного скрипта по cron.
- Внешний мониторинг и оповещения. При необходимости добавится позже.
