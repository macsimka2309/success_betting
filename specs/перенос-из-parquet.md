# Спецификация: перенос накопленных данных из parquet

Основание: ФТ-8 в `docs/01-требования.md`, этап 2 в `docs/06-план-реализации.md`.
Схема — `docs/03-модель-данных.md`.

## Цель

Разово перенести данные, накопленные проектом `download_football`, из
parquet-файлов в PostgreSQL. После переноса база становится основным
хранилищем, файлы остаются только как источник для повторной сверки.

## Границы

**Входит:** каталог лиг, матчи, события, статистика.

**Не входит:** составы, травмы, коэффициенты (в parquet их нет — собираются
с нуля при ежедневном сборе); производные файлы `matches_features`,
`odds_joined`, `matches_merged` (пересчитываются из базовых данных, ADR-4);
резервные копии `*.backup.parquet`.

## Источник данных

Каталог: `/Users/mesalikhov/Dev/football/data/apifootball/`

| Файл | Строк | Назначение |
|---|---:|---|
| `apifootball_leagues.json` | 782 | код лиги → `league_id`, сезоны, покрытие |
| `leagues_catalog.parquet` | 1 239 | каталог лиг API |
| `fixtures.parquet` | 1 092 857 | матчи |
| `events.parquet` | 2 711 817 | события |
| `statistics.parquet` | 267 598 | статистика команд |

Проверено 23.09.2026: все 782 кода лиг из `fixtures.parquet` имеют
соответствие в `apifootball_leagues.json`. Матчей без сопоставления нет.

## Сценарий

1. Владелец запускает скрипт, указав каталог с parquet и строку подключения.
2. Скрипт загружает наборы по порядку и печатает ход работы.
3. По завершении выводится отчёт: прочитано, записано, пропущено, причины.
4. Владелец запускает сверку и получает сравнение числа строк.

Порядок загрузки продиктован внешними ключами:

```
лиги → сезоны лиг → команды → игроки → матчи → события → статистика
```

## Функциональные требования

### ПР-1. Наполнение справочника лиг

Источник — `leagues_catalog.parquet` (1 239 строк) и `apifootball_leagues.json`.

| Поле базы | Источник |
|---|---|
| league_id | `id` каталога |
| name, type, country | одноимённые поля каталога |
| country_code | `cc` каталога |
| legacy_code | ключ из `apifootball_leagues.json`, где `id` совпал |

Лиги из каталога переносятся полностью, даже те, по которым матчей нет:
справочник дешёвый, а `fixtures` ссылается на него внешним ключом.

### ПР-2. Сезоны лиг и покрытие

Источник — `apifootball_leagues.json`: для каждой лиги список сезонов
и флаги покрытия. Соответствие: `coverage.events` → `has_events`,
`coverage.statistics_fixtures` → `has_statistics`, `coverage.lineups` →
`has_lineups`, `coverage.injuries` → `has_injuries`.

`has_odds` остаётся пустым: в файле этих данных нет, заполнится при сборе.
`start_date` и `end_date` тоже пусты — в источнике отсутствуют.

### ПР-3. Справочники команд и игроков

Отдельных файлов нет, справочники собираются из данных:

- команды — из `fixtures.parquet` (`home_id`/`HomeTeam`, `away_id`/`AwayTeam`)
  и `statistics.parquet` (`team_id`/`team`);
- игроки — из `events.parquet` (`player_id`/`player`).

При конфликте имён по одному идентификатору берётся последнее по дате матча:
названия команд в источнике меняются, актуальное важнее.

**Ограничение.** Поле `assist` в событиях содержит только имя, без
идентификатора. Поэтому `assist_player_id` при переносе остаётся пустым,
а имя ассистента теряется. Восстановить связь можно лишь повторным запросом
событий к API. Предложение: не тратить на это 25 000 запросов сейчас;
при дозагрузке (ФТ-11) свежие события придут уже с идентификаторами.

### ПР-4. Матчи

Источник — `fixtures.parquet`.

| Поле базы | Источник | Примечание |
|---|---|---|
| fixture_id | `fixture_id` | ключ |
| league_id | `LeagueCode` через маппинг | |
| season | `Season` | |
| kickoff_at | `kickoff` | ISO со смещением, приводится к UTC |
| match_date | `Date` | |
| status_short | `status` | |
| home_team_id, away_team_id | `home_id`, `away_id` | |
| goals_home, goals_away | `FTHG`, `FTAG` | пусто у несыгранных |

**Полей нет в источнике**, остаются пустыми: `round`, `status_long`,
`elapsed`, `ht_home`, `ht_away`, `venue_name`, `venue_city`. Они появятся
у матчей, собранных после запуска системы. Это ожидаемое расхождение,
а не ошибка переноса.

Матчи с пустым `fixture_id`, `home_id`, `away_id` или `kickoff`
не переносятся и попадают в отчёт.

### ПР-5. События

Источник — `events.parquet`.

Прямое соответствие: `fixture_id`, `team_id`, `minute`, `minute_extra`,
`type`, `detail`, `player_id`, `comments`.

`event_key` собирается из значений, разделённых `|`:

```
fixture_id | minute | minute_extra | team_id | type | detail | player_id
```

Пустые значения заменяются пустой строкой. Ключ обязан считаться одинаково
здесь и в ежедневном сборе — иначе те же события задвоятся. Это правило
покрывается тестом на одинаковых данных из обоих путей.

События матчей, отсутствующих в `fixtures.parquet`, не переносятся:
внешний ключ не позволит. Их число фиксируется в отчёте.

### ПР-6. Статистика

Источник — `statistics.parquet`, 33 колонки. Ключ — `(fixture_id, team_id)`.

Приведение типов:

| Поле | В источнике | В базе | Правило |
|---|---|---|---|
| ball_possession | `"58%"` | SMALLINT | отбросить `%`, к целому |
| passes_pct | `"84%"` | SMALLINT | отбросить `%`, к целому |
| expected_goals | `"1.74"` | NUMERIC(5,2) | к числу |
| goals_prevented | `"0.31"` | NUMERIC(5,2) | к числу |

Нечисловое значение не прерывает перенос: поле остаётся пустым, случай
учитывается в отчёте. Остальные 23 числовых поля переносятся как есть.

### ПР-7. Состояние сбора

Для каждого перенесённого матча создаётся строка в `fixture_fetch_state`:

- `events_fetched_at` — время последнего события матча, если события есть;
- `statistics_fetched_at` — аналогично для статистики;
- `lineups_fetched_at` — пусто всегда (составов в parquet нет);
- счётчики попыток — 0.

Без этого шага дозагрузка (ФТ-11) не будет знать, что уже собрано,
и потратит лимит на повторный сбор миллиона матчей.

### ПР-8. Возобновляемость и отсутствие дублей

Запись идёт пакетами по 5 000 строк, каждый пакет — отдельная транзакция
с `ON CONFLICT DO UPDATE`. Прерванный перенос продолжается повторным
запуском: уже записанные строки обновятся теми же значениями.

Повторный полный запуск не меняет число строк в базе.

### ПР-9. Отчёт

По каждому набору: прочитано из файла, записано, пропущено, причины
пропуска с количеством. Отчёт печатается и сохраняется файлом.

### ПР-10. Сверка

Отдельная команда сравнивает базу и файлы:

- число строк по каждому набору;
- число уникальных `fixture_id` в событиях и статистике;
- десять случайных матчей — сверка всех полей;
- перечень матчей, оказавшихся в файле, но не в базе.

Сверка только читает и ничего не меняет.

## Интерфейс

```bash
python3 -m src.jobs.import_parquet --source ПУТЬ [--only НАБОР] [--limit N] [--dry-run]
python3 -m src.jobs.import_parquet --verify --source ПУТЬ
```

- `--only` — один набор: `leagues`, `fixtures`, `events`, `statistics`;
- `--limit` — ограничение числа строк, для проверки на малом объёме;
- `--dry-run` — читать и проверять, в базу не писать;
- `--verify` — сверка (ПР-10).

Строка подключения — из `DATABASE_URL`.

## Ошибки и крайние случаи

| Ситуация | Поведение |
|---|---|
| Файл отсутствует | набор пропускается с предупреждением, остальные идут |
| Лига без сопоставления | матчи набора пропускаются, попадают в отчёт |
| Нет обязательного поля | строка пропускается, попадает в отчёт |
| Нечисловой процент или xG | поле пустое, случай в отчёте |
| Событие без матча | строка пропускается, попадает в отчёт |
| Повтор `event_key` в файле | сохраняется первая строка (ограничение ФТ-3) |
| Обрыв на середине | записанные пакеты сохранены, запуск продолжается |
| База недоступна | завершение с ошибкой, файлы не изменяются |

## Безопасность

Скрипт только читает файлы и пишет в базу. Удаление данных не выполняется
ни при каких условиях. Строка подключения берётся из окружения, в логи
не попадает (НФТ-3).

## Производительность

Ожидаемое время: единицы часов на 4 млн строк. Память ограничена чтением
parquet по частям, файл целиком в память не поднимается: `events.parquet`
занимает 55 МБ на диске, но в памяти существенно больше.

## Критерии приёмки

1. Число строк в базе совпадает с числом строк в файлах за вычетом
   пропущенных, и каждое расхождение объяснено в отчёте.
2. Повторный запуск не меняет число строк.
3. Десять случайных матчей совпадают по всем полям.
4. `fixture_fetch_state` заполнена для всех перенесённых матчей.
5. Прерывание на середине и повторный запуск дают тот же результат,
   что и один непрерывный запуск.

## Тестовые сценарии

| № | Проверка | Ожидание |
|---|---|---|
| 1 | Перенос на малом наборе (`--limit 100`) | строки в базе, отчёт сходится |
| 2 | Повторный запуск того же набора | число строк не изменилось |
| 3 | `event_key` из parquet и из ответа API | ключи совпадают |
| 4 | Проценты `"58%"` и `"нет данных"` | 58 и пусто |
| 5 | Матч без `home_id` | пропущен, причина в отчёте |
| 6 | Событие матча, которого нет | пропущено, причина в отчёте |
| 7 | Прерывание после первого пакета | продолжение с места остановки |
| 8 | `--dry-run` | база не изменилась |
| 9 | Сверка после переноса | расхождений нет |

Тесты работают на небольших искусственных наборах, без production-базы (НФТ-8).
