# Спецификация: модель предсказаний (1X2, ТБ/ТМ лиги)

Основание: `docs/00-контекст-проекта.md` («данные используются для обучения
модели»), `specs/препроцессинг-для-модели.md` (источник данных —
`ml_match_features`). ФТ-12 ограничивала объём «только подготовка данных»;
этот документ описывает следующий этап — саму модель.

Этот этап (01.10.2026, по решению владельца) — **только подготовительные
работы**: спецификация, разведочный анализ данных (EDA) и временной
train/val/test сплит. Обучение модели (подбор гиперпараметров, финальный
прогон, сохранение артефакта) — отдельный, следующий этап; здесь не
реализуется.

## Цель

Предсказывать два рынка с откалиброванными вероятностями:

- **1X2** (`result_1x2`) — мультикласс (H/D/A);
- **ТБ/ТМ лиги** (`league_total_over`) — бинарный, относительно
  скользящей линии `league_total_line`.

Остальные 5 рынков из `docs/00` (ИТБ/ИТМ команды, ОЗ/нОЗ, фора, двойной
шанс) — вне охвата этого этапа; инфраструктура (сплит, EDA, выбор
признаков) рассчитана так, чтобы их можно было добавить тем же способом
позже, без переделки.

**Критерий успеха** — из `docs/00`: оценка против рыночных коэффициентов.
С оговоркой (см. «Ограничение данных» ниже) — на этом этапе это не выполнимо
исторически, только через честные метрики качества на отложенной выборке;
сравнение с рынком станет возможно позже, по мере накопления `eval_*`.

## Ограничение данных (обнаружено 01.10.2026)

`eval_*`-коэффициенты (ДП-10) собираются только на горизонт 1-3 дня вперёд
от текущего момента (`src/jobs/collect.py::run_odds`) — исторических
коэффициентов для прошлых матчей никто не грузил. На 981 268 матчах с
известным результатом коэффициенты Pinnacle есть всего у **903** (0.09%).

**Следствие:** бэктест «модель против рыночной цены» на исторических данных
почти невозможен — выборка слишком мала и смещена (только последние
несколько дней перед 01.10.2026). Оценка качества на этом этапе — через
собственные метрики модели (log loss, калибровка) на отложенной выборке,
не через сравнение с рынком. Сравнение с рынком станет возможно позже,
по мере того как `eval_*` накопится за счёт ежедневного сбора — отдельное
решение, когда этого будет достаточно для содержательного бэктеста.

## Алгоритм (принято 01.10.2026)

**Градиентный бустинг деревьев** (LightGBM) — не логистическая регрессия.
Причина: признаки статистики матча (ДП-4) покрыты на 15–19% **даже в
последних месяцах** (не только в старых данных, см. EDA) — это свойство
данных, а не временная проблема, которая решится сама. Деревья нативно
работают с пропусками (не требуют импутации, не создают искусственного
сигнала из заполненных нулей/средних), в отличие от линейных моделей.

Один GBM на класс (3 бинарных LightGBM для H/D/A через `multiclass` объектив,
либо честный multiclass — решается на этапе обучения, не здесь) для 1X2;
один бинарный LightGBM для `league_total_over`. Baseline для сравнения —
наивный (частоты классов на train) и логистическая регрессия на подмножестве
признаков без пропусков (линии, Эло, форма, контекст лиги) — чтобы показать,
насколько деревья реально выигрывают за счёт устойчивости к пропускам.

## Признаки

Источник — `src/common/feature_columns.py` (`all_columns()`), уже
используемый `ml_match_features`. Для модели явно исключены:

- **Целевые колонки** (`target_columns()`) — очевидно, кроме самой линии
  (`league_total_line`), которая остаётся **признаком**, а не целью: нужна
  модели как контекст (на какую линию отклоняется прогноз).
- **`eval_*` (ДП-10)** — коэффициенты для сверки с рынком, не признак
  (это и раньше было решено, см. `препроцессинг-для-модели.md`); включение
  в обучение было бы утечкой рыночного консенсуса в признаки.
- **Идентификаторы** (`grain_columns()`: `league_id`, `season`, `match_date`,
  `kickoff_at`, `home_team_id`, `away_team_id`) — на этом этапе не признаки.
  Сила команды уже выражена через Эло/форму/турнирное положение; сырой
  `team_id` в качестве категориального признака рискует переобучиться на
  конкретные команды без обобщения на новые/малоизвестные — решение можно
  пересмотреть на этапе обучения, если понадобится.

Итоговый список — `form_columns() + stat_columns() + h2h_columns() +
injury_columns() + league_context_columns() + elo_columns() +
["league_total_line", "home_team_line", "away_team_line"]` (две последние —
не из `target_columns()`, это линии-признаки для ИТБ/ИТМ, на будущее;
`league_total_line` нужна и для текущего этапа).

## Временной сплит

Матчи упорядочены во времени (`match_date`), случайное перемешивание
(k-fold) создало бы оптимистичную оценку: модель видела бы матчи «из
будущего» относительно тех, на которых её проверяют, хотя признаки сами
по себе не содержат утечки (ДП-1) — проблема именно в оценке, не в данных.

**Границы** (по факту распределения по годам, см. EDA):

| Выборка | Период | Матчей (оценка) |
|---|---|---:|
| train | `match_date < 2025-01-01` | ~739 200 |
| val | `2025-01-01 .. 2025-12-31` | ~142 200 |
| test | `match_date >= 2026-01-01` | ~99 900 (год не завершён) |

`val` — подбор гиперпараметров и ранняя остановка (следующий этап);
`test` — финальная, один раз, метрика для отчёта. `test` — текущий,
неполный год: это осознанно, соответствует реальному сценарию применения
(модель предсказывает вперёд, не ретроспективно).

## EDA (разведочный анализ)

Скрипт `src/model/eda.py` (только чтение `ml_match_features`, без API)
печатает отчёт:

1. Число строк и диапазон дат по train/val/test.
2. Баланс классов `result_1x2` и `league_total_over` в каждой выборке.
3. Доля `NULL` по каждой группе признаков (форма/статистика/H2H/травмы/
   контекст лиги/Эло), по выборкам — показать, что пропуски не
   специфичны для test (иначе модель, обученная на train, была бы
   системно хуже на test не из-за качества, а из-за сдвига покрытия).
4. Покрытие статистики по месяцам (подтверждение раздела «Ограничение
   данных» выше).

## Критерии приёмки (для этого этапа — подготовка, не обучение)

1. `src/model/features.py::FEATURE_COLUMNS` не содержит ни одной колонки
   из `target_columns()` (кроме `league_total_line`) и ни одной `eval_*` —
   проверяется тестом (пересечение множеств пусто).
2. `src/model/splits.py::time_split(df, val_start, test_start)` делит
   строго по `match_date`: максимальная дата в train строго меньше
   минимальной в val, максимальная в val строго меньше минимальной в test.
   Проверяется тестом на синтетических данных.
3. `src/model/eda.py` выполняется на реальной базе без ошибок и печатает
   все 4 пункта отчёта.
4. Тесты новых модулей — на синтетических данных, без обращения к
   production-базе (НФТ-8), как и у `build_features.py`.

## Что не входит в этот этап

- Обучение модели, подбор гиперпараметров, сохранение артефакта.
- Инфраструктура инференса (как подавать `--upcoming`-строки в обученную
  модель) — естественный следующий шаг, не этот.
- Остальные 5 рынков (ИТБ/ИТМ, ОЗ/нОЗ, фора, двойной шанс).
- Бэктест против рыночных коэффициентов (см. «Ограничение данных»).

## Обучение модели (этап 2, принято 02.10.2026)

Подготовительный этап выше завершён (`features.py`, `splits.py`, `eda.py`).
Этот раздел описывает собственно обучение — `src/model/train.py`.

**1X2 — один multiclass LightGBM**, не три бинарных one-vs-rest: вероятности
трёх классов гарантированно суммируются в 1, меньше кода и артефактов.
`league_total_over` — отдельный бинарный LightGBM.

**Гиперпараметры** — разумные дефолты, без перебора: `n_estimators=2000`,
`learning_rate=0.05`, ранняя остановка по `val` (`early_stopping_rounds=50`,
метрика — log loss). Подбор по сетке/случайный поиск — следующая итерация,
если качество на `val`/`test` покажет, что это оправдано.

**Baseline для сравнения** (оба — на `test`):
- наивный — частоты классов `train`, одинаковые вероятности для всех строк;
- логрегрессия — на подмножестве признаков без систематических пропусков
  (`form_columns() + league_context_columns() + elo_columns() +
  LINE_FEATURE_COLUMNS`, не вся статистика/H2H/травмы). Строки с пропуском
  хотя бы в одной из этих колонок исключаются из обучения и оценки
  логрегрессии — её метрики считаются на **другом**, более узком
  подмножестве `test`, чем LightGBM (который получает все `FEATURE_COLUMNS`
  и работает с пропусками нативно). Это осознанное ограничение сравнения:
  цель — показать выигрыш деревьев от устойчивости к пропускам, не дать
  метрики на одинаковой выборке.

**Метрики** (на `test`, для каждой модели и baseline):
- log loss (основная метрика для калибровки);
- accuracy;
- Brier score (для 1X2 — обобщённый, `mean(sum((proba - onehot)^2))`;
  для `league_total_over` — стандартный бинарный).

**Артефакты** — сохраняются локально в `models/` (добавлено в `.gitignore`,
не коммитится): `result_1x2_lightgbm.joblib`, `result_1x2_logreg_baseline.joblib`,
`league_total_lightgbm.joblib`, `league_total_logreg_baseline.joblib`,
`metrics.json`. Причина не коммитить: бинарные артефакты не читаемы в diff,
воспроизводимы запуском `train.py`, а инфраструктура деплоя модели на
сервер для инференса — отдельная, ещё не начатая задача.

### Критерии приёмки (обучение)

1. `python3 -m src.model.train` выполняется на реальной базе без ошибок,
   печатает и сохраняет `metrics.json` с метриками naive/logreg/lightgbm
   для обеих целей на `test`.
2. LightGBM обучается на полном `FEATURE_COLUMNS` (включая колонки с
   пропусками) без ошибок и без импутации.
3. Тесты новых функций — на синтетических данных (НФТ-8), включая: базовый
   сценарий (обучение+оценка+сохранение), граничный случай (строки с
   пропуском в целевой `league_total_over` исключаются из обучения и
   оценки), корректность наивного baseline, корректность вычисления метрик.

### Что не входит в этот этап

- Подбор гиперпараметров (сетка/случайный поиск).
- Инфраструктура инференса (подача `--upcoming`-строк в сохранённый
  артефакт) и деплой модели на сервер.
- Остальные 5 рынков.
- Бэктест против рыночных коэффициентов (см. «Ограничение данных»).

### Результаты первого прогона (02.10.2026) и переобучение после фикса (03.10.2026)

Побочная находка перед обучением: исходное определение `LR_FEATURE_COLUMNS`
оказалось на 100% пустым для 36 колонок (`home_team_away_*`,
`away_team_home_*`) — баг в `compute_form` (build_features.py), не
связанный с этим этапом: scope "away"/"home" заполнялся только для строк
с соответствующим `is_home`, поэтому «форма хозяина в гостевых матчах» и
«форма гостя в домашних» структурно никогда не вычислялись. Сообщено
в чат «Обработка данных» (их зона, ДП-3); исправлено через `merge_asof`
по `team_season_key` (коммит `d2c846b`), полный пересчёт `ml_match_features`
на проде подтверждён независимо (933-934 тыс. заполненных из 984 784,
сопоставимо с контрольной колонкой — 904 325). Модель переобучена на
исправленных данных 03.10.2026; исключение 36 колонок из
`LR_FEATURE_COLUMNS` снято.

Метрики на `test` (match_date >= 2026-01-01), после фикса:

| Цель | Модель | log loss | accuracy | Brier | n |
|---|---|---:|---:|---:|---:|
| 1X2 | naive | 1.068 | 0.441 | 0.646 | 100 339 |
| 1X2 | logreg (узкое подмн.) | 0.991 | 0.516 | 0.591 | 74 085 |
| 1X2 | LightGBM | 0.993 | 0.513 | 0.593 | 100 339 |
| ТБ/ТМ лиги | naive | 0.692 | 0.525 | 0.249 | 89 447 |
| ТБ/ТМ лиги | logreg (узкое подмн.) | 0.679 | 0.566 | 0.243 | 74 085 |
| ТБ/ТМ лиги | LightGBM | 0.677 | 0.572 | 0.242 | 89 447 |

Фикс практически не изменил метрики (разница в третьем знаке) — ожидаемо:
LightGBM и так игнорировал всегда-NaN колонки, а узкое LR-подмножество их
и раньше исключало через `dropna`. Это подтверждает, что наблюдение ниже —
не артефакт бага, а реальный результат.

**Наблюдение, требующее внимания:** для 1X2 LightGBM **не превосходит**
логрегрессию — они статистически на одном уровне (0.993 против 0.991
log loss), при том что LightGBM оценивался на более широком и объективно
более сложном подмножестве `test` (полном, без выброшенных строк с
пропуском в LR-признаках). Гипотеза спецификации («деревья выигрывают за
счёт устойчивости к пропускам») пока не подтвердилась для 1X2 — без
подбора гиперпараметров. Для ТБ/ТМ лиги LightGBM скромно, но стабильно
лучше обоих baseline. Обе модели ощутимо лучше наивного baseline на
обеих целях — сигнал в признаках есть, вопрос в том, правильно ли он
используется деревьями при текущих дефолтных гиперпараметрах.

**Критерии приёмки (обучение) выполнены**: `train.py` отрабатывает на
реальной базе без ошибок, печатает и сохраняет `metrics.json`; артефакты
сохранены в `models/` (не в Git); 19 тестов на синтетике (`test_model_train.py`
и смежные) проходят.
