# Спецификация: авторизация

## Статус

Черновик.

## Цель и границы

Позволить пользователю безопасно войти в систему. Регистрация, восстановление пароля и MFA в эту спецификацию не входят, пока не добавлены явно.

## Пользовательский сценарий

Пользователь вводит email и пароль. Система проверяет данные и при успехе создаёт авторизованную сессию или выдаёт токены согласно утверждённой архитектуре.

## Функциональные требования

- `AUTH-001`: пользователь может войти по email и паролю.
- `AUTH-002`: ошибка не раскрывает, существует ли пользователь.
- `AUTH-003`: пароль хранится только как стойкий хеш.
- `AUTH-004`: число попыток входа ограничивается.
- `AUTH-005`: успешные и подозрительные попытки отражаются в журнале аудита без секретов.

## API

`POST /api/auth/login`

Пример запроса:

```json
{
  "email": "user@example.com",
  "password": "example-only"
}
```

Формат успешного ответа определяется выбранной схемой сессий и не должен фиксироваться до архитектурного решения.

## Ошибки

- `400` — неверный формат запроса;
- `401` — неверные учётные данные;
- `429` — слишком много попыток;
- `500` — внутренняя ошибка без раскрытия деталей.

## Безопасность

Не хранить пароль в логах. Использовать современный алгоритм хеширования с подходящими параметрами. Защищать endpoint от перебора. Передавать данные только по HTTPS.

## Критерии приёмки

- [ ] корректные данные позволяют войти;
- [ ] неверный пароль и отсутствующий пользователь дают неразличимые ответы;
- [ ] пароль не хранится и не логируется открытым текстом;
- [ ] rate limit работает;
- [ ] тесты проходят.

## Тестовые сценарии

- успешный вход;
- неверный пароль;
- отсутствующий пользователь;
- пустые и некорректные поля;
- превышение лимита попыток;
- отсутствие утечки секрета в логах.
