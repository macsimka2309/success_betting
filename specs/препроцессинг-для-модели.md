# Спецификация: препроцессинг для модели предсказаний

Основание: цель проекта расширена (`docs/00-контекст-проекта.md`) — данные
теперь используются для обучения модели, предсказывающей исход матча.
Опирается на схему `docs/03-модель-данных.md`. Сама модель, её обучение
и метрики качества — вне границ этого документа (это следующий этап).

## Цель

Собрать **одну широкую материализованную таблицу** `ml_match_features`:
одна строка — один завершённый матч, целевые переменные по пяти рынкам
и признаки, известные **до начала матча**. Таблица — единственный источник
данных для обучения моделей; сами модели её только читают.

## Рынки и целевые переменные

| Рынок | Колонка | Определение |
|---|---|---|
| П1 / X / П2 | `result_1x2` | `H` \| `D` \| `A` по счёту **основного времени** |
| ТБ/ТМ (среднего по лиге) | `league_total_over` | тотал матча выше скользящей линии лиги |
| ОЗ/нОЗ (обе забьют) | `btts` | обе команды забили минимум один гол |
| ИТБ/ИТМ, хозяева | `home_total_over` | голы хозяев выше их собственной скользящей линии |
| ИТБ/ИТМ, гости | `away_total_over` | голы гостей выше их собственной скользящей линии |
| Фора (гандикап) | `handicap_favorite_covers` | фаворит матча покрыл динамическую фору (ДП-13) |
| Непроигрыш хозяев (1X) | `dc_1x` | хозяева победили или сыграли вничью |
| Непроигрыш гостей (X2) | `dc_x2` | гости победили или сыграли вничью |
| Без ничьей (12) | `dc_12` | матч закончился не вничью |

Линии (`league_total_line`, `home_team_line`, `away_team_line`,
`handicap_line`) — тоже колонки таблицы, не константы: без сохранённой
линии сравнить факт с прогнозом задним числом невозможно.

**Одна таблица обслуживает и один общий мультивыходной классификатор,
и раздельные модели по рынкам** — выбор архитектуры моделей делается на
следующем этапе и здесь не фиксируется.

## Границы

**Входит:** исправление источника счёта (ДП-0); построение таблицы признаков
и целей по завершённым матчам; правило отсечения по времени (без утечки
будущего); обработка пропусков в исходных данных.

**Не входит:** обучение моделей, подбор гиперпараметров, метрики качества
предсказаний, инференс на будущие матчи (это шаблон для отдельной
спецификации после того, как определится, как модель будет применяться
день в день), признаки на основе составов (ДП-9, отложено).

## ДП-0. Исправление источника счёта (предпосылка)

**Находка 28.09.2026.** Поле `fixtures.goals_home/goals_away` — это счёт
**после дополнительного времени**, а не по итогам основного. У API есть
отдельное поле `score.fulltime` (90 минут + добавленное время) — оно
запрашивается тем же ответом `/fixtures`, но сейчас не сохраняется.

Пример на реальных данных (fixture_id 1638620): `goals` = 2:2, `score.fulltime`
= 1:2 — гостевая победа в основное время, которую мы разметили бы как ничью.
Рынок П1/X/П2 всегда считается по основному времени; тоталы и ОЗ/нОЗ по
итоговому счёту тоже расходятся с 90-минутным при разных сценариях доп.
времени.

**Масштаб:** 2 972 матча со статусом `AET`/`PEN` (0,27% базы), сосредоточены
в кубковых турнирах (топ-5 лиг дают от 17 до 46 таких матчей). Для обычных
`FT`-матчей `goals` и 90-минутный счёт совпадают — исправление их не касается.

**Решение:**
1. Миграция добавляет `fixtures.ft90_home`, `fixtures.ft90_away`
   (`SMALLINT`, `NULL` по умолчанию) — счёт основного времени.
2. Шаг сбора «матчи» (`src/jobs/collect.py::run_fixtures`) при разборе ответа
   дополнительно сохраняет `score.fulltime`. Для будущих матчей это не
   стоит ни одного лишнего запроса — поле уже приходит в том же ответе.
3. Разовая дозагрузка `score.fulltime` для 2 972 уже собранных `AET`/`PEN`
   матчей: `/fixtures?id=…`, по одному запросу на матч (~3 000 запросов,
   укладывается в один день остатка лимита).
4. Регулярный счёт для целей: `reg_home = COALESCE(ft90_home, goals_home)`,
   аналогично для гостей. Для `FT`-матчей `ft90_*` остаётся `NULL`,
   и `COALESCE` берёт `goals_*` — переопределять миллион строк не нужно.

Без этого пункта таблица признаков не строится: он определяет, что вообще
считается «результатом матча».

## ДП-1. Отсечение по времени (защита от утечки будущего)

Признаки для матча `M` с временем начала `kickoff_at(M)` вычисляются только
по матчам `N`, для которых `kickoff_at(N) < kickoff_at(M)` (строго раньше)
и у которых уже известен регулярный счёт (ДП-0). Матчи без результата
(`NS`, `PST`, …) в скользящие расчёты не входят.

**Исключение — травмы.** `injuries.fixture_id = M` — это сведения о травмах
именно к матчу `M`, известные заранее, а не результат матча. Такие строки
используются напрямую (ДП-6), не через скользящее окно.

**Не входит в v1 — составы.** См. ДП-9.

## ДП-2. Линии рынков ТБ/ТМ и ИТБ/ИТМ

**Решение 29.09.2026: обе линии считаются в рамках сезона** (лига **и**
сезон, не только лига) — матчи прошлого сезона не участвуют. Причина:
состав лиги и состав команды меняются на межсезонье (переходы, вылет/выход
в высший дивизион), и смешивать сезоны в одну среднюю величину означало
бы усреднять разные по силе версии одной и той же лиги или команды.

Отсюда следствие: фиксированное окно вроде «последние 100 матчей» плохо
сочетается с границей сезона — в начале сезона такого окна просто не
набирается, а к концу оно избыточно велико относительно того, что вообще
есть в сезоне. Поэтому вместо трейлингового окна фиксированного размера —
**накопительное среднее с начала текущего сезона**, без верхнего предела:

| Линия | Что усредняется | Область усреднения |
|---|---|---|
| `league_total_line` | суммарный тотал матча (`reg_home + reg_away`) | все матчи `(league_id, season)` этой лиги с начала сезона |
| `home_team_line` | голы, забитые командой **дома** | домашние матчи этой команды в `(league_id, season)` с начала сезона |
| `away_team_line` | голы, забитые командой **в гостях** | гостевые матчи этой команды в `(league_id, season)` с начала сезона |

Линии для дома и гостей считаются раздельно (команда дома в среднем
забивает больше, чем в гостях) — это соответствует принятому решению
«скользящее среднее по команде».

**Минимум данных.** Проверено на реальных данных Премьер-лиги (2024/25):
20-й матч лиги в сезоне происходит уже 25 августа — почти сразу после
старта, а 8-й домашний матч отдельной команды — в среднем 7 декабря, то
есть у 40% сезона. Порог `MIN_WINDOW = 20` для `league_total_line`
безопасен при переходе на накопительный расчёт в рамках сезона. Порог
для командных линий снижен: **`MIN_WINDOW = 3`** домашних/гостевых
матча — тот же порог, что дальше используется для формы команды (ДП-3),
и он открывает ИТБ/ИТМ уже после третьего матча команды в сезоне, а не
после восьмого.

Если для линии не набралось минимума — строка **не включается** в
таблицу для этого рынка (`league_total_line`, `home_team_line` или
`away_team_line`, а с ней и соответствующий `*_over`, получают `NULL`,
остальные рынки строки это не затрагивает). Лучше меньше строк, чем
линия, посчитанная по одному матчу.

## ДП-13. Фора (гандикап) — динамическая линия

Решение 28.09.2026: фора считается **по разнице уже готовых командных
линий** из ДП-2, без отдельной модели силы команд.

```
raw_handicap  = home_team_line − away_team_line
favorite      = 'home', если raw_handicap >= 0, иначе 'away'   (при равенстве — хозяева, условность)
handicap_line = floor(|raw_handicap|) + 0.5                    -- та же формула, что в ДП-2
```

`home_team_line` — домашняя результативность хозяев, `away_team_line` —
гостевая результативность гостей (те же значения, что уже посчитаны для
ИТБ/ИТМ), поэтому фора не требует новых входных данных.

**Покрытый счёт фаворита:**

```
margin(favorite='home') = reg_home − reg_away
margin(favorite='away') = reg_away − reg_home
handicap_favorite_covers = margin > handicap_line
```

Формула `floor(x) + 0.5` — та же, что в ДП-2 для линий тотала: результат
всегда `0.5, 1.5, 2.5, …`, никогда не целое число, поэтому margin (он
всегда целый — разница голов) не может совпасть с линией, и «пуш» по
форе невозможен по построению.

Если `home_team_line` или `away_team_line` — `NULL` (см. ДП-2, минимум
данных), `handicap_line` и `handicap_favorite_covers` тоже `NULL`.

## ДП-14. Непроигрыш (двойной шанс)

Три бинарные колонки, прямая производная от `result_1x2` (ДП-0), без
дополнительных вычислений и допущений:

```
dc_1x = result_1x2 in ('H', 'D')   -- хозяева не проиграли
dc_x2 = result_1x2 in ('A', 'D')   -- гости не проиграли
dc_12 = result_1x2 in ('H', 'A')   -- без ничьей
```

## ДП-3. Признаки формы команды

**Решение 29.09.2026: окна сокращены и ограничены текущим сезоном** —
`SHORT = 3`, `LONG = 5` последних матчей **того же `(league_id, season)`**,
что и матч `M`; матчи прошлого сезона в окно не попадают. Форма должна
отражать, как команда играет сейчас, а не память через межсезонье с
изменившимся составом.

Для обеих команд матча, раздельно `overall` (все матчи) / `home` (только
дома) / `away` (только в гостях), в обоих окнах:

- `goals_scored_avg`, `goals_conceded_avg`;
- `points_avg` (победа 3, ничья 1, поражение 0), `win_rate`, `draw_rate`, `loss_rate`;
- `clean_sheet_rate` (не пропустила), `failed_to_score_rate` (не забила);
- `matches_played` — сколько матчей реально нашлось в окне (знаменатель).

**В отличие от линий (ДП-2), здесь нет `MIN_WINDOW`-отсечения**: признак
считается по тому, что есть, хоть по одному матчу, а `matches_played`
явно показывает, на скольких матчах он основан. Причина — форма это
входной признак, а не сама целевая переменная: NULL-ить её на первые
3–5 матчей **каждой** команды **каждой** лиги **каждый** сезон означало
бы систематическую дыру в начале каждого сезона по всей выборке. Первый
матч сезона неизбежно будет с `matches_played = 0` и пустыми средними —
это ожидаемо, не ошибка.

Схема именования: `{сторона}_{охват}_{окно}_{метрика}`, например
`home_team_home_last3_goals_scored_avg` — команда хозяев, только её
домашние матчи текущего сезона, последние 3, среднее забитых.

## ДП-4. Признаки статистики матча

Из `fixture_statistics`, теми же окнами, разбивкой и правилом сезона,
что в ДП-3: `shots_on_goal_avg`, `total_shots_avg`, `corner_kicks_avg`,
`ball_possession_avg`, `expected_goals_avg` (свои и пропущенные — `_for`
и `_against`).

**Покрытие сейчас тонкое** — 13–20% матчей в год имеют статистику
(проверено на базе 28.09.2026). Эти признаки будут `NULL` там, где в окне
не нашлось ни одного матча со статистикой. Рядом с каждой группой признаков
хранится `{...}_coverage` — доля матчей окна, по которым статистика была
(0.0–1.0), чтобы при обучении можно было отличить «команда играет слабо»
от «данных просто нет».

## ДП-5. Личные встречи (head-to-head) — исключение из правила сезона

**Решение 29.09.2026: сквозной расчёт по всем сезонам, без ограничения
сезоном.** Причина: команды за один сезон встречаются один-два раза,
поэтому в границах сезона очных встреч почти никогда не набралось бы —
признак был бы `NULL` почти всегда, что обесценивает саму идею личных
встреч.

По последним `H2H_WINDOW = 5` очным матчам этих двух команд (в любом
порядке хозяева/гости), до `kickoff_at(M)`, по всей истории: средний
суммарный тотал, доля побед каждой стороны, доля ничьих. Если очных
встреч в истории меньше 2 — поле `NULL`.

## ДП-6. Травмы к матчу

`injuries_home_count`, `injuries_away_count` — число травмированных
игроков каждой команды, привязанных к `fixture_id = M` (см. ДП-1,
это не утечка). Разбивки по типу травмы нет: то, что есть в источнике,
уже посчитано.

**Ограничение.** Счётчик не различает важность игрока: пропуск ключевого
форварда и пропуск третьего вратаря дают одинаковый `+1`. Причина —
в базе нет статистики игрока (голы, минуты на поле, статус в заявке),
только `players.name`. См. ДП-6.1 — пункт на будущее.

### ДП-6.1. Вес травмы по вкладу игрока — вне охвата v1 (задел на будущее)

Идея: заменить счётчик травм на сумму «веса» травмированных игроков —
например, доли голов команды, которые каждый из них забил за последние
N матчей до травмы. Тогда пропуск лучшего бомбардира весит больше, чем
пропуск запасного.

Считается из уже собираемых данных, без новых запросов к API:

- **вклад в атаку** — из `fixture_events` (тип `Goal`) с разбивкой по
  `player_id`, скользящим окном, как в ДП-3;
- **статус в составе** (основа/ротация) — из `fixture_lineup_players`,
  доля матчей в старте за последние N игр.

**Почему не в v1.** Покрытие `fixture_lineup_players` сейчас 0,7% матчей
(см. ДП-9) — статус «основа/ротация» посчитать почти не для кого. Вклад
в атаку из `fixture_events` посчитать можно уже сейчас (покрытие событий
выше), но без статуса в составе он даёт только половину смысла: игрок
мог забивать много голов, выходя на замену. Возвращаемся к этому пунктом
вместе с ДП-9, когда дозагрузка составов продвинется существенно дальше.

## ДП-7. Контекст лиги и турнирное положение

- `league_home_win_rate`, `league_draw_rate`, `league_away_win_rate` —
  накопительно с начала текущего сезона (тот же принцип и тот же
  `MIN_WINDOW = 20`, что у `league_total_line` в ДП-2), базовая частота
  исходов в этой лиге на данный момент сезона;
- `home_team_rank`, `away_team_rank`, `points_gap` — положение в таблице
  **текущего сезона** на дату матча. Считается по фактическим результатам
  (очки, разница мячей) **по датам матчей**, не по текстовому полю
  `round`: оно не всегда упорядочено одинаково между лигами и ненадёжно
  для сортировки. Турнирная таблица по определению начинается с нуля
  каждый сезон — здесь правило сезона совпадает с самой природой признака,
  не требует отдельного решения.

## ДП-8. Рейтинг силы команд (Elo) — исключение из правила сезона

**Решение 29.09.2026: рейтинг сквозной, не сбрасывается по сезонам.**
Причина: Эло — не скользящее окно, а непрерывно обновляемая оценка силы
команды, и весь смысл подхода в том, что рейтинг переносит форму команды
через межсезонье, а не в том, что он «окно» какого-то размера. Обнулять
его каждый сезон означало бы каждый раз выбрасывать самую суть признака.

Скользящий рейтинг Эло по каждой отслеживаемой лиге отдельно (кубковые
турниры между разными лигами не смешиваются), с постоянной поправкой на
преимущество своего поля. Рейтинг команды **до** матча — `home_team_elo`,
`away_team_elo`, разница — `elo_diff`. Обновляется последовательно, в
хронологическом порядке матчей: это единственный признак, который нельзя
посчитать оконным SQL-запросом, только проходом по истории по порядку дат
(довод в пользу решения ДП-11 — Python, не SQL VIEW).

Стартовый рейтинг новой команды — среднее по лиге на момент её первого матча.

## ДП-9. Составы — вне охвата v1

Причины: покрытие `fixture_lineups` сейчас 7 665 из 1 096 183 матчей
(0,7%); и содержательная — состав объявляется примерно за час до матча,
а не тогда, когда реально понадобится прогноз в течение дня. Возвращаемся
к этому явным отдельным решением после того, как определится, за сколько
времени до матча модель должна выдавать прогноз, и когда дозагрузка
составов продвинется существенно дальше. Вместе с этим пунктом
пересматривается и ДП-6.1 (вес травмы по вкладу игрока) — они зависят
от одного и того же покрытия.

## ДП-10. Коэффициенты — не признак, только для сверки

По вашему решению коэффициенты не входят в признаки модели: если линия
буквально копируется в модель, она выучится копировать рынок и не даст
основания для сравнения с ним. Предлагаю дополнительно — **вне признаков**
— сохранить в отдельных колонках `eval_*` ближайший к матчу снимок линии
(1xBet/Pinnacle) по каждому рынку: `eval_odds_home`, `eval_odds_draw`,
`eval_odds_away`, `eval_odds_league_total_over/under`, `eval_odds_btts_yes/no`,
`eval_odds_home_total_over/under`, `eval_odds_away_total_over/under`,
`eval_odds_handicap_favorite_covers`, `eval_odds_dc_1x/x2/12` — из
последнего `odds_snapshots` перед `kickoff_at`. Не для каждого рынка
у букмекера обязательно найдётся точная линия, совпадающая с нашей
(especially для форы и ИТБ/ИТМ, где линия у нас своя, расчётная, а у
букмекера — его собственная); для таких случаев колонка остаётся `NULL`,
это ожидаемо, а не ошибка. Эти колонки нужны только
для того, чтобы после обучения сравнить прогноз модели с рынком (ради
этого весь проект и задумывался, судя по вашему подходу к value-бетам).
Модель их не видит: они не подаются на вход при обучении, только читаются
при оценке. **Решение 28.09.2026: добавлять, в признаки не включать** —
именно так и реализовано (колонки существуют в таблице, но не входят
ни в один `*_feature`-список, который пойдёт на вход модели).

## ДП-11. Материализация и обновление

**Таблица**, не VIEW (принятое решение): рейтинг Эло (ДП-8) в принципе
не выражается оконным SQL-запросом, а остальные признаки на миллионе с
лишним строк в VIEW считались бы заново при каждом обращении.

**Job** `src/jobs/build_features.py`, Python (`pandas`, уже зависимость
проекта): читает сырые таблицы, строит признаки проходом по матчам в
хронологическом порядке (нужен для Эло и корректных скользящих окон),
пишет в `ml_match_features` пакетами через `ON CONFLICT DO UPDATE` по
`fixture_id` — тот же приём, что в `src/common/db.py`.

**Инкрементальность.** Полный пересчёт всех строк — дорогая операция
(проход по 1 млн+ матчей с оконными расчётами и Эло). Два режима:

- `--incremental` (по умолчанию): досчитывает только матчи, у которых
  `kickoff_at` позже последней уже посчитанной строки, продолжая
  Эло-рейтинг и скользящие окна с сохранённого состояния;
- `--full-rebuild`: пересчитывает всё заново. Нужен, когда меняется
  определение признака, и периодически, пока идёт дозагрузка (ДП-12).

**Состояние Эло между запусками** хранится в отдельной служебной таблице
`ml_team_elo_state` (`team_id`, `league_id`, `rating`, `as_of_fixture_id`) —
без неё инкрементальный режим не смог бы продолжить рейтинг, не пересчитав
историю с нуля.

## ДП-12. Пересчёт по мере дозагрузки

Дозагрузка (`specs/дозагрузка-пропущенного.md`) продолжает дополнять
статистику и составы по старым матчам. Когда она дозаполняет матч из
прошлого, все более поздние строки, чьи скользящие окна его затрагивают,
формально устарели (их `*_coverage` могли вырасти).

**Решение:** `--full-rebuild` запускается **раз в неделю** отдельным
заданием cron, пока дозагрузка разрыва не завершится (ожидается
к 3–4 октября, `docs/04`); после этого — по необходимости, вручную.
Ежедневных инкрементальных дозапусков это не отменяет: они добавляют
вчерашние матчи между полными пересчётами.

## Интерфейс

```bash
python3 -m src.jobs.build_features                          # инкрементально
python3 -m src.jobs.build_features --full-rebuild
python3 -m src.jobs.build_features --short-window 3 --long-window 5 --h2h-window 5 --min-league-matches 20 --min-team-matches 3
```

Строка подключения — из `DATABASE_URL`, как у остальных заданий. Запросов
к API не делает — только к базе.

## Ошибки и крайние случаи

| Ситуация | Поведение |
|---|---|
| Недостаточно матчей для линии (ДП-2) | линия и её `*_over` — `NULL`, остальные рынки строки не затронуты |
| Нет статистики в окне (ДП-4) | признаки `NULL`, `*_coverage = 0`, строка не исключается |
| Меньше 2 личных встреч (ДП-5) | h2h-признаки `NULL` |
| Новая команда без истории | Эло — средний по лиге старт; форма и линии — по правилу минимума данных |
| Матч без регулярного счёта (`NS`, отменён) | не попадает в таблицу вовсе — целей нет |
| Прерывание `--full-rebuild` посередине | незавершённый пересчёт не публикуется: пишет во временную таблицу, переключает одним `RENAME` по завершении (атомарно, старые данные читаемы всё время пересчёта) |
| Изменилось определение признака | требует `--full-rebuild`, инкрементальный режим этого не обнаружит |

## Безопасность

Только чтение сырых таблиц и запись в `ml_match_features`/`ml_team_elo_state`.
Секретов не использует, к API не обращается.

## Критерии приёмки

1. `ДП-0` применена: `ft90_*` заполнены у всех 2 972 `AET`/`PEN`-матчей,
   `result_1x2` считается по `COALESCE(ft90_*, goals_*)`.
2. Признак матча `M` не зависит от исхода `M` и от любого матча позже него
   (проверяется тестом: изменение будущего матча не меняет уже посчитанную
   строку).
6. Фора никогда не кратна целому числу; `handicap_favorite_covers`
   согласуется с `result_1x2` (нельзя, чтобы фаворит «не покрыл» фору
   при этом выиграв с большим отрывом, чем сама линия).
7. `dc_1x`, `dc_x2`, `dc_12` в точности следуют из `result_1x2` на всей
   таблице без исключений (это тождество, не статистика).
3. Повторный `--incremental` запуск не меняет ранее посчитанные строки.
4. `--full-rebuild` и последовательные `--incremental` с того же исходного
   состояния дают одинаковый результат.
5. Отчёт по завершении: число строк по каждому рынку, средняя `*_coverage`
   по статистике, распределение `result_1x2`/`btts`/`*_over` — простая
   проверка на перекос классов перед обучением.
