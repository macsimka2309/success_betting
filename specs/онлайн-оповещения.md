# Спецификация: оповещения по идущим матчам в Telegram

Основание: запрос владельца (15.10.2026). Опирается на `docs/02-архитектура.md`
(ADR-3: cron без планировщика), `docs/05-безопасность.md` (секреты),
`specs/ежедневный-сбор.md` (журнал `collection_runs`, лимит API), клиент
`src/api/client.py`.

Статус: **утверждена 15.10.2026**. Ответы владельца на открытые вопросы:
доставка — через собственный сервер за рубежом; бюджет — 300 запросов в сутки на
оповещения, ежедневный сбор уменьшен с 6 500 до 6 200; память «уже отправлено» — в базе
(владелец разрешил также дублировать информацию в боте, поэтому сообщение в Telegram
служит ещё и журналом); канал и бот у владельца есть.

## Цель

Каждые 10 минут в дневное и вечернее время смотреть на идущие матчи и, когда
матч подходит под заданное условие (триггер), присылать сообщение в Telegram-канал.
Данные идущих матчей пока **не хранятся**: только оповещение.

## Проверено на живом API (15.10.2026)

- `GET /fixtures?live=all` — все идущие матчи одним запросом: минута
  (`fixture.status.elapsed`), статус, счёт (`goals`), события. **Статистики в
  ответе нет.**
- `GET /fixtures?ids=<id>-<id>-…` (до 20 матчей) возвращает для каждого матча
  `events`, `lineups`, `statistics`, `players`. Значит, статистику для всех
  кандидатов можно получить **одним запросом**, а не по запросу на матч.
- У части матчей (низшие лиги) блок `statistics` пустой: данных нет, оповещение
  по ним невозможно (сценарий «нет необходимой информации»).
- С нашего сервера `api.telegram.org` **недоступен** (таймаут 10 с, 15.10.2026).
  Способ доставки — открытый вопрос 1.

Частота обновления по документации: матчи и события — каждые 15 секунд, статистика —
каждую минуту (приблизительно, зависит от турнира). Шаг 10 минут в пределах этого.

## Пользовательские сценарии

1. В 18:20 по Москве идёт матч, 67-я минута, у одной из команд (хозяев или гостей)
   владение 58 % и 7 ударов в створ (при любом счёте). Приходит сообщение.
2. Тот же матч в 18:30 всё ещё подходит под условие. Повторного сообщения нет.
3. Матч низшей лиги без статистики не даёт сообщений, ошибки нет.

## Триггер

Оповещение отправляется, если у идущего матча одновременно выполняется всё:

| № | Условие | Источник |
|---|---|---|
| Т-1 | минута матча от 60 до 75 включительно | `fixture.status.elapsed` |
| Т-2 | ~~хозяева проигрывают или играют вничью~~ — **убрано 15.10.2026** по решению владельца: счёт в условии не участвует (в сообщении остаётся для информации) | — |
| Т-3 | владение мячом команды строго больше 55 % (с целыми процентами это 56 % и выше) | `statistics`, `Ball Possession` |
| Т-4 | удары в створ той же команды не меньше 6 | `statistics`, `Shots on Goal` |

Т-3 и Т-4 проверяются для **каждой из двух команд** (с 16.10.2026; раньше только для
хозяев): достаточно, чтобы обоим условиям отвечала одна и та же команда. Владение больше
55 % возможно только у одной команды, поэтому оповещений по матчу не больше одного.
Матчи в дополнительное время и серии пенальти
не рассматриваются: берутся только статусы первого и второго тайма
(`1H`, `2H`); минута 60–75 на практике относится ко второму тайму.
Если любое значение отсутствует или не число, матч не подходит.

## Вторая категория: владение во втором тайме (с 16.10.2026)

Отдельный триггер, независимый от первого. Оповещение отправляется, если у **любой из двух команд**
владение мячом **во втором тайме** строго больше 70 % (точное значение — из блока
`statistics_2h` запроса `fixtures/statistics?fixture=…&half=true`). Счёт не фильтруется. Матч должен
идти во втором тайме и находиться в той же минуте, что и первый триггер: 60–75 (допущение, меняется
константами). В сообщении: `Тип: владение во 2-м тайме`, команда, владение во втором тайме и за матч.

**Экономия запросов.** Точный запрос по таймам стоит отдельный вызов на матч, и без отбора
их было бы около тысячи в сутки. Поэтому:
1. Для матчей со статусом `HT` (перерыв) один раз берётся статистика пачкой `ids=`; итог на
   перерыве равен первому тайму. Владение обеих команд сохраняется в `live_ht_possession`
   (рабочая память, чистится через 2 суток).
2. В окне 60–75 по итогу за матч и сохранённому первому тайму оценивается второй тайм:
   `(итог · минута − первый_тайм · 45) / (минута − 45)`. Оценка приближённая (равномерное
   распределение владения по времени), поэтому порог отбора **62 %**, а не 70.
3. Только матчи с оценкой выше 62 % получают точный запрос; решение принимается по точному значению.
4. Если снимка на перерыве нет (оповещения не успели его взять, нет статистики), матч в категории
   не проверяется.

Оповещения уникальны по паре (матч, категория): по одному матчу могут прийти оба, с разными ID.
Расход запросов оповещений: оценочно до 500 в сутки (было 300); ежедневный сбор уменьшен с 6 200
до 6 000, итог 6 000 + 2 × 300 + 50 + 300 + 500 = 7 450 из 7 500. Потолок на запуск — 30.
Ограничение: оценка может пропустить редкий случай, когда оценка ниже 62 %, а точное значение выше 70.

## Третья категория: атака во втором тайме (с 16.10.2026)

Оповещение, если у **любой из двух команд на момент среза (запуска)** во втором тайме одновременно
**4 и более ударов в створ** и **владение строго больше 55 %**. Счёт не фильтруется. Матч идёт
во втором тайме в минутах 60–75 (то же окно, что у остальных категорий; допущение). Значения
берутся из `statistics_2h` запроса `fixtures/statistics?fixture=…&half=true`.

**Отбор без лишних запросов.** Удары в створ складываются, поэтому удары второго тайма равны
итогу за матч минус удары на перерыве: снимок на перерыве (`live_ht_possession`) теперь хранит и
удары в створ. Матч идёт на точный запрос только если у команды по этой разности 4 и более ударов
и оценка владения во втором тайме выше 48 %. Один точный запрос на матч обслуживает обе категории
второго тайма (владение больше 70 % и атака). Без снимка с ударами категория по матчу не проверяется.

В сообщении: `Тип: атака во 2-м тайме`, команда, владение и удары в створ второго тайма, удары
соперника. Одно оповещение на матч в каждой категории.

**Бюджет:** оценочно +100–200 запросов в сутки к категориям выше; бюджет оповещений остаётся
500 в сутки, фактический расход сверяется по журналу через сутки.

## Учёт проходимости (с 17.10.2026)

Каждое оповещение любой категории заносится в таблицу `live_alerts_sent` (она и есть реестр
рекомендованных событий) и после матча получает отметку: **был ли ещё хотя бы один гол после
75-й минуты**. Денег нет, цель — оценивать, как часто рекомендации «проходят».

- **Что считается:** гол любой из двух команд на 76-й минуте и позже в основное время, включая
  добавленное (минуты 90+N). Дополнительное время и серия пенальти не учитываются. Автогол и пенальти
  в основное время считаются, незабитый пенальти нет.
- **Статусы `outcome`:** `pending` (ждёт конца матча), `hit` (гол после 75-й был), `miss` (не было),
  `void` (матч отменён или перенесён), `no_data` (источник отдал неполные события: число голов в
  событиях не сходится со счётом основного времени; такие оповещения в оценку не входят).
- **Кто проставляет:** задание `settle_bets` каждые 30 минут. Оно использует тот же запрос
  `fixtures?ids=` (ответ содержит события), что и расчёт ставок, поэтому отдельных запросов почти не
  тратит. К матчу обращается, когда с момента оповещения прошло не меньше 40 минут.
- **Дополнительные поля:** `goals_after_75`, итоговый счёт основного времени, `resolved_at`.
- **Просмотр:** представление `alert_hit_rate` (по категориям: оповещений, оценено, голов после 75-й,
  процент, ожидают) и кнопка бота «Проходимость» с тем же содержимым.

## Функциональные требования

| № | Требование |
|---|---|
| ОП-1 | Запуск каждые 10 минут по расписанию cron с 10:00 до 01:00 по Москве включительно: в 10:00, 10:10 … 23:50, 00:00 … 00:50 и 01:00. Сервер работает в MSK. |
| ОП-2 | Каждый запуск делает один запрос `fixtures?live=all`, отбирает матчи по Т-1, и только для них запрашивает `fixtures?ids=…` пачками не более 20. |
| ОП-3 | Триггеры Т-3 и Т-4 проверяется по блоку `statistics` из ответа `ids=`. |
| ОП-4 | Для подходящего матча в канал уходит одно сообщение (формат ниже). |
| ОП-5 | Повторная отправка по одному и тому же матчу не происходит (защита от дублей). |
| ОП-6 | Если отправка в Telegram не удалась, оповещение считается неотправленным и повторяется на следующем запуске, пока матч подходит под условие. |
| ОП-7 | Режим `--dry-run`: те же расчёты, сообщение печатается в журнал вместо отправки. Нужен для проверки на проде до включения. |
| ОП-8 | Каждый запуск пишет строку в `collection_runs` (`job_name = 'live_alerts'`, запросов, отправлено оповещений). |
| ОП-9 | У запуска свой потолок запросов (по умолчанию 10) и суточный потолок на стороне cron-обёртки; при исчерпании лимита API запуск завершается штатно. |

## Формат сообщения

```
Лига: Pro League (Saudi-Arabia)
Матч: Al-Faisaly FC — Al Kholood
Минута: 67' | Счёт: 0:1
Команда: Al Kholood (гости)
Владение: 58 %
Удары в створ: 7 против 2
```

Одно сообщение на матч; в строке «Команда» указано, по кому сработало условие. Обычный текст без форматирования (без риска поломки
из-за спецсимволов в названиях).

## Данные и хранение

Снимки идущих матчей **не сохраняются** (решение владельца: хранение настроим позже).
Для защиты от дублей (ОП-5) нужна минимальная память «по этому матчу уже
отправлено». Предлагается таблица:

`live_alerts_sent` — `fixture_id` (ключ), время отправки, лига, названия команд, минута, счёт,
`team_side` (хозяева или гости), владение и удары в створ сработавшей команды и удары соперника. Один матч — одна строка.
Журнал отправленных оповещений пригодится и позже для разбора срабатываний.

Миграция 007 (номера 005–006 заняты миграциями «Анализа данных»), аддитивная, без блокировок, с `.down.sql`.

## Бюджет запросов API

Один запуск: 1 запрос `live=all` + `ceil(кандидатов / 20)` запросов `ids=`; кандидатов
обычно от 0 до нескольких десятков. Оценка: 91 запуск в сутки, от 91 до ~250 запросов.
Суточный лимит тарифа 7 500; сейчас расписание заполняет его до 7 450
(`6 500` ежедневный + `2 × 300` коэффициенты + `300` международные + `50` каталог).
Для оповещений предлагается выделить 300 и уменьшить ежедневный сбор
с 6 500 до 6 200 (открытый вопрос 4).

## Расписание и доставка

- cron-строка в `/etc/cron.d/football-collector` (время MSK, как остальные):
  `*/10 10-23 * * *`, `*/10 0 * * *` и `0 1 * * *`, через обёртку с `flock`
  (запуски не накладываются) и проверкой часового пояса, как у `run_collect.sh`.
- Доставка в Telegram — Bot API, метод `sendMessage` по HTTPS. С сервера
  доступа нет, способ описан в открытом вопросе 1.

## Безопасность

- Токен бота и идентификатор канала хранятся только в `.env` на машине, где
  работает отправка (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`). В Git и в чат
  они не попадают; владелец кладёт их в файл сам.
- Адрес запроса к Telegram содержит токен. Тексты ошибок и журнал не выводят
  адрес целиком: исключения перехватываются, в журнал пишется только код ответа.
- Бот имеет право писать только в заданный канал (должен быть администратором
  канала). Входящих сообщений бот не обрабатывает.
- В сообщения идут публичные спортивные данные.

## Ошибки и крайние случаи

| Ситуация | Поведение |
|---|---|
| Нет идущих матчей | запуск делает 1 запрос и завершается |
| Матч подходит по Т-1, но статистики нет | не оповещаем, учитываем в счётчике пропущенных |
| В ответе `ids=` у матча нет `statistics` для одной из команд | не оповещаем |
| Ошибка или таймаут API | запуск завершается со статусом `failed` в журнале, следующий запуск через 10 минут |
| Лимит API исчерпан | штатное завершение, статус `quota_exceeded` |
| Telegram недоступен или вернул ошибку | оповещение не помечается отправленным, повтор на следующем запуске (ОП-6) |
| Два запуска наложились | второй не стартует (`flock`) |
| Сменился часовой пояс сервера | обёртка отказывается работать |
| Матч прервали, отложили или он закончился между запросами | считаем по последним данным ответа; завершённые не рассматриваются |

## Критерии приёмки

| № | Критерий |
|---|---|
| АП-1 | Для таблицы тестовых матчей решение «оповестить / нет» совпадает с ожидаемым на границах: минута 59/60/75/76, счёт любой, команда хозяев и команда гостей, владение 55/56, удары в створ 5/6 |
| АП-2 | Один подходящий матч в двух подряд запусках даёт ровно одно сообщение |
| АП-3 | При ошибке отправки второй запуск повторяет сообщение, после успеха больше не повторяет |
| АП-4 | Запуск с N кандидатами делает `1 + ceil(N/20)` запросов и не превышает потолок |
| АП-5 | Матч без статистики не вызывает ошибку и сообщение |
| АП-6 | В журналах и текстах ошибок нет токена |
| АП-7 | `--dry-run` на проде в течение суток: журнал показывает срабатывания, сообщений в канал нет |
| АП-8 | Расписание срабатывает ровно в окне 10:00–01:00 MSK (проверка строк cron) |

## Тестовые сценарии

Основной: подходящий матч → одно сообщение с верными числами. Граничные: см. АП-1,
плюс `elapsed = None`, нулевое число кандидатов, ровно 20 и 21 кандидат (одна и две
пачки). Ошибки: пустой `response`, `errors` в теле, таймаут, код 429 и 4xx/5xx
от Telegram, обрыв сети. Некорректный ввод: нечисловые значения статистики,
`"58%"` строкой, `null`. Идемпотентность и повторы: ОП-5, ОП-6. Безопасность:
токен не попадает в журнал и текст исключения. Прав доступа в системе нет, кроме
доступа бота к каналу; проверяется вручную при включении.
