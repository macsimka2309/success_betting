# Оповещения по общим live-данным API-Football и Fonbet

Дата: 10.11.2026. Статус: **согласована владельцем 10.11.2026;
реализована и включена на vac-ru 10.11.2026**.

Основание: отправлять в существующий Telegram-бот подходящие матчи обоих
источников после обновления live-данных, если матч ещё не был отправлен.
Связанные спецификации: [оповещения](онлайн-оповещения.md),
[объединение источников](объединение-live-api-fonbet.md),
[сбор Fonbet](лайв-статистика-fonbet.md), [реестр ставок](реестр-ставок.md).

## Цель и действующий триггер

Сборщики отвечают за получение и сохранение данных. Отдельный диспетчер
принимает решение по сохранённым данным, ведёт общую очередь и отправляет
одно сообщение на матч независимо от источника.

Активна категория `half_pressure`. Условия одинаковы для API-Football и Fonbet:

- обычный футбольный матч во втором тайме, минута **65–75 включительно**;
- **не менее 8 ударов в створ суммарно у обеих команд за второй тайм**
  **ИЛИ не менее 5 у любой одной команды за второй тайм**;
- счёт любой, **ничейные матчи включаются**; владение не требуется;
- матч ещё не отправлен и не находится в очереди отправки.

Применяются действующие исключения: название лиги начинается на `FC`
без учёта регистра/начальных пробелов, футзал, микрофутзал, тег события `2X40`
(включая `2Х40`, `2×40` и варианты с пробелами). Для API использовать
подтверждённые признаки формата; не переносить исключение по названию команды.
Другие категории автоматически не включаются.

Ноль — значение, отсутствие — NULL. Для суммы нужны обе команды.
При `5 : NULL` условие выполнено, при `4 : NULL` результат проверки неизвестен,
при `4 : 4` выполнено, при `4 : 3` не выполнено. Статистика за матч и вычисленная
разность таймов не подменяют прямые данные второго тайма.

## Почему нужен отдельный слой отправки

`live_match_statistics_75_combined` — SQL VIEW из миграции 026, а не обновляемая
таблица. Она выбирает API-срез при его наличии, включая частичный и старый,
и остаётся аналитической выборкой. Записи источников сохраняются после матча;
сам факт наличия строки с минутой 75 не означает, что матч сейчас идёт.
Прямой триггер UPDATE на этой view или чтение всех её исторических строк
не является достаточным механизмом live-отправки.

Для уведомлений нужен отдельный операционный запрос к исходным срезам 023/025
и подтверждённым связям 026: идентичность и выравнивание команд переиспользуются,
но свежесть и пригодность для триггера проверяются до выбора источника.
Показатели одной карточки берутся из одного наблюдения одного источника.

## Предлагаемый цикл

1. API-Football и Fonbet продолжают собираться независимо каждые 5 минут.
   Сбор и сопоставление коммитятся до обработки оповещений. Ошибка Telegram
   не отменяет сохранение исходных данных.
2. Отдельный серверный диспетчер запускается **каждую минуту**, без пересечения
   своих запусков. Это частота проверки БД, а не новый опрос внешних источников.
   Максимальная штатная задержка обнаружения изменения — один цикл диспетчера.
3. Диспетчер читает свежие срезы обоих источников и актуальное состояние связей.
   Проверяет все свежие ещё не отправленные матчи, включая повторно пригодные
   срезы, новые подтверждения связей и ранее неудачные попытки доставки.
   Единственный timestamp-watermark использовать нельзя: он пропускает
   повторную доставку, смену приоритетного источника и позднее сопоставление.
4. После выбора пригодного источника вычисляет триггер и в транзакции резервирует
   общую идентичность матча, `alert_id` и строку очереди. Конкурентная обработка
   защищается ограничением уникальности и блокировкой строки в БД.
5. Отправитель получает задание из очереди, повторно проверяет свежесть,
   текущий контекст матча, сопоставление и память отправленного. Затем отправляет
   сообщение через действующий транспорт Telegram.
6. Подтверждённый успех сохраняет `telegram_message_id`, время и факт доставки.
   При следующем обновлении любого источника этот матч повторно не отправляется.

LISTEN/NOTIFY может позднее ускорить пробуждение, но не заменяет периодическую
сверку БД: пропуск уведомления или перезапуск процесса не должен терять матч.
Сервис не делает дополнительных запросов статистики к API-Football или Fonbet.

## Свежесть и выбор источника для оповещения

Предлагаемый стартовый TTL среза — **120 секунд от `observed_at`**,
настраиваемый и проверяемый при приёмке. `updated_at` не продлевает TTL:
повтор сохранения, сопоставление или перерасчёт view не делают статистику новой.
Будущее время наблюдения, неверный период и неподтверждённый контекст исключаются.

1. При наличии свежего API-среза с определимым результатом триггера используется
   API-Football. Это относится и к отрицательному результату: свежий API `4 : 3`
   не заменяется положительным Fonbet `5 : 3` ради отправки.
2. Если API-среза нет, он устарел либо по нему нельзя определить результат
   триггера из-за отсутствующих полей, допускается свежий пригодный срез Fonbet.
   Например, API `4 : NULL` допускает проверку Fonbet; API `5 : NULL`
   уже достаточен для отправки по API.
3. Несопоставленный Fonbet-срез также участвует в проверке; отсутствие fixture_id
   само по себе не является причиной пропустить матч.
4. При неизвестном результате у обоих источников отправки нет. Нельзя взять
   удары одной команды из API, другой из Fonbet или минута/счёт другого снимка.
5. При нескольких подтверждённых событиях Fonbet одного матча выбирается один
   последний пригодный срез по минуте, observed_at и ID события.

Это **правило операционной отправки**, а не изменение приоритета аналитической
view: её существующий контракт «API при наличии» сохраняется. В карточке и
журнале фиксируется причина выбора: API, API отсутствует, устарел или неполон.

Перед отправкой требуется свежий live-контекст: второй тайм, минута 65–75,
матч не завершён. Предлагаемый предел возраста контекста — 120 секунд, чтобы минутный
диспетчер успевал увидеть новый срез между пятиминутными сборами.
Если свежего контекста в БД нет, отправка ждёт следующего сбора, а не считает
последний архивный снимок текущим состоянием. Для этого сборщики должны сохранять
лёгкий live-контекст для кандидатов и ожидающих матчей, включая переход на 76-ю
минуту и завершение, даже когда статистика окна больше не обновляется.
Предлагается отдельная таблица текущего контекста по `(source, source_event_id)`.
Исчезновение события отмечается только после подтверждённого полного обхода;
неполный список не доказывает завершение. На 76-й минуте, после истечения TTL
или при неизвестном актуальном статусе задание не отправляется. Данные остаются
в архиве. Дискретные часы источника и задержки провайдера фиксируются как
ограничение точности; точная секунда реального матча не гарантируется.

## Общая идентичность и дедупликация

В объединении уже есть `api:<fixture_id>` и `fonbet:<event_id>`. Однако после
подтверждения связи ключ может смениться с Fonbet на API; хранить «отправлено»
только по текущему canonical_match_id недостаточно.

Предлагается постоянный `alert_match_id` и таблица уникальных алиасов
`(source, source_event_id) → alert_match_id`. Подтверждение связи связывает
оба внешних ID с одной идентичностью. При объединении двух идентичностей
атомарно переносятся алиасы и факты отправки; наличие успешной отправки
хотя бы у одной блокирует вторую. Ожидающие дубли объединяются, отправитель
повторно разрешает алиасы непосредственно перед доставкой.

Уникальность очереди/успешного оповещения — **на матч**, не на источник,
наблюдение или версию правила. Обновление минуты, счёта, показателя, версии
триггера или подтверждение fixture_id не разрешают повтор. Другие неактивные
категории не начинают отправляться вследствие этой доработки.

До включения импортируется память `live_alerts_sent`: существующий fixture_id
становится алиасом API, исходные alert_id и факты отправки сохраняются.
Ранее отправленный API-матч не должен прийти повторно как Fonbet после
подтверждённого сопоставления. Существующие события Fonbet с одной
подтверждённой связью также дедуплицируются.

**Граница гарантии:** если два источника ещё не удалось сопоставить,
программа не может достоверно знать, что это один реальный матч.
Неоднозначные пары с кандидатами на связь удерживаются от второй отправки
до разрешения связи, фиксируются как `identity_ambiguous`. Fonbet-only
без известного кандидата отправляется самостоятельно. Если связь обнаружится
уже после двух доставок, третьего сообщения не будет, но прежний дубль
автоматически не исчезнет; такой случай отражается в аудите.
Нечёткое сходство названий не используется как доказательство связи.

## Очередь, доставка и сбои

Предлагаемые состояния: `pending`, `sending`, `sent`, `retry`, `expired`,
`uncertain`, `identity_ambiguous`. Точная схема и добавочная миграция
готовятся перед реализацией; миграции 025/026 не переписываются.
Запись очереди не означает успешную отправку. Резервирование ID и создание
задания атомарны; один отправитель владеет заданием через блокировку/lease.
Смена связи синхронизируется с отправкой блокировкой общей идентичности.

Подтверждённый отказ Telegram повторяется с паузой только до истечения
допустимого окна. Потеря соединения до передачи запроса допускает повтор.
Если запрос мог быть принят, но ответ потерян, либо процесс упал между
успехом Telegram и сохранением результата, статус становится `uncertain`:
автоматического слепого повтора нет, нужна проверка факта доставки.
Очередь не полагается на внешний ключ идемпотентности доставки;
гарантировать одновременно отсутствие дублей и доставку при неизвестном исходе
нельзя. Выбран приоритет защиты от повторного сообщения.

Перезапуск восстанавливает очередь, а не пересоздаёт её из истории.
При зависшем sending истёкший lease не является доказательством неотправки.
Старые исторические срезы после запуска сервиса массово не рассылаются.

## Сообщение и совместимость с ботом

В карточке: прежний `alert_id`, команды, лига, минута/счёт наблюдения,
удары в створ каждой команды за второй тайм, сумма при наличии обоих значений,
сработавшее условие, источник, время наблюдения по Москве и ссылка на матч.
У неизвестного значения показывать «нет данных», а не 0. Наличие второго
источника можно указать справочно; его значения не смешиваются с выбранными.

`fixture_id` API и ID Fonbet хранятся отдельно. Для Fonbet-only нужны nullable
fixture_id в контракте оповещения и работа форматирования без API-ID.
Нельзя подставлять event_id Fonbet в поле fixture_id для обхода ограничений.

Для подтверждённого API-матча сохраняются действующие кнопки ТБ и ввод
коэффициента. Для Fonbet-only карточка доставляется и без fixture_id, но
кнопки, создающие открытую ставку, не показываются: действующая схема bets
не допускает открытых ставок без ID. Это ограничение явно обозначается
в карточке. Расширение реестра для таких открытых ставок — отдельная задача;
доставка уведомления от него не зависит.

## Внедрение и наблюдаемость

1. Добавить контракт текущего live-контекста, постоянной идентичности,
   алиасов и очереди; расширить данные оповещения без фиктивного API-ID.
2. Перенести вычисление активного триггера в общую функцию без сетевого I/O;
   нормализовать shots_on_goal API и shots_on_target_2h Fonbet.
3. Подключить диспетчер к свежим данным и сопоставлениям, перенести старую
   память отправленного. Сборщики продолжают сохранять снимки независимо.
4. Проверить dry-run и сценарии приёмки. Не очищать память успешных отправок.
5. При переключении отключить прямую отправку из старого API-процесса,
   сохранив API-сбор. Только один механизм может реально отправлять карточки.
   Установить минутный диспетчер и проверить первый цикл каждого источника.
6. При откате остановить новый отправитель; возвращать старую отправку только
   после синхронизации новых успешных API-отправок в её память. Для Fonbet-only
   старый процесс не получает фиктивных ID. Очередь и архив не удалять.

В отчёте: свежих строк по источникам, выбранных источников и причин выбора,
срабатываний, неизвестных данных, старых/вне окна, отфильтрованных форматов,
already_sent, identity_ambiguous, pending/sent/retry/expired/uncertain,
задержка observed_at→sent_at и ошибки. Токены, .env, cookies, пароли и приватные
ключи не читаются для диагностики и не попадают в логи. Транспорт и адресат
Telegram остаются существующими; внешних публичных сервисов не добавляется.

## Критерии приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Свежий API `4:4`, свежий Fonbet-only `5:0` | по одной карточке каждому матчу |
| `4:3`, `4:NULL`, `5:NULL`, `NULL:NULL` | false, unknown, true, unknown соответственно |
| Ничья, минуты 65 и 75 | не исключают подходящий сигнал |
| 64, 76, HT, FT, ET, FC/футзал/2X40 | не отправляются |
| API и Fonbet подтверждены как один матч | одна карточка, API при пригодных свежих данных |
| API старый/неполный, Fonbet свежий пригодный | Fonbet по операционному правилу; аналитическая view не меняется |
| API свежий отрицательный, Fonbet положительный | отправки нет; не выбирается источник ради сигнала |
| Обновление только Fonbet, перезапуск диспетчера | подходящий матч обнаруживается без нового API-запроса |
| Fonbet отправлен, позднее появился fixture_id | повторного сообщения нет |
| Несколько Fonbet event_id одной подтверждённой пары | одно оповещение |
| Два диспетчера/отправителя и одновременное сопоставление | одна резервация и одна подтверждённая доставка |
| Память старого API-процесса перенесена | ранее отправленный матч не приходит повторно |
| Архивная минута 75, свежесть истекла или текущая минута 76 | нет запоздалой отправки |
| Потерян ответ Telegram после возможной доставки | uncertain, слепого повтора нет |
| Fonbet-only без API-ID | сообщение есть; нет некорректных кнопок записи открытой ставки |
| Неоднозначное сопоставление и неполный сбор | не выдаются за подтверждённую идентичность/свежее завершение |

Согласованы: проверка БД каждую минуту, TTL среза и live-контекста 120 секунд,
приоритет пригодного свежего API с переходом на Fonbet при отсутствии, устаревании
или неопределимом результате API, общая идентичность и очередь отправки.
Перед выкладкой проверить задержки обоих сборщиков и подготовить добавочную
миграцию. Изменение порогов триггера этим документом не предусматривается.

## Реализация и переключение 10.11.2026

Код: `src/jobs/alert_dispatch.py`, `alert_rules.py`, `live_context.py`;
сборщики API/Fonbet сохраняют текущий контекст независимо от окна статистики.
Миграция 027 добавляет очередь/идентичности/алиасы и общий переключатель.
На production выполнены backup схемы и предыдущих файлов, dry-run, импорт
прежних отправленных матчей; enabled=true включает единую отправку и подавляет
прямую API-отправку после сохранения срезов. Таймер football-alert-dispatch
работает каждую минуту с AccuracySec=1s, без догоняющего запуска.
Первый запуск 10:48:39 МСК: Result=success, ExecMainStatus=0.

Проверено 199 целевых сценариев pytest (включая 42 проверки диспетчера) и 8 браузерных тестов. В расширенной
регрессии два прежних расхождения тестов неактивной favorite воспроизводятся
без новой логики и не изменяют активный half_pressure. Переключение и откат
описаны в [README эксплуатации](../deploy/README-unified-alerts.md).


## Уточнение 12.11.2026: голы входят в нормализованные удары

По поручению владельца для Fonbet исходные удары в створ второго тайма
дополняются голами именно второго тайма к моменту снимка. Сырые значения
не меняются; аналитика и уведомления используют нормализованный результат.
Неизвестный счёт к перерыву не считается нулевым. Контракт и проверки:
[нормализация-ударов-fonbet.md](нормализация-ударов-fonbet.md).

## Одно напоминание для новых сигналов

После включения `live_signal_config.reminders_enabled` исходное подтверждённое сообщение получает не более одного напоминания. Следующий успешный опрос должен начаться после подтверждения отправки и предоставить свежий контекст матча (не старше 120 секунд); повторное чтение старого результата не подходит. Статистика и критерии half_pressure повторно не проверяются. Ошибка/отсутствие контекста оставляет ожидание до следующего успешного опроса, в том числе на 80-й минуте или 90+12. Исходное окно статистики остаётся 65–75 минут.

Завершение основного времени, переход в ET/серию пенальти или отмена матча отменяет напоминание. Исчезновение из live не считается завершением. Сообщение явно названо напоминанием и содержит номера исходного сигнала и первого сообщения; новые кнопки независимой ставки не создаются. Потеря ответа Telegram и восстановление незавершённого sending переводят доставку в uncertain без слепого повтора.

Подтверждённый merge API/Fonbet сохраняет самое раннее первое сообщение и отменяет лишние ожидающие напоминания. Уже отправленное либо uncertain напоминание исключает новое по объединённому матчу. История прежних доставок сохраняется. Новые таблицы и флаги пока не активированы в production; миграции 030–032 и новая версия standalone Fonbet `store.py`/`match_clock.py` должны выпускаться согласованно.

Проверки: `tests/test_signal_context.py`, `tests/test_signal_reminders.py`; примеры включают 90+12, ET/FT, 80-ю минуту без статистики, retry, uncertain, рестарт, competing lock и поздний merge.

### Исправление очереди после review

Готовность напоминания проверяется по всем алиасам до LIMIT: waiting без свежего контекста и противоречивые контексты не занимают слот готовой отправки. Терминальные состояния отменяются отдельным SQL-проходом. Очередь готовых сообщений упорядочена по next_attempt_at, затем времени первого сигнала и ID.

Initial dispatcher и reminders используют единый monotonic deadline: 85 секунд от начала службы при её таймауте 90 секунд. До каждого внешнего вызова резервируется 30 секунд (25 на Telegram, 5 на фиксацию/завершение). При нехватке времени запрос и sending lease не создаются; сообщение остаётся в очереди. Критерии первого сигнала, окно 65–75 и uncertain-политика не менялись.
