# Live-статистика матчей на 65–75-й минуте

Основание — поручение владельца 09.11.2026 и уточнение требований в том же чате.
Статус — согласована владельцем 09.11.2026, выложена на production 09.11.2026 в 17:17 МСК.

Связанные документы — `надёжность-сбора.md`, `онлайн-оповещения.md`,
`разведочный-анализ-поздних-голов.md`, `docs/03-модель-данных.md`.

Дополнительный сбор с сайта Fonbet описан отдельно в
[лайв-статистика-fonbet.md](лайв-статистика-fonbet.md). Он хранит собственные
наблюдения и не подменяет снимки API-Football в этой спецификации.

## Цель

Накопить таблицу для анализа состояния матчей максимально близко к 75-й минуте.
Один матч занимает одну строку со счётом и статистикой обеих команд. По мере
получения более близких к 75-й минуте данных строка обновляется.

## Требования владельца

1. Опрос подробной статистики выполняется для всех видимых в live матчей
   со статусом `2H` и минутой от 65 до 75 включительно.
2. Статистика запрашивается независимо от лиги, `is_tracked`, счёта,
   владения, ударов, результатов модели и наличия отправленного оповещения.
3. Непустая статистика сохраняется. Повторный подходящий ответ обновляет
   существующую строку матча по правилам близости к 75-й минуте.
4. `fixture_id` совпадает с ID API-Football, используемым в `fixtures.fixture_id`.
   Этот ID является первичным ключом новой таблицы и ключом сопоставления.
5. Пустой ответ сохраняет прежние пригодные данные. Когда непустых ответов
   по матчу ещё не было, строка статистики отсутствует.

## Частота и последовательность запроса

Используется текущая частота live-процесса — каждые 5 минут.

1. Получить `/fixtures?live=all` и выбрать все матчи в окне 65–75 включительно.
2. Для каждого выбранного матча получить накопительную статистику за матч
   и доступную статистику таймов через
   `/fixtures/statistics?fixture=<fixture_id>&half=true`.
3. Переиспользовать подходящий непустой ответ, уже полученный для этого матча
   в текущем запуске. Повторный сетевой запрос того же набора в запуске не нужен.
4. Сохранить или обновить строку, затем применить правила оповещений.
   Запись статистики выполняется также в `--dry-run`.
5. При следующем запуске снова запросить статистику всех подходящих матчей,
   включая матчи с уже сохранённой строкой и отправленным `half_pressure`.
6. После выхода матча из окна сохранённая строка остаётся доступна для анализа.
   На 76-й минуте и позже эта задача прекращает запросы и обновления по матчу.

Все дополнительные запросы учитываются в бюджете live-процесса. Перед выкладкой
оценить максимальное число подходящих матчей за запуск относительно действующего
лимита. Если бюджета не хватает на все матчи, зафиксировать пропуски и причину
в журнале, а необходимую корректировку лимита представить владельцу до включения.
Повторный обход пропущенных матчей допускается только пока они находятся в окне.

## Что считать непустой статистикой

Ответ успешен, не содержит ошибок API и содержит хотя бы одно числовое значение
из поддерживаемых показателей статистики одной из команд данного матча.
Числовой ноль считается значением. Пустой `response`, только имена команд,
пустые массивы показателей и показатели исключительно с NULL считаются пустотой.

Частичная статистика сохраняется с `quality_status=partial`. Отсутствующие
показатели и блоки второй команды остаются NULL. Если показатели доступны для
обеих команд, используется `quality_status=both_teams`. Этот статус описывает
наличие статистики обеих команд, полнота отдельных полей оценивается отдельно.

Полученные данные должны относиться к указанному fixture_id и командам из
контекста матча. Чужой ID команды, ошибочный формат, отсутствующие fixture_id
или минута, а также неизвестная принадлежность показателей фиксируются как
ошибка проверки. Такой ответ не заменяет сохранённые данные.

## Правила перезаписи одной строки

Операция выполняется атомарным upsert по `fixture_id`.

- Первая непустая статистика в диапазоне 65–75 создаёт строку.
- Новая непустая статистика с большей минутой заменяет строку.
- При одинаковой минуте более поздний ответ по `observed_at` заменяет строку.
  При равном времени используется observation_id как детерминированный порядок.
- Более ранняя минута не заменяет более позднюю, даже если ответ пришёл позже.
- Пустой ответ или ошибка API не изменяет существующую строку.
- Новая строка содержит единый полученный набор данных. При перезаписи
  отсутствующие поля нового ответа остаются NULL. Показатели из прежних минут
  не дополняют новый снимок. Пригодный частичный ответ на 75-й минуте заменяет
  полную статистику на 74-й с отметкой `partial`.
- После сохранения 75-й минуты возможны уточнения той же минуты по времени
  получения. Данные других минут не вытесняют снимок на 75-й.
- Два конкурентных обработчика применяют эти правила непосредственно в БД.
  В результате всегда остаётся одна строка с максимальным порядком
  `(elapsed, observed_at, observation_id)` среди подходящих непустых ответов.

| Ответы по порядку получения | Результат в таблице |
|---|---|
| 65, 70, 74 — все непустые | Одна строка на 74-й минуте |
| 70 и 75 — непустые | Одна строка на 75-й минуте |
| 70 непустой, 75 пустой | Остаётся строка на 70-й минуте |
| 74 непустой, затем задержавшийся 71 непустой | Остаётся строка на 74-й минуте |
| Два непустых ответа на 75-й минуте | Одна строка с более поздним ответом |
| 65–75 — все ответы пустые | Строка статистики отсутствует |
| 75 частичный непустой после 74 полного | Одна строка на 75-й с quality_status=partial |

## Таблица данных

Согласованное имя — `live_match_statistics_75`. Точная схема утверждается
перед реализацией отдельной добавочной миграцией.

| Поле | Назначение |
|---|---|
| fixture_id | PRIMARY KEY, исходный ID API-Football, тот же ID, что в fixtures |
| league_id, season, kickoff_at | Турнир, сезон и начало матча |
| home_team_id, away_team_id | Идентификаторы команд для сопоставления |
| status_short, elapsed, elapsed_extra | Статус и минута выбранного состояния |
| goals_home, goals_away | Счёт на момент выбранного контекста |
| statistics | JSONB с именованными блоками home/away и match/1h/2h в этой же строке |
| requested_at, observed_at | Начало и окончание запроса выбранной статистики, UTC |
| context_observed_at | Время получения минуты и счёта |
| observation_id, context_observation_id, run_id | Ссылки на исходные ответы API и запуск |
| minute_basis | same_response или context |
| quality_status | both_teams или partial |
| updated_at | Время последнего обновления строки в БД, UTC |

Блок `statistics` содержит доступные показатели провайдера для обеих команд
за матч и за каждый тайм. Включаются удары в створ, мимо и всего, блокированные
удары, владение, передачи и точность передач, угловые, нарушения, офсайды,
карточки, сейвы, xG и goals_prevented. Значения нормализуются действующим
парсером. Отсутствующие периоды и показатели обозначаются NULL. Вычисленные
оценки второго тайма в эти поля не подставляются.

Отдельных строк на команду, тайм или минуту в этой таблице нет.
Пример сопоставления с основным хранилищем

```sql
SELECT f.fixture_id, f.match_date, s.elapsed, s.goals_home, s.goals_away, s.statistics
FROM fixtures f
JOIN live_match_statistics_75 s ON s.fixture_id = f.fixture_id;
```

Если live-матч ещё отсутствует в `fixtures`, его статистика сохраняется под
исходным fixture_id. Обязательная внешняя ссылка на существующую строку fixtures
не должна препятствовать сбору. После появления матча в основной таблице
обычный JOIN связывает данные без переназначения ID.

## Согласованность минуты и статистики

Если статистика, счёт и минута получены одним ответом, `minute_basis=same_response`.
Для отдельного `/fixtures/statistics` используются минута и счёт из live-контекста,
`minute_basis=context`. Они отражают время контекста, собственная минута
статистики из такого endpoint может быть неизвестна.

Предлагаемый предел от получения контекста до окончания запроса статистики —
30 секунд. При более долгом ожидании контекст считается устаревшим, снимок
не обновляется, причина фиксируется в журнале. Это ограничивает расхождение
между минутой отбора и временем получения данных при последовательном опросе.
Параметр 30 секунд согласован вместе со спецификацией.

Опрос с шагом 5 минут сохраняет последний фактически полученный непустой ответ
в диапазоне. Точная 75-я минута зависит от доступности и минутных отметок API.

## Архив, хранение и ошибки

Существующий `api_observations` продолжает хранить сырые ответы по своему
контракту. Новая аналитическая таблица содержит ровно одну актуальную строку
на матч и использует архив для происхождения данных. Новая отдельная история
нормализованных снимков не создаётся.

Строки хранятся долговременно, включаются в резервное копирование и остаются
после завершения матча. Очистка временных снимков перерыва и файлового кэша
не удаляет эти строки. Итоговая статистика и финальный счёт матча не обновляют
сохранённое состояние 65–75-й минуты.

Журнал различает пустой ответ, ошибку API, неверный контекст и пропуск по бюджету.
Повторная запись одного ответа идемпотентна. Сбой отправки Telegram не отменяет
запись статистики. Ошибка БД отражается в результате запуска, исходный ответ
позволяет повторить запись с сохранением фактической минуты и времён.
В таблице и логах отсутствуют API-ключи, токены и строки подключения.

При последующем анализе используются фактическая минута и разница `75-elapsed`.
Строка является последним доступным состоянием матча в этом окне. Для анализа
более раннего момента при необходимости используются соответствующие исходные
наблюдения архива с условием `observed_at <= decision_at`.

## Критерии приёмки

1. На каждом опросе все матчи со статусом 2H и минутой 65–75 отбираются для
   получения статистики, в том числе матчи с прежним сигналом и вне is_tracked.
2. Минуты 64 и 76 исключаются. Минуты 65 и 75 включаются. Статусы HT, ET и FT
   исключаются, отсутствующая минута считается ошибкой контекста.
3. Непустой ответ создаёт одну строку, последующие подходящие ответы её обновляют.
   Проверены все примеры из таблицы правил перезаписи.
4. Нули сохраняются. Пустота и API-ошибка сохраняют прежнюю строку. Для матча
   исключительно с пустыми ответами строка отсутствует.
5. Проверены частичные ответы, отсутствие таймов и одна команда. При обновлении
   показатели разных минут не смешиваются.
6. Повтор запуска, задержавшийся ответ и конкурентные записи сохраняют
   уникальность fixture_id и ближайшую к 75-й минуте статистику.
7. fixture_id совпадает с API и fixtures. Проверены JOIN с основной таблицей
   и сохранение статистики до появления матча в fixtures.
8. Проверены устаревший контекст, сбой БД, выключенные категории, dry-run,
   исчерпанный бюджет и ошибка Telegram.
9. По журналу видны количество выбранных матчей, запросов, непустых ответов,
   вставок, обновлений, пустых ответов и пропусков по каждой причине.
10. Проверено переиспользование ответа текущего запуска, отсутствие дублирующих
    запросов и соблюдение согласованного бюджета.

до проверки сигналов в run_live_alerts. ApiClient возвращает метаданные свежего
ответа для связывания строки с архивом. Окно half_pressure/half_shots — 65–75.
Логи включают selected, requests, nonempty, inserted, updated, empty,
older_or_duplicate, context_stale, api_error, invalid_context, budget_exceeded.
