# Спецификация: статистика матча по таймам

Основание: запрос владельца (12.10.2026, для отдельного исследования). Опирается
на `specs/ежедневный-сбор.md` (шаг «статистика»), `specs/дозагрузка-пропущенного.md`
(раунды дозагрузки, `fixture_fetch_state`), `docs/03-модель-данных.md`
(`fixture_statistics`, ADR-4), `docs/02-архитектура.md` (ADR-2, ADR-5).

Статус: **утверждена 12.10.2026**. Решения владельца: приоритет — вариант Б
(сначала новые матчи, события и составы дозагрузки на паузе, пока идёт добор
таймов); таймы нужны за **все годы 2018–2026**; отдельная колонка голов не нужна
(голы по таймам — из `fixtures.ht_*` и событий); отдельная таблица вместо новых
колонок в `fixture_statistics` принята.

## Цель

Хранить статистику матча отдельно по первому и второму тайму для каждой команды:
владение мячом, удары, фолы, угловые, передачи, карточки и остальные показатели,
которые мы уже собираем за весь матч. Сейчас в базе только итог за матч.

## Что подтверждено проверкой (12.10.2026)

Два живых запроса `GET /fixtures/statistics?fixture=…&half=true` (матчи
1100293 Эквадор–Венесуэла и 1557422 Халл–Эвертон, АПЛ), по одному запросу на матч:

- в элементе ответа для команды помимо `statistics` появляются `statistics_1h`
  и `statistics_2h`;
- в каждом из трёх блоков одинаковый набор из **18 типов**: `Shots on Goal`,
  `Shots off Goal`, `Total Shots`, `Blocked Shots`, `Shots insidebox`,
  `Shots outsidebox`, `Fouls`, `Corner Kicks`, `Offsides`, `Ball Possession`,
  `Yellow Cards`, `Red Cards`, `Goalkeeper Saves`, `Total passes`,
  `Passes accurate`, `Passes %`, `expected_goals`, `goals_prevented`;
- итоговый блок `statistics` с `half=true` совпадает с ответом без параметра
  (71 % / 570 передач), то есть запрос с `half=true` заменяет прежний без потерь;
- владение по таймам не складывается в итог (Эквадор: 81 % и 58 % при 71 % за матч),
  поэтому второй тайм **нельзя вычислить** как «итог минус первый» — он хранится
  как пришёл;
- разбивки по минутам или периодам короче тайма нет.

Не проверено: для каких лиг блоки `statistics_1h/2h` приходят пустыми. Проверка
входит в приёмку (АП-5).

Что вне статистики: **голы по таймам** в этом эндпоинте отсутствуют. Они уже есть
в базе другим путём: `fixtures.ht_home/ht_away` (голы к перерыву) и
`fixture_events` (голы с минутой). Второй тайм = `COALESCE(ft90_*, goals_*)` минус
`ht_*`. Отдельное хранение не требуется (ADR-4: производное не хранится). Девять
колонок `fixture_statistics`, которые API-Football в статистике не отдаёт
(`substitutions`, `free_kicks`, `assists`, `counter_attacks`, `cross_attacks`,
`goals`, `goal_attempts`, `throwins`, `medical_treatment`), в разбивку не попадают.

## Пользовательские сценарии

1. Исследователь выбирает владение мячом команды в первом и втором тайме матча
   и сравнивает их.
2. Исследователь считает по лиге и сезону, как меняются удары, фолы и угловые от
   первого тайма ко второму.
3. Новые матчи получают разбивку автоматически, без отдельных действий.
4. Старые матчи со статистикой получают разбивку по мере дозагрузки.

## Функциональные требования

| № | Требование |
|---|---|
| ПТ-1 | Статистика по таймам хранится в отдельной таблице `fixture_statistics_halves`, ключ `(fixture_id, team_id, half)`, `half` = 1 или 2. |
| ПТ-2 | Набор полей совпадает с 18 показателями, которые API отдаёт по таймам; имена колонок и преобразования те же, что в `fixture_statistics` (`ball_possession`, `passes_pct` — проценты в число; `expected_goals`, `goals_prevented` — `NUMERIC(5,2)`). |
| ПТ-3 | Шаг «статистика» (ежедневный и дозагрузка) запрашивает `/fixtures/statistics` с `half=true` и из одного ответа пишет итог в `fixture_statistics` и таймы в `fixture_statistics_halves`. Число запросов на матч не растёт. |
| ПТ-4 | Матчи, у которых статистика уже есть, а таймов нет, добираются отдельным набором дозагрузки (ПТ-8), с отметкой в `fixture_fetch_state`. |
| ПТ-5 | Повторная запись безопасна: `ON CONFLICT … DO UPDATE` по ключу таблицы, дубли невозможны (ФТ-3). |
| ПТ-6 | Пустой или отсутствующий блок `statistics_1h/2h` — не ошибка: строки не пишутся, матч считается обработанным по таймам; счётчик попыток не растёт. |
| ПТ-7 | Существующая таблица `fixture_statistics` и её читатели (`build_features`, запросы владельца) не меняются. |
| ПТ-8 | Дозагрузка таймов идёт от новых матчей к старым, бюджет и приоритет задаются владельцем (открытый вопрос 1); свежие матчи по-прежнему обрабатываются первыми. |

## Бизнес-правила

- Значения хранятся как отдал источник; производные (второй тайм минус первый,
  доли, разницы) считает запрос, не схема (ADR-4).
- Строка тайма, в которой все 18 значений пустые, не пишется.
- Сопоставление тайма: `statistics_1h` → `half = 1`, `statistics_2h` → `half = 2`.
  Дополнительное время и серия пенальти в разбивку не входят: у матчей `AET`/`PEN`
  таймы относятся к основному времени.
- Кэш сырых ответов (ADR-2): ключ запроса меняется (добавляется `half`), поэтому
  прежние файлы кэша без таймов для разбора таймов непригодны.

## Данные

### Новая таблица `fixture_statistics_halves`

| Поле | Тип | Обяз. | Ограничения |
|---|---|---:|---|
| fixture_id | INTEGER | да | PK, FK → fixtures |
| team_id | INTEGER | да | PK, FK → teams |
| half | SMALLINT | да | PK, `CHECK (half IN (1, 2))` |
| shots_on_goal, shots_off_goal, total_shots, blocked_shots, shots_insidebox, shots_outsidebox, fouls, corner_kicks, offsides, yellow_cards, red_cards, goalkeeper_saves, total_passes, passes_accurate | SMALLINT | нет |  |
| ball_possession, passes_pct | SMALLINT | нет | проценты |
| expected_goals, goals_prevented | NUMERIC(5,2) | нет |  |
| fetched_at | TIMESTAMPTZ | да | время записи |

Индекс: `(team_id)`. Оценка объёма: ~143 тыс. матчей × 2 команды × 2 тайма ≈ 572 тыс.
строк, порядка 60–70 МБ (сейчас `fixture_statistics` занимает 34 МБ).

### Изменение `fixture_fetch_state`

Добавляются `halves_fetched_at TIMESTAMPTZ` и `halves_attempts SMALLINT NOT NULL
DEFAULT 0`. Контракт тот же, что у остальных наборов: максимум `MAX_ATTEMPTS = 3`
попыток; успешный разбор с `half=true` проставляет `halves_fetched_at` вместе с
`statistics_fetched_at`.

### Миграция

Одна миграция (следующий номер после текущей) с парным `.down.sql`: создание
таблицы и две колонки в `fixture_fetch_state`. Оценка: аддитивная, обратно
совместимая; блокировок нет (новая таблица; `ADD COLUMN` с константным
значением по умолчанию в PostgreSQL 17 не переписывает таблицу). Откат удаляет
таблицу и колонки вместе с накопленными таймами — только по явному решению
владельца.

## Объём работы по запросам API

Матчей со статистикой в базе: **142 974** (по годам: 2018 — 7 984, 2019 — 13 126,
2020 — 12 408, 2021 — 17 759, 2022 — 16 462, 2023 — 20 038, 2024 — 19 744,
2025 — 20 124, 2026 — 15 329). Добор таймов у них — по запросу на матч, то есть
**до 142 974 запросов**, из них с 2024 года — около 55 200.

Матчи, по которым статистику ещё предстоит собрать впервые (очередь дозагрузки и
глубокой истории), сразу берутся с `half=true` и дополнительных запросов не стоят.

**Уточнение 22.10.2026.** Тариф вырос до 75 000 запросов в сутки, остаток для
дозагрузки может быть порядка 60 000. Очередь таймов (98 083 на 22.10) тогда закрывается
за 1,5–2 суток, а разница между вариантами А, Б и В стирается; порядок «от новых к
старым, таймы первыми» (вариант Б) сохраняется (`docs/06`, этап 12).

При остатке лимита около 5 500 запросов в сутки (и текущей очереди дозагрузки
~175 тыс. запросов) это означает:

| Вариант приоритета | Срок добора таймов | Влияние на дозагрузку событий и составов |
|---|---|---|
| А. Четвёртый набор с равной долей (по ¼ остатка) | порядка 100 суток | события/составы замедляются на ¼ |
| Б. Сначала таймы с 2024 года (~55 тыс.), затем остальное | ~10 суток на 2024+, ~26 суток всего | события/составы стоят на паузе на это время |
| В. Все таймы разом перед событиями и составами | ~26 суток | события/составы сдвигаются на те же ~26 суток |

Рекомендация: вариант Б. Чем новее матч, тем он полезнее для исследования и
выше шанс, что источник отдаёт таймы; решение по остальным годам можно принять
после оценки покрытия (АП-5).

## Интерфейсы

- Шаг `statistics` в ежедневном сборе и в дозагрузке: меняется запрос и разбор
  (`_process_statistics`), новый вызов `ApiClient.get("/fixtures/statistics",
  {"fixture": id, "half": "true"})`.
- Новый набор дозагрузки таймов в `run_backfill`/`backfill-report`: одна строка
  очереди «статистика по таймам».
- CLI: `--job statistics` и `--job backfill` продолжают работать без новых флагов;
  отчёт `backfill-report` получает четвёртый столбец.
- Читателям данных: таблица доступна запросами SQL; в `ml_match_features` ничего
  не добавляется (решение об использовании признаков по таймам — за чатами
  «Обработка данных» и «Модели»).

## Ошибки и крайние случаи

| Ситуация | Поведение |
|---|---|
| Ответ без `statistics_1h/2h` (лига не отдаёт таймы) | итог пишется, таймы нет; `halves_fetched_at` проставляется, попытки не растут |
| Пустой или `[]` ответ целиком | как сейчас: `mark_attempt`, до 3 попыток |
| В блоке пришли не все 18 типов | пишутся имеющиеся, остальные `NULL` |
| Незнакомый тип показателя | игнорируется (как сейчас) |
| Процент пришёл не строкой `"58%"` | `to_percent` обрабатывает оба вида, нераспознанное → `NULL` |
| Исчерпан суточный лимит | шаг останавливается штатно, незавершённый матч остаётся в очереди |
| Миграция не применена, а код выкачен | запись таймов падает; порядок выкатки: сначала миграция, потом код |

## Безопасность

Новых секретов, прав и внешних интерфейсов нет. Ключ API по-прежнему только в
`.env` сервера. Данные таймов — публичная спортивная статистика.

## Критерии приёмки

| № | Критерий |
|---|---|
| АП-1 | Миграция применяется и откатывается на копии БД; `fixture_statistics` не затронута |
| АП-2 | Для свежего матча один запрос даёт и итог, и 2×N строк таймов; `requests_used` на матч равен 1 |
| АП-3 | Итог из ответа с `half=true` сверен с `fixture_statistics` на выборке не менее 200 матчей; расхождения объяснимы поправками источника (см. результаты пробной партии) |
| АП-4 | Повторный запуск шага не создаёт дублей и не меняет число строк |
| АП-5 | Измерено покрытие: доля матчей выборки по лигам и годам, у которых таймы пришли; результат записан в `docs/03` |
| АП-6 | Матч без блоков таймов обрабатывается без ошибки и без роста `halves_attempts` |
| АП-7 | `backfill-report` показывает очередь таймов; общий расход за сутки не превышает 7 500 запросов с учётом 300 на международные турниры |
| АП-8 | Существующие тесты проходят; новые тесты из раздела ниже проходят |

## Тестовые сценарии

Основной: ответ с тремя блоками → итог и 4 строки таймов (2 команды × 2 тайма),
значения совпадают с эталоном. Ошибки: HTTP-ошибка, `errors` в теле, пустой
`response` — попытка засчитывается. Граничные: пустой `statistics_2h`, блок с
частью типов, `null` в значениях, проценты строкой и числом, матч `AET`/`PEN`.
Некорректный ввод: незнакомый тип показателя, `half` вне 1..2 (ограничение
`CHECK`). Идемпотентность: двойная запись, обновление значения. Очередь
дозагрузки: матч с итогом без таймов попадает в набор «таймы»; после успеха —
выпадает; после 3 неудач — не выбирается. Бюджет: набор «таймы» не выходит за
свою долю раунда. Совместимость: читатели `fixture_statistics` дают прежний
результат. Прав доступа в системе нет — проверка неприменима.

## Принятые решения

| Вопрос | Решение | Дата |
|---|---|---|
| Приоритет добора таймов для старых матчей | вариант Б: от новых к старым, события и составы дозагрузки на паузе до закрытия очереди таймов | 2026-10-12 |
| Годы | все: 2018–2026 (~143 тыс. запросов, около 26 суток остатка лимита) | 2026-10-12 |
| Голы по таймам | из `fixtures.ht_*` и `fixture_events`, отдельно не хранить | 2026-10-12 |
| Структура хранения | отдельная таблица `fixture_statistics_halves` | 2026-10-12 |
| Влияние тарифа Ultra | срок добора таймов сокращается с ~26 суток до 1,5–2 суток; порядок не меняется | 2026-10-22 |

## Результаты пробной партии на проде (12.10.2026)

Первые 200 запросов добора таймов (матчи сезона 2026, самые новые) сверены с
базой по данным из кэша ответов:

- блоки таймов пришли у **200 из 200** матчей; покрытие более старых лет будет
  измеряться по мере продвижения очереди от новых матчей к старым (АП-5);
- сумма таймов равна итогу за матч у **4 999 из 5 014** аддитивных показателей
  (99,7 %); остальные 15 — расхождения самого источника (например, 269 + 254 при
  итоге 524);
- итог в ответе отличается от записанного ранее в `fixture_statistics` у 32 из 400
  строк команд (8 %): чаще на 1–2, редко до 23. Источник уточняет статистику
  уже после матча, поэтому АП-3 в исходной редакции («совпадает») выполнить
  нельзя; принято: расхождения — поправки источника, а не ошибка разбора;
- итог для старых матчей **не перезаписывается** (ПТ-7). Следствие: у старых
  матчей сумма таймов может отличаться от записанного итога на те же поправки.
  Если нужны согласованные итоги, есть вариант обновлять их при добире таймов,
  решение за владельцем.
