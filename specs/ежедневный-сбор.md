# Спецификация: ежедневный сбор

Основание: ФТ-2 … ФТ-7, ФТ-9, ФТ-10 в `docs/01-требования.md`; порядок шагов
и ADR — в `docs/02-архитектура.md`; схема — в `docs/03-модель-данных.md`;
клиент API — `src/api/client.py` (этап 3).

## Цель

Каждый шаг из `docs/02` (каталог лиг, матчи, травмы, коэффициенты, события,
статистика, составы) реализован отдельной функцией сбора, которая:
запрашивает API через `ApiClient`, разбирает ответы в строки таблиц
(стадия 2, ADR-2) и пишет их в базу с защитой от дублей. Каждый запуск
фиксируется в `collection_runs` (ФТ-6).

## Границы

**Входит:** шаги 1–7 из таблицы в `docs/02-архитектура.md` — сбор свежих
и предстоящих данных.

**Не входит:** шаг 8, дозагрузка пропущенного периода (ФТ-11) — отдельная
спецификация `specs/дозагрузка-пропущенного.md`, этап 4б плана. Обе
спецификации используют один и тот же контракт «fixture_fetch_state»
(раздел «Состояние сбора» ниже), поэтому дозагрузка добавляется без
переделки этой части.

**Не входит:** запуск по расписанию на сервере (cron) — этап 5 плана;
особенности часового пояса cron — `docs/04`, «Расхождения», пункт 1а.

## Общий контракт шага

Каждый шаг — отдельная функция в `src/jobs/collect.py` с одинаковой формой:

```python
def run(client: ApiClient, conn, budget: int | None = None) -> RunResult
```

`RunResult` — то, что попадает в `collection_runs`: число обработанных
элементов и число потраченных запросов. Бюджет, если задан, ограничивает
шаг сверху; не заданный бюджет — значит «сколько нужно, но не больше
общего дневного лимита клиента» (лимит уже встроен в `ApiClient`).

Перед первым запросом шаг открывает строку в `collection_runs` со статусом
`running`, по завершении — закрывает её `success`, `failed` или
`quota_exceeded` (ФТ-6). Строка закрывается в любом случае, включая
необработанное исключение (`try/finally`).

## Шаг 1. Каталог лиг и покрытие

**Источник:** `/leagues`, без параметров — отдаёт все ~1 239 лиг постранично
(до 6 запросов, `ApiClient.paged`).

**Частота:** раз в неделю. Данные меняются редко; чаще — трата лимита
впустую.

**Запись:**
- `leagues`: `league_id` ← `league.id`, `name`, `type`, `country` ←
  `country.name`, `country_code` ← `country.code`. `legacy_code` не
  трогается — он проставляется только переносом (ПР-1).
- `league_seasons`: по каждому элементу `seasons[]` — `season` ← `year`,
  `start_date`, `end_date`, `has_events` ← `coverage.fixtures.events`,
  `has_statistics` ← `coverage.fixtures.statistics_fixtures`, `has_lineups`
  ← `coverage.fixtures.lineups`, `has_injuries` ← `coverage.injuries`,
  `has_odds` ← `coverage.odds`.

Ключ конфликта — `league_id` и `(league_id, season)` соответственно,
`ON CONFLICT DO UPDATE`: покрытие могло измениться.

**Почему это первый шаг.** Шаги 2–7 читают `has_events`/`has_statistics`/
`has_lineups`/`has_odds` из `league_seasons`, чтобы не слать запросы туда,
где источник всё равно ничего не вернёт (ФТ-5). Без свежего шага 1 остальные
шаги работают на данных недельной давности — это допустимо, покрытие
меняется редко.

## Шаг 2. Матчи по лигам и сезонам

**Источник:** `/fixtures?league=…&season=…`, один запрос на пару
лига-сезон.

**Отбор пар:** только лиги с `is_tracked` (ФТ-9) и только **активные сезоны**:
от 30 дней до `start_date` до 7 дней после `end_date`. Сезон без дат
(каталог ещё не загружен) считается активным. Завершившийся сезон не
запрашивается: его результаты не меняются, а ежедневный запрос стоил бы
сотни запросов впустую (ФТ-5). Так на 24.09.2026 отбирается 477 пар вместо
1 855.

**Частота:** ежедневно, по всем отобранным парам (не только изменившимся:
расписание сдвигается, статусы меняются).

**Кэш не используется** (`use_cache=False`): при одинаковых параметрах
запроса статус и счёт меняются день ото дня.

**Запись:** `teams` (upsert по `home`/`away` из ответа), `fixtures` — все
поля из `docs/03`, включая те, что при переносе были пустыми (`round`,
`status_long`, `elapsed`, `ht_home`, `ht_away`, `venue_name`, `venue_city`).
Ключ конфликта — `fixture_id`.

**Особый случай.** Матч, ранее записанный со статусом `NS`, может прийти
с `FT` и итоговым счётом — это ожидаемое обновление, а не ошибка (ФТ-3).

## Шаг 3. Травмы

**Источник:** `/injuries?league=…&season=…`, один запрос на пару
лига-сезон. Отбор — как в шаге 2 (отслеживаемые лиги, активные сезоны)
плюс `league_seasons.has_injuries = true`. Кэш не используется.

**Частота:** ежедневно.

**Запись:** `players` (upsert), `injuries` по ключу `(fixture_id,
player_id)`. Строка без `fixture_id` в ответе (травма не привязана к
конкретному матчу) пропускается — таблица требует `fixture_id NOT NULL`
(`docs/03`); такие случаи считаются и попадают в отчёт запуска.

## Шаг 4. Коэффициенты

**Источник:** `/odds?date=YYYY-MM-DD`, постранично, по 10 матчей на
страницу. Дата — сегодня и следующие несколько дней вперёд (горизонт
задаётся настройкой, по умолчанию 3 дня: линия на матчи дальше вперёд
неустойчива и не всегда доступна).

**Частота:** дважды в сутки, 00:00 и 12:00 UTC (ФТ-2, ФТ-10), отдельным
запуском от остальных шагов.

**Кэш не используется** — это существенно: при одинаковом параметре `date`
ответ в 12:00 отличается от ответа в 00:00 (линия двигается). Закэшированный
утренний ответ сделал бы второй снимок копией первого.

**Запись:**
1. `bookmakers` и `bet_types` — upsert из полного ответа (все 33
   букмекера), справочники наполняются здесь, не миграцией (решение из
   `docs/06`).
2. `odds_snapshots` — одна строка на матч на запуск: `taken_at` = время
   начала запуска (одно для всех снимков в нём, не время API-ответа),
   `source_updated_at` ← поле `update` ответа. Ключ конфликта —
   `(fixture_id, taken_at)`.
3. `odds_values` — только для букмекеров из настройки (**1xBet, Pinnacle**,
   ФТ-10), по всем их рынкам. Значения других букмекеров в ответе
   присутствуют, но отбрасываются при разборе.

**Список букмекеров — настройка**, не константа в коде: `[1xBet, Pinnacle]`
по умолчанию, задаётся конфигурацией сбора. Раз сырые ответы лежат в кэше
целиком, изменение списка не требует новых запросов к API — только
повторного разбора последних 30 дней кэша (ADR-2).

## Шаг 5. События завершённых матчей

**Источник:** `/fixtures/events?fixture=…`, один запрос на матч.

**Отбор матчей:** лига отслеживается (`is_tracked`), `status_short` в множестве
завершённых (`FT`, `AET`, `PEN`), `league_seasons.has_events = true`, и в `fixture_fetch_state`
либо нет строки, либо `events_fetched_at IS NULL` и `events_attempts <
3`. Порядок — от новых матчей к старым: свежие данные важнее.

**Запись:** `teams`, `players` (upsert из встречающихся в событиях — как
в переносе, ПР-3), `fixture_events` с `event_key` из `src/common/keys.py`
— той же функцией, что и перенос (иначе задвоение, проверено тестом
`test_event_key_same_for_parquet_and_api`).

**Состояние.** После успешного запроса (даже если события — пустой
список: у матча их может не быть): `fixture_fetch_state.events_fetched_at`
= сейчас, `events_attempts` не увеличивается. При ошибке запроса —
`events_attempts += 1`, `events_fetched_at` не трогается. При
`events_attempts >= 3` матч больше не выбирается этим шагом (счётчик
защищает от бесконечных повторов по матчам, где источник молчит).

## Шаг 6. Статистика завершённых матчей

Тот же отбор и то же состояние, что в шаге 5, но по `has_statistics` и
`statistics_fetched_at`/`statistics_attempts`.

**Источник:** `/fixtures/statistics?fixture=…`.

**Запись:** `fixture_statistics`, приведение типов — как в переносе (ПР-6):
проценты из строк, xG и `goals_prevented` в `NUMERIC`. Преобразование
вынесено в общую функцию `src/common/stats.py`, используемую и переносом,
и этим шагом — чтобы не разойтись в двух местах.

## Шаг 7. Составы

Тот же отбор и состояние, что в шагах 5–6, но по `has_lineups` и
`lineups_fetched_at`. Счётчика попыток `lineups_attempts` в схеме уже
достаточно (`docs/03`).

**Источник:** `/fixtures/lineups?fixture=…`.

**Запись:** `teams`, `players`, `fixture_lineups` (`formation`, `coach_id`,
`coach_name`), `fixture_lineup_players` (`is_starter` = `true` для
`startXI`, `false` для `substitutes`, `shirt_number`, `position`, `grid`).
Ключ — `(fixture_id, team_id)` для составов, `(fixture_id, team_id,
player_id)` для игроков.

## Распределение бюджета внутри одного запуска

Все семь шагов используют один и тот же `ApiClient` с одним счётчиком
`requests_used`, поэтому бюджет распределяется естественным образом: шаг,
идущий раньше в списке, тратит первым. Порядок 1→7 продиктован
приоритетом (`docs/02`): если лимит кончится на шаге 6, шаг 7 просто не
запустится в этот раз и продолжится на следующий день — данные шагов 1–5
уже в базе (НФТ-1).

Явного деления бюджета по шагам нет: попытка заранее разрезать общий лимит
на порции для каждого шага добавила бы сложность без выгоды — шаги и так
идут по порядку важности.

## Функциональные требования

### ЕС-1. Журнал запусков

Каждый вызов `run()` открывает и закрывает строку `collection_runs`
(`job_name` = имя шага). При исключении строка закрывается со статусом
`failed` и текстом ошибки, исключение пробрасывается дальше — сбой одного
шага не должен тихо потеряться, но и не должен уронить весь процесс
(шаги 2–7 работают из общего раннера, см. «Интерфейс»).

### ЕС-2. Возобновляемость

Прерывание в середине шага 5, 6 или 7 не теряет уже записанные матчи:
запись идёт по одному матчу за раз, каждый — отдельная транзакция
(`ON CONFLICT DO UPDATE`), `fixture_fetch_state` обновляется сразу после
записи данных того же матча, в одной транзакции с ней.

### ЕС-3. Отсутствие дублей

Все ключи конфликта — из `docs/03-модель-данных.md`. Повторный запуск
того же шага в тот же день не меняет число строк (кроме уточнённых
данных вроде статуса матча).

### ЕС-4. Уважение покрытия

Шаги 3, 5, 6, 7 не отправляют запросы туда, где `league_seasons` говорит,
что источник не отдаёт нужный набор (ФТ-5). Шаг 2 не ограничен покрытием:
результаты матчей есть почти всегда, ограничение здесь — по сезону
(текущий год ± запас).

### ЕС-5. Не более трёх попыток на матч

Отбор для шагов 5–7 исключает матчи с `*_attempts >= 3`. Без этого
несуществующие или навсегда недоступные данные съедали бы бюджет каждый
день заново.

## Интерфейс

```bash
python3 -m src.jobs.collect --job catalog
python3 -m src.jobs.collect --job fixtures
python3 -m src.jobs.collect --job injuries
python3 -m src.jobs.collect --job odds
python3 -m src.jobs.collect --job events
python3 -m src.jobs.collect --job statistics
python3 -m src.jobs.collect --job lineups
python3 -m src.jobs.collect --job daily   # 2, 3, 5, 6, 7 подряд (без коэффициентов), один клиент и бюджет
python3 -m src.jobs.collect --job cleanup # удалить кэш старше 30 дней (без ключа и базы)
```

На сервере шаги запускает обёртка `deploy/run_collect.sh <шаг> [бюджет]`,
расписание — `deploy/football-collector.cron` (`docs/04`).

`--job daily` — то, что реально стоит в cron ежедневно: матчи, травмы, события,
статистика, составы. **Коэффициенты в него не входят:** `odds` и `catalog` идут
отдельными строками расписания (дважды в сутки и раз в неделю). Иначе
ежедневный сбор делал бы лишний, третий снимок линии в неурочное время.
Отдельные `--job <шаг>` — для ручного запуска и разбора проблем (ПР
из спецификации переноса используют то же соглашение).

Общие флаги: `--max-requests N` (переопределяет бюджет клиента для
разового запуска), `--dry-run` (разбор без записи — для проверки на
живых данных без изменения базы).

## Ошибки и крайние случаи

| Ситуация | Поведение |
|---|---|
| Сетевая ошибка на матче | `*_attempts += 1`, шаг идёт дальше к следующему матчу |
| Суточный лимит API исчерпан (`ApiClient.quota_exhausted`) | текущий шаг останавливается, `collection_runs.status = quota_exceeded`, остальные шаги `daily` не запускаются в этот раз |
| Собственный дневной бюджет исчерпан | то же самое, но это наш резерв, не лимит API — назавтра продолжится с того же места |
| Матч без `fixture_id` в ответе `/injuries` | строка пропускается, событие в отчёт |
| Пустой `response` (данных у матча правда нет) | считается успехом: `*_fetched_at` проставляется, `*_attempts` не растёт |
| База недоступна | шаг завершается с ошибкой, кэш ответов на диске цел — следующий запуск ничего не теряет |

## Наблюдаемость

По завершении `--job daily` печатается сводка: сколько матчей обработано
на каждом шаге, сколько запросов потрачено суммарно и что осталось от
дневного бюджета (`ApiClient.daily_remaining`). Это ручная проверка перед
включением в cron (этап 5) и материал для отчёта о полноте (ФТ-7,
отдельная задача).

## Безопасность

Ключ API берётся из окружения, в логи и `collection_runs.error_text` не
попадает (НФТ-3) — при ошибке HTTP сохраняется код и путь запроса, не
заголовки.

## Критерии приёмки

1. Каждый из семи шагов отдельно запускается на одной лиге и одном дне,
   результат сверяется с ответом API вручную.
2. Повторный запуск `--job daily` подряд два раза не меняет число строк
   (кроме уточнений вроде статуса матча).
3. Прерывание `--job daily` посередине шага 6 и повторный запуск дают тот
   же результат, что один непрерывный запуск.
4. При установленном малом `--max-requests` `collection_runs` фиксирует
   `quota_exceeded`, и уже обработанные матчи остаются в базе.
5. `odds_values` после запуска шага `odds` содержит записи только для
   1xBet и Pinnacle, при том что в сыром кэше есть все 33 букмекера.

## Тестовые сценарии

Все — на подменённом `ApiClient.transport` (как в `tests/test_api_client.py`)
и временной базе, без обращения к сети (НФТ-8).

| № | Проверка | Ожидание |
|---|---|---|
| 1 | Шаг 2 на ответе с двумя матчами | оба в `fixtures`, команды в `teams` |
| 2 | Повторный запуск шага 2 с изменённым статусом матча | строка обновлена, не задвоена |
| 3 | Шаг 5 на матче без покрытия событий (`has_events=false`) | запрос не отправлен |
| 4 | Шаг 5, у матча уже 3 попытки | матч не выбирается |
| 5 | Шаг 5, пустой ответ `response: []` | `events_fetched_at` проставлен, `attempts` не растёт |
| 6 | Шаг 5, сетевая ошибка | `attempts += 1`, шаг переходит к следующему матчу |
| 7 | Шаг 4 на ответе с 5 букмекерами | в `odds_values` только 1xBet и Pinnacle |
| 8 | Прерывание на середине списка матчей и повтор | итоговое состояние совпадает с непрерывным запуском |
| 9 | `--job daily`, лимит клиента заканчивается на шаге 5 | шаги 6–7 не запускаются, `collection_runs` шага 5 = `quota_exceeded` |
| 10 | `--dry-run` | база не изменилась, `collection_runs` не пишется |

## Открытые вопросы

1. **Горизонт сбора коэффициентов вперёд** — по умолчанию 3 дня.
   Подтвердить или изменить.
2. **Куда сначала.** Как и с переносом: сначала локальная база и ручная
   проверка каждого шага, затем сервер (этап 5).
