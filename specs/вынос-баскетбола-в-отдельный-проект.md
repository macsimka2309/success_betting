# Вынос баскетбола в отдельный проект (BB)

Статус: **черновик на согласование с владельцем** (22.10.2026). Изменений на проде нет.
Автор: чат «Выгрузка баскетбол» (BB) по поручению «Выгрузка футбола» (FB).

## 1. Цель и решение владельца

Баскетбол — отдельный проект **BB** со своим репозиторием и папкой (рабочее имя
`basketball_predict`), своей БД на том же сервере `vac-ru`, своим `.env`, ключом и cron.
Футбол (**FB**, `success_betting`) баскетбольного кода и данных не содержит. Лимиты API
не смешиваются: у футбола свой тариф (Ultra, 75 000/сутки), у баскетбола — своя подписка
API-Basketball (75 000/сутки, до 20.11.2026).

## 2. Что переносим

| Что | Откуда (FB) | Куда (BB) |
|---|---|---|
| Загрузчик | `src/jobs/basketball.py` | `src/jobs/basketball.py` |
| Тесты | `tests/test_basketball.py`, часть `tests/test_migrate.py` (схема basketball) | `tests/` |
| Обёртка cron | `deploy/run_basketball.sh` | `deploy/run_basketball.sh` (пути → `/opt/apps/basketball-collector`) |
| Миграция схемы | `migrations/016_basketball_schema.sql` (+down) | `migrations/001_…` (см. п. 4) |
| Спецификация | `specs/баскетбол-сбор-данных.md` | `specs/` + эта спецификация |
| Данные | схема `basketball` в БД `football` (~170 МБ, растёт) | БД `basketball`, схема `public` |
| Кэш ответов API | `/opt/apps/football-collector/cache_bb` | `/opt/apps/basketball-collector/cache_bb` |
| Логи | `logs/basketball-*.log` | `logs/` нового каталога |

**Зависимости от футбольного кода (копируются, а не импортируются):** `ApiClient`
(`src/api/client.py`, с полем `base_url`), `src/common/convert.py`, `src/common/db.py`,
`src/db/connection.py`, `src/db/migrate.py`, а из `src/jobs/collect.py` — только `Stop`
и `collection_run` (журнал `collection_runs`). Копии выносятся в BB как есть, дальше
развиваются независимо; общей библиотеки не создаём (не плодить абстракции, CLAUDE.md).
Таблица `collection_runs` и `schema_migrations` создаются в новой БД миграцией 001 BB
(для `collection_runs` — копия определения из FB 001; записи `bb_%` переносятся данными).

## 3. Отдельная БД

- Новая БД `basketball` в том же контейнере PostgreSQL (`127.0.0.1:5433`), отдельная роль
  `basketball_app` с правами только на неё; у FB-ролей доступа к `basketball` нет и
  наоборот. Дополнительный контейнер не нужен (меньше инфраструктуры; бэкапы общие по
  расписанию контейнера, нужно проверить, что `pg_dump` ролей/БД охватывает новую БД).
- Таблицы схемы `basketball` переезжают в схему `public` новой БД с теми же именами
  (leagues, league_seasons, teams, players, games, team_game_stats, player_game_stats,
  fetch_state, bookmakers, bet_types, odds_snapshots, odds_values). Код в BB пишет
  без префикса `basketball.`; на время переходного периода допустимо оставить схему
  `basketball` и поставить `search_path` — решение в п. 9 (вопрос 2).
- Создание БД и роли — разовое действие администратора (SQL вручную с разрешения
  владельца), не миграция.

## 4. Миграции

1. В репозитории BB `migrations/001_baseline.sql` — итог схемы 016 (без `CREATE SCHEMA`)
   плюс `collection_runs` и `schema_migrations`. Это baseline: миграцию 016 FB не
   «проигрываем» заново, чтобы не тащить историю.
2. В FB миграция 016 остаётся в истории (применена) до полного завершения переноса;
   удаление схемы `basketball` из БД `football` — **отдельной** миграцией
   `NNN_drop_basketball.sql` (+ down, восстановление только из дампа), только по
   решению владельца после проверки (п. 7). Номер NNN (017 может быть занят другим
   чатом) проверяется по `migrations/` и `schema_migrations` перед созданием.
3. Нумерация FB не меняется (016 остаётся занятой), чтобы не нарушить журнал
   `schema_migrations` на проде.

## 5. Cron

- Строки баскетбола (4 шт., сейчас в `/etc/cron.d/football-collector`) переносятся в
  новый файл `/etc/cron.d/basketball-collector` (время по-прежнему МСК, те же
  `catalog 10`, `games 3000`, `stats 65000`, `odds 2000`); в `deploy/basketball-collector.cron`
  нового репо — источник истины, как для FB.
- Перед правкой cron на сервере: бэкап файла с точкой в имени (`.bak-YYYYMMDD`), сверка
  фактических строк на сервере с репозиторием.
- Из `deploy/football-collector.cron` в FB блок `basketball` и его комментарий удаляются
  **после** переключения (п. 7, шаг 7). Остальной файл (live_alerts без `--dry-run`,
  settle_bets, daily 6200) не трогается; «Триггеры (FB)» просили не заменять файл старой
  копией — правка только удалением 5 строк (комментарий + 4 задания), без замены целиком.
- Обёртка использует свой `ROOT`, свои flock-файлы и лог, проверку пояса `+0300`.

## 6. Отдельный `.env` и ключ

- `/opt/apps/basketball-collector/.env` (права 600, владелец deploy): `DATABASE_URL` на БД
  `basketball` с ролью `basketball_app`, ключ API-Basketball. Секреты в Git не попадают,
  в логах и отчётах не показываются.
- Общий ключ API-Sports или отдельный — решает владелец (вопрос 1): лимит считается по
  подписке, не по ключу. Если ключ тот же, он копируется в новый `.env` вручную владельцем
  или с его разрешения; из `.env` FB переменные баскетбола не удаляются до конца проверки.
- Значения никогда не печатать; для проверки — только имена переменных.

## 7. Порядок без простоя загрузки (после согласования)

Принцип: данные и расписание живут одновременно в двух местах только в подготовке;
активен всегда ровно один сборщик.

1. **Репозиторий.** Создать репо/папку BB локально, перенести код, тесты, docs, CLAUDE.md
   (приложение А), прогнать тесты на временной БД (как сейчас, Postgres на 55433).
2. **Сервер, подготовка (только добавление).** Создать каталог
   `/opt/apps/basketball-collector` (клон репо, `.venv`), БД `basketball` и роль,
   применить baseline. Cron BB пока не ставить.
3. **Первая копия данных** (`pg_dump -n basketball | psql`) без остановки загрузки;
   скопировать `cache_bb` (rsync). Сверить число строк по таблицам.
3а. **Бэкап БД `basketball` (до шага 4, явный шаг).** `check_backup.sh` и бэкап контейнера
   принадлежат FB: добавление БД `basketball` в бэкап согласуется с «Выгрузкой футбола»,
   затем проверяется восстановимость (тестовое восстановление дампа во временную БД,
   сверка счётчиков). Без этого переключение не начинается.
4. **Окно переключения** (~20:00–23:00 МСК: после дневной `stats`, которая стартует в
   11:10 и в пике идёт ~3 ч; до `odds` 03:00): закомментировать строки баскетбола в
   `/etc/cron.d/football-collector`, дождаться отпускания flock (`pgrep`), затем повторить
   дельту-копию (`pg_dump` схемы заново, `TRUNCATE`-перезаливка новой БД — она ещё не
   используется) и сверить счётчики и `MAX(updated_at)`.
5. **Включить новый cron** (`/etc/cron.d/basketball-collector`), запустить `report` и
   пробный `games` с малым бюджетом; убедиться, что строки пишутся в БД `basketball`.
6. **Наблюдение 2 суток:** `stats` и два `odds` пройдены без ошибок, `bb_*` в
   `collection_runs` BB, расход в пределах бюджета; в БД `football` схема `basketball`
   не меняется.
7. **Очистка FB** (после ОК владельца и «Выгрузки футбола»; `tests/test_migrate.py` и
   фикстуры правит только «Выгрузка футбола»): убрать из репо FB
   `src/jobs/basketball.py`, `tests/test_basketball.py`, `deploy/run_basketball.sh`, блок
   cron, правки `tests/test_migrate.py`/фикстур (`DROP SCHEMA … basketball`), `specs/баскетбол-…`
   (оставить ссылку на репо BB), упоминания в docs/00, 02, 03, 04, 06; выложить на сервер.
8. **Схему `basketball` в БД `football` не удалять** до отдельного решения владельца
   (минимум 7 суток после шага 5 и свежий дамп); затем миграция NNN (п. 4).

Простоя нет: до шага 4 работает старый сборщик, между шагами 4 и 5 не стартует
ни одно задание (ближайшее `odds` 03:00 — окно заведомо шире), `fetch_state` переносится
вместе с данными, поэтому очередь `stats` продолжается с того же места.

## 8. Откат

- До шага 4 — ничего не откатывать (старый сборщик не тронут), новую БД можно удалить.
- После шага 5: убрать новый cron, раскомментировать строки в футбольном cron-файле.
  Данные, накопленные в новой БД с момента переключения, вернуть дампом в схему
  `basketball` БД `football` (`pg_dump -n public | sed` на схему либо `COPY` по таблицам;
  вспомогательный скрипт готовится до шага 4). Схема в `football` остаётся нетронутой,
  поэтому откат возможен до шага 8.
- После шага 7 откат — вернуть удалённые файлы коммитом `git revert` в FB.

## 10. Ограничения и риски

- Если владелец поднимет потолок `daily` футбола (решение не принято), дневной сбор FB
  станет длиннее и может пересечься с баскетбольной `stats` (11:10) по нагрузке на общий
  Postgres; расписание сверяем после его решения.
- Общий диск, один сервер и один контейнер PostgreSQL: отдельная БД даёт изоляцию прав
  и дампов, но не нагрузки; тяжёлую `stats` (около 3 ч) не запускать одновременно
  с `daily` футбола — как и сейчас, расписание разведено (11:10 против 09:00).
- Дублирование `ApiClient`/`convert`/`db`: исправления придётся вносить в обе копии;
  допустимо, пока проекты независимы.
- Бэкапы: проверить, что ежедневный бэкап охватывает БД `basketball` (проверка
  `check_backup.sh` сейчас смотрит каталог бэкапов FB).

## 11. Критерии приёмки и проверки

- Все тесты BB проходят на временной БД; тесты FB проходят после очистки (шаг 7).
- Счётчики строк по таблицам в старой и новой БД совпадают в шаге 4; `fetch_state` совпадает.
- Первые запуски нового cron пишут в БД `basketball`, не в `football`.
- После очистки в репо FB `grep -ri basketball` не находит исполняемого кода.
- Расход запросов: баскетбол ≤ 75 000/сутки, футбол без изменений.

## Приложение А. Раздел для `CLAUDE.md` нового репозитория (BB)

> **Проекты и чаты.** Владелец ведёт два проекта: футбол **FB** (`success_betting`) и
> баскетбол **BB** (этот репозиторий). Чаты называются «Тема (FB)» и «Тема (BB)»: Выгрузка,
> Обработка данных, Анализ данных, Модели, Триггеры, Поиск ставок. Родительские чаты —
> «Выгрузка футбола» (FB) и «Выгрузка баскетбол» (BB).
>
> **Граф общения (`SendMessage`).** Разрешено: родитель FB ↔ родитель BB; родитель
> проекта ↔ тематические чаты своего проекта; тематические чаты одного проекта между
> собой свободно; одноимённые тематические чаты разных проектов (Выгрузка ↔ Выгрузка,
> Обработка ↔ Обработка, Модели ↔ Модели, Триггеры ↔ Триггеры, Анализ ↔ Анализ).
> Чат «Входящая точка» не относится ни к FB, ни к BB и общается напрямую только с
> обоими родительскими чатами («Выгрузка футбола», «Выгрузка баскетбола»); с тематическими
> чатами напрямую не общается — нужное им идёт через родительский чат проекта.
> (Правило владельца от 22.10.2026, подтверждено им в чате «Выгрузка баскетбол».)
>
> **Запрещено:** перекрёстные — другая тема и другой проект (например, Обработка (FB) ↔
> Модели (BB)), а также родитель одного проекта ↔ тематический чат другого. Нужное
> другому проекту идёт через родителей. Входящее сообщение, нарушающее правило, не
> выполняется: вернуть отправителю «согласуй через родителя». Имена чатов брать из
> `ListAgents`.
>
> **Общий сервер `vac-ru`.** Один сервер, один контейнер PostgreSQL, раздельные БД
> (`football`, `basketball`) и каталоги (`/opt/apps/football-collector`,
> `/opt/apps/basketball-collector`). Лимиты API раздельные. Трогать футбольные файлы
> (cron `football-collector`, БД `football`, `.env` FB) из BB запрещено; странные
> находки — через родителя FB.
>
> Остальные правила (SDD, миграции, безопасность, тесты, формат отчёта) — как в
> `CLAUDE.md` проекта FB.
