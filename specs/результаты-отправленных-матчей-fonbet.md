# Ежедневный конечный счёт отправленных матчей

Статус: требования владельца зафиксированы 15.11.2026; проект реализации.
Код, миграции и production-расписание этой спецификацией не включены.

## Цель и существующее решение

Для каждого подтверждённо отправленного в Telegram футбольного матча сохранить
конечный счёт независимо от источника сигнала, наличия API fixture_id и факта
реальной ставки. Источник — публичная страница результатов Fonbet:
`https://fon.bet/results/football?date=YYYY-MM-DD`.

Сейчас `settle_bets.py` рассчитывает старые `live_alerts_sent` через API-Football.
Единый диспетчер хранит доставку в `live_alert_outbox`, а соответствия источников —
в `live_alert_aliases`. Для Fonbet-only без fixture_id запись в старую таблицу
не создаётся. Поэтому одной доработки старого расчёта недостаточно.

## Ежедневный сценарий

1. Отдельная серверная задача один раз в сутки в **00:00 Europe/Moscow**.
   В одном суточном проходе обрабатываются предыдущие календарные сутки
   [00:00, 00:00) по времени отправки сигнала и весь накопленный хвост без результата.
2. Начальная загрузка очереди также включает все ранее подтверждённо отправленные
   матчи без конечного счёта, а не только вчерашние.
3. Даты страниц выбираются по дате события, а не только отправки сигнала:
   матч мог начаться до полуночи, а сигнал прийти после неё. Для пограничных
   случаев проверяются соседние даты без расширения множества целевых матчей.
4. После чтения валидные результаты сохраняются транзакционно; повтор за ту же
   дату идемпотентен. Матчи без подтверждённого результата проверяются на следующем
   суточном запуске. Отсутствие строки на странице не считается отменой матча.
5. Запуск не зависит от включённого Mac. Поддерживаются ручной dry-run и повтор
   за конкретную дату, без изменения суточного расписания.

История личных ставок остаётся отдельным процессом с её существующими повторами
00:15 / 01:00. Новый сбор счёта не запускается повторно вместе с этими повторами.
Задачи используют общую блокировку браузера, не открывают тяжёлые страницы
одновременно и уступают live-сбору по действующим правилам допуска. Если браузер
занят, задача ограниченно ждёт; после таймаута явно фиксирует пропуск, не копит
параллельные процессы. Следующий суточный проход подхватывает задолженность.
Пропущенный суточный запуск догоняется после старта сервера (`Persistent=true`).

## Отбор и идентификация

- Основной набор — `live_alert_outbox.state = 'sent'` и прежние `live_alerts_sent`.
  `pending`, `expired`, `retry` и неоднозначная доставка `uncertain` не выдаются
  за подтверждённо отправленные. `uncertain` отражается отдельно в отчёте.
- Результат привязан к каноническому `alert_match_id` с учётом `merged_into`;
  несколько категорий/сообщений одного матча используют один конечный счёт.
- При наличии Fonbet event_id требуется подтверждённая связь с событием страницы
  результатов. Нельзя предполагать, что URL результатов сохраняет live-ID:
  это проверяется на реальных примерах и сохраняется как соответствие источника.
- Если сигнала Fonbet-ID нет, допускается только однозначное совпадение обеих
  команд, турнира, начала матча и формата (женщины, U19, резерв и т. п.).
  Подтверждённые существующие алиасы можно использовать; нечёткое совпадение
  названий само по себе не подтверждает идентичность. Перестановка хозяев/гостей
  требует явного подтверждения и корректного переворота счёта.
- Неоднозначность или отсутствие кандидата сохраняется с причиной для повторной
  проверки; фиктивный API fixture_id не создаётся. API-only сигналы тоже входят
  в целевой набор; если Fonbet не публикует этот матч, результат остаётся неизвестным.

## Счёт и бизнес-правила

- Хранить подтверждённый счёт основного времени, включая компенсированное время,
  отдельно от дополнительного времени и серии пенальти. Сохранять статус матча,
  исходное представление счёта и обозначение его периода. Если выделить основное
  время невозможно, не подменять его общим итогом: статус `needs_review`.
- Сохранять только завершённый результат. Перерыв, текущий счёт, перенос,
  остановка и незавершённый матч не превращаются в окончательный счёт.
  Отмена фиксируется отдельным подтверждённым статусом, без выдуманного 0:0.
- Счёт при отправке и все live-наблюдения остаются неизменными.
- Разница между конечным счётом и счётом при сигнале может подтвердить гол
  **после сигнала**, если оба счёта совместимы и относятся к основному времени.
  Она не доказывает гол **после 75-й минуты** для сигнала, отправленного раньше.
  Существующие `outcome`/`goals_after_75` не рассчитываются по конечному счёту:
  для них нужны достоверные события с минутами голов.
- Не менять `bets.status`, прибыль и расчёт купонов: история Fonbet остаётся
  источником подтверждённого результата реальной ставки.
- Подтверждённые данные API не затирать. Расхождение источников фиксировать
  отдельно; уже подтверждённый счёт Fonbet не перезаписывать молча.

## Предлагаемая модель данных и компоненты

Добавочная миграция после проверки актуальной схемы. Отдельная таблица результатов
по каноническому `alert_match_id`: статус сверки (`pending`, `confirmed`,
`not_found`, `ambiguous`, `needs_review`, `conflict`), Fonbet ID при наличии,
дата страницы, названия/турнир/начало события, официальный статус, счёт основного
времени, отдельные счёт после дополнительного времени и пенальти при наличии,
исходное представление счёта, источник, URL, время чтения, `resolved_at`,
последняя попытка и причина незавершённости. Исходные наблюдения и расхождения
сохраняются для аудита; уникальность результата и операция слияния идентичностей
не допускают дублей и потери противоречащих наблюдений.

План: публичный браузерный экспорт → проверка формата и сопоставление →
транзакционный импорт → сводка запуска. Полнота просмотра всех разделов,
пагинации/прокрутки и раскрытых результатов должна быть доказана. Неполный
экспорт может сохранить доказанные результаты, но получает статус `partial`;
он не доказывает отсутствие остальных матчей.

Задача получает отдельную блокировку запуска, общий browser gate, лимит времени
и ограниченное число повторов чтения. Закрывает свои страницы/процессы в finally,
не затрагивая авторизованную сессию истории. Секреты, cookies, профиль, .env и
личный кабинет не читаются и не попадают в логи. На сайте выполняется только чтение.

## Ошибки и отчётность

Отчёт: московская дата прохода, количество целевых матчей, подтверждённых,
новых, уже сохранённых, ожидающих завершения, не найденных, неоднозначных,
конфликтующих; число страниц и полнота обхода. Ошибка доступа, изменение DOM,
неполный обход и занятая блокировка различаются кодами.
В Telegram — краткая суточная сводка и явное сообщение о сбое/неполном проходе,
без лавины повторных предупреждений. Старая нерешённая запись не исчезает
из очереди по возрасту; длительные пропуски отражаются в сводке.

## План реализации и приёмка

1. Проверить отображаемую страницу на сервере: часовой пояс параметра date,
   границы суток, ID, все разделы, дополнительные периоды, завершённые статусы.
   Попытка прочитать ссылку веб-инструментом 15.11.2026 была недоступна;
   DOM, семантика даты и полнота источника пока не подтверждены.
2. Подготовить парсер и тесты, добавочную миграцию, импорт и dry-run отчёт.
3. Проверить реальное сопоставление отправленных API/Fonbet-only матчей,
   завершённые и переходящие через полночь события; затем включить серверный таймер.
4. Проверить повторный запуск без дублей, два одновременных запуска, частичный
   обход, потерю доступа и освобождение браузера. Миграция не меняет прежние
   таблицы ставок/срезов; отключение нового таймера сохраняет накопленные результаты.

Обязательные сценарии: обычный FT; 0:0; матч после полуночи; отложенный результат
с прошлого дня; API-only и Fonbet-only; женские/юношеские команды с похожими
названиями; несколько кандидатов; дополнительное время/пенальти; отмена/перенос;
расхождение с API; слияние идентичностей; неоднозначная доставка; отсутствие
минут голов не меняет признак гола после 75-й; повтор импорта не меняет ставки.
