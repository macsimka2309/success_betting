# Проверка реализации напоминаний и голов после сигнала

Результат: нужны исправления перед production-выпуском. Прежняя отметка 23/23 отражала выполненный чек-лист, но не покрывала обнаруженные пограничные случаи. В этой проверке реализация и production не менялись; использована отдельная PostgreSQL localhost:55439 и mock источники. Файлы/настройки production и активные сборщики не трогались.

## P1 — один известный гол дублируется после непустого частичного ответа

Место: `src/jobs/signal_goal_store.py:40–43`.

Ключ без provider ID включает вычисленные `score_after_home/away`. Полный API-ответ с единственным голом на 80-й минуте даёт счёт после гола 1:0. Когда API повторно возвращает этот же гол, но список неполон относительно итогового счёта 2:0, нормализатор оставляет score_after неизвестным. Fingerprint меняется; прежняя строка не деактивируется, новая добавляется, отношения включают обе. `live_signal_goals_selected` выдаёт **два подтверждённых гола после сигнала вместо одного**. Флаг неполноты не устраняет дублирование.

Воспроизведение: `test_partial_nonempty_response_must_not_duplicate_known_goal`, ожидается 1, получено 2. Требуется сопоставление неполных событий с прежними записями без использования изменяемых вычисленных полей как единственной идентичности; неоднозначность не должна превращаться в ещё один подтверждённый гол.

## P1 — ежедневная попытка расходуется, когда запрос пропущен из-за внутреннего лимита

Место: `src/jobs/signal_results.py:49–60`, `schedule_after()` и безусловный вызов планировщика после `poll_sources()`.

После исчерпания `browser_limit=1` Fonbet-only матч получает пустые observations без обращения к источнику. Worker трактует это как source_unavailable и увеличивает review_day. В тесте два due-матча и один разрешённый browser read: запрос выполнен для одного, но счётчики обоих стали 1. Так семь обязательных фактических проверок могут закончиться без единого обращения к части матчей.

Воспроизведение: `test_internal_browser_budget_must_not_consume_daily_check`. Требуется различать выполнение попытки, внешний отказ и внутренний перенос из-за квоты/лимита; внутренний перенос не расходует review_day и должен сохранять ближайшую возможность выполнить запрос.

## P1 — 30 ожидающих напоминаний блокируют все более новые

Место: `src/jobs/signal_reminders.py:34–35`, `:50`.

Выбираются старейшие 30 строк до проверки наличия свежего контекста. Строка без контекста остаётся waiting с прежним приоритетом. Если таких строк накопилось 30 (например, матчи исчезли и нет подтверждения окончания), они выбираются каждым запуском. Даже 31-й матч со свежим контекстом никогда не обрабатывается. Повторный запуск воспроизводит ту же блокировку.

Воспроизведение: `test_waiting_reminders_must_not_starve_ready_31st_signal`, получено 0 сообщений вместо 1 после двух запусков. Требуется отбирать готовые записи до LIMIT либо обеспечивать ротацию/продвижение очереди; одной короткой задержки без изменения порядка недостаточно.

## P2 — у исчезнувшего Fonbet-only матча не читается подтверждение завершения

Место: `tools/fonbet_live/timeline.cjs:39`, `src/jobs/signal_goals.py:101`.

Когда событие уже исчезло из discovery, адаптер открывает сохранённую URL, но возвращает `period_text=''`: статус самой карточки не извлекается. Нормализатор определяет FT только из этого метаданного поля, а не из полученного DOM. В воспроизведении завершённый sports widget с полным списком голов и временем 90:00 остаётся `2H / regulation_end_unconfirmed`. Для матча без API и другого подтверждения окончания worker останется waiting_end, не назначит первичную загрузку и суточные проверки.

Воспроизведение: `test_archived_card_reader_metadata_must_expose_finished_status`. Это проверка проводки статуса на синтетическом завершённом widget; доступность и конкретная разметка реальной архивной карточки ранее не подтверждались. Нужен проверенный источник явного окончания карточки/результата; исчезновение из live само по себе не является таким подтверждением.
