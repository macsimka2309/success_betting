# Proposal

## Why

После первого сигнала полезно напомнить о матче, только пока исходный триггер всё ещё выполняется. Для матчей, обнаруженных через Fonbet, «Ход матча» нужно сохранить до исчезновения live-карточки, особенно в концовке и добавленном времени.

Исправления девятого раунда прошли локальную приёмку. Дополнительная проверка воспроизвела завершение наблюдения и отмену повтора по запоздавшему статусу Fonbet. [Предыдущая приёмка](../../../../reports/signal-tracking-implementation/2026-11-20-round-9.md) · [Проверка порядка статусов](../../../../reports/signal-tracking-review-round-10-2026-11-20/review.md)

## What Changes

- Для обоих источников допускается один повтор по свежему срабатыванию того же триггера в обычном окне 65–75 минут. После доставки повтора или закрытия возможности его отправки завершается наблюдение ради напоминания.
- Перед повтором учитывать более свежую минуту, уже подтверждённую браузером Fonbet для того же матча. Она закрывает окно после 75-й минуты без дополнительных запросов.
- Для сигнала API-Football обработка матча в рамках этой функции заканчивается вместе с напоминанием. Дополнительных опросов результатов, голов и ежедневных перепроверок для такого сигнала нет.
- По сигналу Fonbet сбор событий продолжается после первого сообщения независимо от повтора. С 89-й минуты второго тайма назначается опрос «Хода матча» каждую минуту до подтверждённого конца основного времени, включая добавленное. За ним следуют первичная загрузка результата, суточная перепроверка и до семи ежедневных попыток при неполноте.
- Режим закрепляется по источнику первого подтверждённого сообщения. Подтверждённые алиасы используются для единой идентичности матча. Матч, известный в обоих источниках, получает один режим и не более одного повтора.
- Частичные ответы сохраняют отмену гола и устойчивую идентичность автогола. Раздельно проверяются факт окончания и полнота списка голов по счёту основного времени. Пустые ответы и лимиты API не должны блокировать уже назначенный опрос Fonbet.
- Функция применяется к новым первым сигналам после активации. Сохраняются действующие критерии первого сигнала и смысл `goals_after_75`.

## Исправления после третьего раунда проверки

- Для повтора зафиксировать первый определимый результат по сохранённым опросам исходного источника. Поздний положительный снимок не открывает ожидание после отрицательного результата.
- Различать голы по базовой и добавленной минутам во всех ветках сопоставления. Отдельно сохранять достоверные голы на 90+2 и 90+6 уже в live, с последующей сверкой и возможностью отмены VAR.
- Сохранять исходный срок каждой послематчевой проверки при переносах. После одного пятиминутного цикла ожидания отдавать просроченной проверке ближайший доступный штатный слот в пределах действующего браузерного лимита.

## Исправления после четвёртого раунда проверки

- Сохранять известный гол при конфликте счёта в частичном ответе без надёжной идентификации. Спорную запись направлять на отдельное сопоставление.
- Резервировать однозначные соответствия по всему таймлайну до обработки исправленных минут. Если финальный таймлайн переносит один гол на минуту другого, сохранять оба прежних ID при подтверждённом соответствии.
- Перед первым решением по открытому напоминанию API-Football включать в хронологию однозначно связанные архивные наблюдения до миграции 036. Восстановление использует сохранённые ответы в пределах исходного окна напоминания.

## Исправления после пятого раунда проверки

- При добавлении более раннего гола сохранять ID событий, забитых одной командой на одной минуте, если тип и подтверждённая последовательность позволяют их различить. Накопленный счёт обновляется у прежних событий. При неоднозначности сохраняются прежние записи и кандидаты на сопоставление.
- При восстановлении архивной пары для API-напоминания проверять последний успешный live-ответ того же запуска, полученный до запроса статистики. Если в нём матч отсутствует, дублируется или имеет несовместимый контекст, эта статистика без явной связи исключается из решения о повторе.

## Исправления после шестого раунда проверки

- Использовать для первого решения и доставки API-напоминания только проверенные пары исходных наблюдений статистики и контекста. Снимок 75-й минуты может указать на пару через архивные ID. Отклонённая пара исключается из решения и отправки по всем путям.
- Сохранять ID известного гола Fonbet при добавлении другого гола на ту же отметку времени. Однозначное соответствие по типу резервируется до сравнения накопленного счёта, в том числе когда прежняя группа состояла из одного гола.
- При спорном переносе минуты учитывать связанных кандидатов на обеих отметках времени. Если новая строка может оказаться версией уже сохранённого гола, оставить её на сверке с прежними записями. Подтверждённый отдельный гол получает свой ID.

## Исправления после седьмого раунда проверки

- Проверять исходный ответ текущего контекста API-Football перед отправкой повтора и при закрытии ожидания по минуте или статусу. Если матч указан дважды, сохранять принятое первое решение и ждать пригодного штатного опроса в пределах действующего окна.
- Резервировать однозначное совпадение известного гола по стороне, периоду, обеим минутам и типу до поиска спорных переносов. Обновлять накопленный счёт на прежнем ID при проверенном таймлайне и продолжать сверку спорных событий.

## Исправления после восьмого раунда проверки

- Сверять упорядоченные ID команд API с подтверждённой идентичностью матча до решений о повторе. Несовместимый текущий ответ оставляет напоминание в ожидании, в том числе при отметке после 75-й или статусе FT.
- Сохранять каждую однозначную пару внутри группы голов на одной отметке. Если финальный таймлайн меняет тип соседнего события, обновлять известный пенальти на прежнем ID и оставлять неподтверждённую связь на сверке.
- Сохранять последнюю применённую версию каждого гола при доставке наблюдений вне порядка. Повтор старого наблюдения не меняет счёт, ссылку на версию или ревизию, даже если в более свежем протоколе остаются спорные события.
- Проверять эти правила на последовательностях опросов с промежуточными проверками состояния, повторным чтением и последующим разрешением неоднозначности.

## Исправления после девятого раунда проверки

- При конфликте известных типов в неполном ответе сохранять действующую версию гола и отправлять спорную строку на сверку. Финальный протокол сопоставляет известный пенальти с его прежним ID, а отдельный гол получает собственный ID.
- Распознавать повтор исходного наблюдения по всей семье объединённых алиасов до создания архивной записи. Использовать уже сохранённый архивный ID и защищать действующую версию гола от лишней ревизии.

## Исправление порядка подтверждений Fonbet

- Сравнивать время статуса окончания или прерывания с подтверждёнными live-наблюдениями из браузера и штатного сборщика перед изменением состояния матча или напоминания.

## Capabilities

### New Capabilities

- `live-alert-reminders`: однократное напоминание, связанное с исходным сигналом и новым успешным опросом.
- `post-signal-goals`: события голов относительно первого сигнала, полнота, коррекции и расписание перепроверок.

### Modified Capabilities

Нет: `openspec list --specs` не обнаружил зарегистрированных основных спецификаций. Старые документы в `specs/` служат контекстом; настоящие дельты описывают новое поведение.

## Impact

Исправление порядка статусов затрагивает `signal_results`, `signal_reminders`, `signal_goal_store` и регрессионные тесты. Оно использует времена в локальном архиве и существующую схему 036.
