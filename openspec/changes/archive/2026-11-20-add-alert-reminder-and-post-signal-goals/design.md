# Design

## Context

Требования описаны в [напоминаниях](specs/live-alert-reminders/spec.md) и [учёте голов](specs/post-signal-goals/spec.md). Существующая версия хранит историю гола и состояние очереди в PostgreSQL. Первое review привело к исправлениям готовности напоминаний, дедлайна отправки, идентичности гола, признака завершения Fonbet и внутренних переносов. [Локальная приёмка первого набора исправлений](../../../../reports/signal-tracking-review-fixes-2026-11-19/acceptance.md)

Исправления девятого раунда прошли локальную приёмку. Десятая проверка воспроизвела переход к окончанию или прерыванию по статусу Fonbet, который старее подтверждённого live того же события. [Предыдущая приёмка](../../../../reports/signal-tracking-implementation/2026-11-20-round-9.md) · [Десятый раунд проверки](../../../../reports/signal-tracking-review-round-10-2026-11-20/review.md)

## Goals / Non-Goals

**Goals:** аддитивное хранение жизненного цикла сигнала и событий; воспроизводимость времени и происхождения; независимые очереди доставки и проверки результатов.

**Non-Goals:** переиспользование legacy-метрики для нового смысла, изменение первого критерия, ретроспективный backfill, изменение приёмки ставок или браузерной инфраструктуры. Этот документ не запускает никакие production-действия.

## Decisions

### 1. Зафиксировать исходный сигнал, не сбрасывать существующий outbox

Предлагается отдельная запись `live_signal_tracking` на исходный `alert_id` со ссылкой на канонический `alert_match_id`, Telegram message ID/chat reference, `first_sent_at`, временем подтверждения, счётом, минутой/периодом/добавленной минутой, ссылкой на исходное наблюдение и версией функции. Telegram `date`, если доступен, — время отправки; время локального подтверждения хранится отдельно. Не выдавать наблюдавшийся до отправки счёт за точный счёт в момент отправки. Сохранять точность времени и интервал возможной отправки при неполных данных.

Создавать tracking и ожидание reminder в одной транзакции с фиксацией успешной первой доставки. Закреплять source и source_event_id первого подтверждённого сообщения из выбранного наблюдения. Открывать очередь голов в той же транзакции только при источнике Fonbet и включённом флаге учёта голов. API-сигнал сохраняет сведения для повтора и аудита без очереди результатов. Сбой после внешней отправки до commit следует существующей политике uncertain, без слепого повтора. Legacy `live_alerts_sent` и `alert_id`, используемый кнопками ставок, сохраняются.

Для reminder — отдельная `live_signal_reminders` с уникальным исходным сигналом, состояниями `waiting/sending/sent/retry/uncertain/cancelled`, причиной, lease и message ID. Сброс `live_alert_matches.sent_at` либо повторное использование исходной строки outbox отвергнуты: они ломают дедупликацию и смешивают два вида доставки. Напоминание — ответ на первое сообщение, когда Telegram это допускает, иначе явная ссылка/идентификатор; не создавать новый сигнал или независимые кнопки регистрации ставки.

### 2. Новый успешный опрос — отдельное наблюдение контекста

Добавить контексту ID опроса/наблюдения, время начала и завершения, точность часов, период (`regulation_1h/regulation_2h/extra_time/shootout/finished/unknown`), добавленное время и происхождение. Хранить минимальный неизменяемый контекст исходного сигнала и завершения; текущий context остаётся быстрым представлением.

Для первого решения читать хронологию сохранённых наблюдений закреплённой пары `first_source` и `first_source_event_id`. Использовать `fonbet_live_observations` и связанный штатный опрос Fonbet, для API использовать `api_observations` и подтверждённую связь статистики с контекстом того же матча. Если архиву API не хватает однозначной привязки, сохранять ссылки на оба наблюдения в штатном сборщике после действующей валидации, в том числе когда снимок 75 остаётся прежним. Использовать существующую нормализацию ударов обоих источников, включая поправку Fonbet на голы. Не менять правила обновления снимка 75 и частоту запросов.

Для открытого API-напоминания без первого решения восстановить отсутствующую связь при чтении локального архива. Ограничить поиск интервалом от подтверждения отправки до действующего предела ожидания и штатными запусками `live_alerts`. Проверенная явная связь в `live_api_reminder_observations` или снимке 75 имеет приоритет для соответствующей записи статистики.

Для записи статистики без явной связи сначала определить последний успешно разобранный ответ `/fixtures` с `live=all` того же `run_id` по паре `(observed_at, observation_id)` среди ответов, полученных до начала запроса статистики. Определять его до фильтрации по присутствию матча, числу его записей и идентификаторам команд. Если матч в этом ответе отсутствует, встречается несколько раз или не проходит проверку контекста, исключить эту запись статистики целиком. Если последний ответ пригоден, использовать пару при единственном допустимом контексте. Применять действующие проверки идентичности матча и команд, статуса, окна и предела в 30 секунд. Ответ, полученный после начала запроса статистики, на восстановление этой пары не влияет.

Объединять восстановленные и явно связанные пары по ID наблюдения статистики. Хронология определяется по `observed_at` и `observation_id` до проверки триггера. Для всех пар действуют проверки окна, времени запросов, возраста контекста и нормализации. Первое решение и закрытые состояния сохраняются.

Для API-Football использовать результат `signal_reminder_history` и для первого решения, и при повторной проверке перед отправкой в `signal_reminders`. Снимок 75 служит источником архивных ID при отсутствии отдельной связи из 036. Его пара проходит ту же проверку исходных ответов, включая единственную строку матча в контексте, совпадение запуска и команд. Диспетчер использует только прошедшие проверку наблюдения API. Совпадение с текущим `poll_id`, явная ссылка или положительный снимок не возвращают отклонённую пару в выборку. Аналитическая запись 75-й минуты сохраняет свою схему и правила обновления. Для повтора используются локальные наблюдения в действующем окне.

Текущий контекст API для отправки и закрытия ожидания по состоянию матча проверять отдельно от исторической пары. По `poll_id` читать именно тот успешный ответ `/fixtures?live=all`, который сформировал актуальную строку. Проверять совпадение времени наблюдения, наличие ровно одной строки того же матча и согласованность статуса и минуты с проекцией. Переиспользовать проверки формата ответа и идентификаторов. Общий `run_id` может связывать проверенную статистику с последующим однозначным контекстом того же матча в пределах действующих условий свежести и окна. Сам по себе ID запуска не подтверждает качество текущего ответа. Дубликат, отсутствие матча или несовместимый контекст исключаются из отправки и из закрытия по минуте или статусу, в том числе при проверке подтверждённых алиасов. Старый контекст не подставляется вместо отклонённого текущего.

Проверка текущего контекста применяется при построении очереди и непосредственно перед отправкой. Она не исключает достоверную раннюю пару из истории первого решения. При неоднозначном обновлении открытое напоминание с положительным решением ждёт следующего штатного опроса или истечения действующего срока. Подтверждённый выход из окна и подтверждённое окончание закрывают ожидание по состоянию матча без новой статистики для этой проверки. Использовать локальный архив и существующую схему. Правила Fonbet для напоминаний сохраняются.

Для каждого API-алиаса определить ожидаемую пару `(home_team_id, away_team_id)` по ранее подтверждённым данным того же матча. Для исходного API-сигнала использовать архивный ответ по ссылке из `first_context`. Для действующих записей, где такой ссылки нет, использовать подтверждённую привязку к матчу или архивную пару ранее принятого решения при проверяемом происхождении. Считать текущий ответ проверяемой записью, а ожидаемые команды брать из независимого от него источника. При недостатке или конфликте доказательств оставлять ожидание до подтверждения или истечения срока. Сверять команды в порядке сторон API.

Одну проверку идентичности применять к архивным парам для первого решения, текущему контексту при формировании очереди и повторной проверке перед отправкой. Проводить её до переходов `outside_window` и `regulation_end_or_void`, включая закрытие по API-алиасу сигнала Fonbet. Сохранять первое решение по пригодному историческому опросу при отклонении последующего контекста. Для закрытия по выходу за 75-ю минуту или по FT достаточно проверенного архивного контекста исходных команд. Истечение срока действует независимо от наличия контекста. Снимок 75, история доставки и исходные наблюдения сохраняют свои функции.

Проверять фазу, минуту 65–75, корректность связи и свежесть контекста на момент получения статистики. Времена начала запроса контекста и запроса статистики должны быть позднее подтверждения первой доставки. Из записей, доступных к моменту обработки, выбирать первую с определимым `pressure()` по времени наблюдения статистики, со стабильным порядком по идентификатору наблюдения при равных временах. Ошибку, пустоту, несвязанные данные и неопределённый триггер пропускать. Давность записи на момент обработки сама по себе не исключает её из выбора первого результата.

В строке `live_signal_reminders` сохранять неизменяемое первое решение и ссылку на источник, матч, опрос и наблюдение вместе с временами и минутой. Фиксировать решение в транзакции под действующей блокировкой диспетчера. При `false` та же транзакция переводит ожидание в `cancelled` с причиной `trigger_cleared`. При `true` разрешается проверка готовности к доставке. Перезапуск и повторный импорт не переоткрывают закрытое ожидание и не заменяют записанный опрос.

Перед сетевым вызовом отдельно проверять актуальные контекст, окно 65–75, существующий TTL статистики и положительный триггер того же источника. Устаревшее положительное решение сохраняется, а для доставки требуется свежее подтверждение. Свежий определимый отрицательный результат закрывает ожидание. После выхода из окна, подтверждённого окончания, отмены либо действующего истечения ожидания доставка закрывается. При нехватке бюджета сохраняется состояние доставки до следующей допустимой попытки. Для API после закрытия повтора нет целевых запросов статуса и результатов. Для Fonbet закрытие повтора не меняет расписание голов.

Готовность отбирать в SQL/планировщике до LIMIT: свежий новый контекст и статистика исходного источника с положительным триггером внутри окна, допустимая фаза и отсутствие запретов доставки. Не включать в отправляемый пакет записи только по возрасту исходного сигнала. Терминальные состояния обрабатывать отдельным проходом отмены; waiting без контекста остаётся видимым оператору, но не занимает слот готового сообщения. Если ready-очередь сама превышает пакет, использовать устойчивый порядок/курсор и сохранять продвижение между запусками. Простая короткая задержка при прежнем ORDER BY first_sent_at не решает блокировку.

Первый dispatcher и reminder worker получают один deadline: завершить работу не позднее чем за 5 секунд до текущего TimeoutStartSec=90. Перед Telegram резервировать его текущий максимум ожидания 25 секунд и время фиксации результата. Если резерва нет, не переводить запись в sending и не вызывать транспорт; перенос не означает uncertain. Не увеличивать таймаут службы для обхода проблемы. Реально начатая доставка по-прежнему использует lease и uncertain-политику.

### 3. Каноническая идентичность и конкурентность

Все новые строки ссылаются на canonical identity, сохраняя исходные source IDs и alert IDs для аудита. Под блокировкой 27001 при merge переадресовывать tracking/очереди, выбирать самое раннее подтверждённое первое сообщение, отменять лишние ожидающие reminders. Перенос алиасов не меняет источник первого подтверждённого сигнала. При объединении ранее раздельных сигналов самый ранний подтверждённый сохраняет режим, а потерявшая право очередь прекращает опросы с сохранением истории. Любая уже sent/uncertain reminder блокирует новую автоматическую отправку по объединённому матчу. Старый сигнал, обнаруженный при merge, не включать задним числом; возможное дублирование до установления связи отражать в аудите, не обещать ретроактивное предотвращение уже доставленных сообщений.

Внешний Telegram-вызов защищать существующей стратегией lease/сериализации отправщика. Несколько результатов одного опроса, конкурирующие workers и повторный запуск не создают дополнительные reminders. Goal workers используют короткие транзакции и claims с lease; сетевые запросы не удерживают общий lock отправки.

### 4. Полная временная шкала и отдельные интерпретации

Предлагаются `live_signal_goal_observations` для неизменяемых снимков источника/версий и `live_signal_goals` для действующих нормализованных событий. Поля: canonical match, source/event ID при наличии, observation ID/time, credited team (home/away и source team ID), base minute, added minute, period, score_after_home/away, действительность/отмена, версия и качество сопоставления. Для автогола исходную команду и сторону, которой засчитан мяч, хранить раздельно. Незабитые пенальти и серия пенальти не являются голами; пенальти, забитый в основное время, является.

Сохранять полный полученный список для проверки полноты и истории исправлений; отношение к сигналу хранить отдельно: `before/after/order_unknown`. В аналитическую выборку после сигнала включать `after` и отдельно показывать `order_unknown` с пользовательской отметкой. Если порядок командных голов одинаковой минуты не восстановим, score_after оставлять неизвестным с причиной: не выдумывать последовательность. Такой результат неполон по деталям до уточнения.

Адаптер Fonbet читает «Ход матча» и сохраняет наблюдение. При недоступности возвращает типизированный `timeline_unavailable`. Уже полученные независимо проверенные данные, включая сохранённый результат API, можно использовать для сверки счёта при совпадении матча и фазы. Worker голов не инициирует запросов API. Сохранять расхождения источников с происхождением данных, чтобы оператор видел причину неполноты.

Стабильный `goal_id` — внутренняя идентичность события. Provider ID использовать при наличии. При его отсутствии сопоставлять новый снимок с прежними голами по canonical match, source, команде, периоду, базовой и добавленной минутам. Счёт служит дополнительным доказательством. При отсутствии `credited_side` искать кандидатов по ID события или комбинации исходной команды, типа события, периода и обеих минут. Известная сторона остаётся при однозначном совпадении. Неполные поля, мешающие надёжному сопоставлению, сохранять в pending. `score_after_*` и порядковый номер внутри снимка сами по себе не определяют идентичность.

Однозначное соответствие обновляет версию того же события, сохраняя исходные наблюдения и известные поля. Исправление минуты или счёта само по себе не создаёт новый гол. В резервном сопоставлении сравнивать пару базовой и добавленной минут. Один `goal_id` сопоставляется не более чем с одним событием текущего наблюдения. Если целостный live-таймлайн с последовательным счётом показывает два отдельных гола, сохранять оба даже при незакрытом матче. Для снимка с 90+2 и 90+6 более ранний гол не является кандидатом на совпадение со вторым только из-за общей базовой минуты. Равноправные варианты сохранять в pending с причиной и исключать из подтверждённых голов. Качество идентификации события, порядок относительно сигнала и полнота финального результата оцениваются отдельно.

До изменения строк построить соответствия по всему текущему наблюдению. Сначала зарезервировать пары по однозначным ID событий источника в рамках матча. Затем рассмотреть группы голов одной команды, периода, базовой и добавленной минут, если хотя бы в одном из двух наблюдений на этой отметке несколько событий. До сопоставления по накопленному счёту проверять известный тип гола (пенальти, гол с игры, автогол) и порядок, подтверждённый таймлайном. Расхождение известных типов требует сверки, если связь по ID источника отсутствует. Порядок внутренних ID сам по себе очередность событий не подтверждает.

Оценивать однозначность каждой пары внутри группы. В проверенных последовательностях резервировать согласованные по типу и порядку соответствия, пока конфликт соседнего события оставляет их единственными. Сохранить правила приоритета ID источника и использования каждого ID один раз. Несовпавший тип при той же отметке и позиции является основанием для сверки: сохранить входную строку и подходящие прежние события в `live_signal_goal_pending` с причиной. Без подтверждённой связи или доказательства отдельного события сохранять прежние записи этой спорной части. Например, изменение соседнего гола с игры на автогол оставляет его на сверке, а пенальти на 90+2 получает счёт 1:1 на прежнем ID. Новый подтверждённый гол соперника записывается отдельно.

В подтверждённом таймлайне с голом на 88-й минуте пенальти и гол с игры на 90+2 получают новые значения счёта на прежних ID, а новый ID назначается голу на 88-й. При расширении группы из одного гола на 90+2 сперва зарезервировать однозначную пару по типу. Если гол с игры теперь второй после добавленного пенальти, гол с игры сохраняет свой ID, а пенальти получает новый ID. Для остальных событий сохраняются признаки непрерывности. Например, если гол 1:0 уточнён с 86-й на 90+2, а уже записанный гол 2:0 на 90+2 сохранил счёт, оба гола сохраняют прежние ID.

До расширения списка спорных переносов зарезервировать оставшиеся взаимно однозначные пары на той же отметке времени по стороне, периоду, базовой и добавленной минутам и известному согласованному типу гола. Использовать свободные ID и учитывать весь текущий таймлайн. ID, уже отнесённые к спорной группе, остаются на сверке до разрешения её соответствий. Для проверенного таймлайна равенство накопленного счёта не требуется. Взаимная однозначность означает, что обе стороны пары имеют по одному соответствию по этим признакам. Совпадение только по счёту и неполный ответ с конфликтом счёта проверяются по действующим правилам.

Перед выделением новых ID проверить кандидатов из спорных групп на других минутах того же периода для оставшихся строк. Учитывать сторону, совместимый тип, последовательность и известный счёт вместе с остальным таймлайном. Зарезервированные однозначные пары сохраняют соответствие. ID, удержанный на сверке без подтверждённой пары, остаётся кандидатом на коррекцию минуты. Однозначное подтверждение обновляет прежний ID. При неоднозначности сохранять возможные версии в `live_signal_goal_pending` с кандидатами и причиной. Например, при добавлении гола соперника на 69-й известный гол на 70-й получает счёт 1:1 на прежнем ID, даже если ещё проверяется перенос одного из голов с 90+2 на 88-ю. Спорный перенос не создаёт лишнюю активную запись. Независимо подтверждённые голы обрабатываются отдельно. Пока соответствие спорных голов не разрешилось, сверка остаётся неполной и продолжает действующее расписание. Сохранение наблюдения, новые версии и изменение активности происходят в одной транзакции.

При частичном ответе совпадение обеих минут, команды и периода с противоречащим известным счётом требует независимого свидетельства идентичности. При его отсутствии записать спорное событие, кандидаты и причину в `live_signal_goal_pending`, сохранив прежние значения и статус гола в аналитике. Планы обновления и сохранение наблюдения фиксировать в существующей транзакции. Достоверный VAR и подтверждённый полный результат по-прежнему могут изменить состояние известного события. При неоднозначности резервирования не считать привязку разрешённой и не отменять связанные голы на основании спорного сопоставления.

Проверять конфликт известных типов для любого предположительного совпадения в неполном наблюдении, включая одиночный гол и пару, предварительно выбранную по счёту и отметке времени. Приоритет имеет однозначная связь по ID события источника. Без независимого подтверждения сохранить спорную строку и кандидатов в `live_signal_goal_pending`, прежнюю версию сохранить целиком. Проверенная структура live-таймлайна подтверждает различимые события, а совпадение минуты и счёта в такой структуре само по себе недостаточно для смены известного типа. Отсутствующий тип обрабатывается по действующим правилам неполного ответа. Следующий проверенный финальный протокол сопоставляет пенальти по исходному сохранённому типу, даже если появившийся отдельный гол с игры получил прежнее значение счёта.

Новый подтверждённый гол создавать после исключения соответствия уже известному либо при достоверном свидетельстве отдельного события. Частичный ответ сохраняет известные поля и статус отмены. При совпадении с неактивным голом фиксировать новое наблюдение в истории без реактивации или нового подтверждённого ID. Только более свежий полный согласованный снимок вправе восстановить отменённый гол. Отмену отражать по достоверному полному авторитетному обновлению/однозначной коррекции с аудитом; отсутствие в частичном ответе не означает VAR-отмену. Возможные дополнительные поля/таблицу сопоставлений вводить аддитивно; наблюдения и старые сигналы не пересоздавать.

При применении версии и переходов активности сравнивать исходные наблюдения по `(observed_at, observation_id)` в рамках матча и источника. Равное время разрешается по ID архивного наблюдения, а повтор исходного payload с той же архивной идентичностью имеет прежний ID. Для известного гола сверять входную пару с наблюдением, на котором основано текущее состояние, включая применённые изменения из частично разрешённого протокола. Полнота всего протокола отдельно определяет право выводить отмены из отсутствия событий.

При записи наблюдения под существующей блокировкой сначала определить канонический матч и все объединённые с ним ID. Найти повтор по `(source, source_event_id, observed_at, payload_hash)` во всей этой семье до вставки под каноническим ID. При совпадении переиспользовать архивную запись и действующие правила возвращения исхода повтора и проверки давности. Если прежняя версия системы сохранила несколько точных копий, возвращать самый ранний архивный ID для этого ключа. Исторические копии остаются в аудите, действующая ссылка на версию не переназначается при повторе. Отличающееся содержимое или ID события источника образует отдельное наблюдение, а новизна при равном времени определяется архивным ID. Использовать существующую схему 036.

Старое наблюдение сохраняется для аудита. Для защищённого гола его повтор не выделяет новый ID и не меняет текущие поля, активность, ссылку или номер ревизии. При смене активности сохранять основание отмены или восстановления с наблюдением. Это основание участвует в сравнении наравне с версией счёта. Коррекцию из нового пригодного наблюдения применять под существующей блокировкой вместе с записью версии. Обработка старого наблюдения не завершает сверку по более свежему спорному протоколу.

Для Fonbet после отсутствия строки в discovery попытаться открыть сохранённую проверенную URL карточки либо доступный спортивный результат. Читать явный статус самого документа, а не подставлять пустой period_text от отсутствующей discovery-строки. Перед принятием статуса проверить identity матча. Источник подтверждения, исходную метку, время наблюдения и нормализованную фазу сохранять вместе; FT и переход в ET подтверждают конец regulation, AET/PEN не подменяют его счёт итогом дополнительных таймов. Использовать существующий обезличенный fixture строки «Завершённые» с совпадающим ID. Отдельно проверить 90:00 без явного конца, live 90+N и недоступную карточку. Полный список голов не заменяет статус окончания. До подтверждения — waiting_end с причиной, без выдуманного FT; доступность реальной архивной карточки не объявлять доказанной синтетическим тестом.

Перед переходом к результатам или отменой напоминания сверять наблюдение терминального статуса Fonbet со временем принятого браузерного live-наблюдения того же события. Для статуса из браузера учитывать также более свежий проверяемый штатный контекст `2H`. Использовать время исходного наблюдения и существующую проверку идентичности и происхождения. Подтверждённые часы второго тайма сохраняют временную ссылку даже при нулевом списке голов. Ссылка продвигается по времени наблюдения. При одинаковом времени и конфликте статусов ждать следующего пригодного опроса.

При отборе напоминания и перед отправкой проверять минуту последнего подтверждённого браузерного `2H` после исходного сигнала для каждого связанного события Fonbet. Минута выше 75 закрывает ожидание, если более свежий проверенный штатный `2H` того же события ещё не уточнил часы. Если отметки времени совпадают, браузерная минута выше 75 также закрывает ожидание. Отсутствие карточки в штатной выдаче не отменяет подтверждённую минуту. Первый определимый триггер и подтверждение для отправки по-прежнему берутся из штатных опросов исходного источника.

Запоздавший ответ браузера сохранять как отклонённое наблюдение с причиной `superseded_observation`. Сначала проверять и записывать наблюдение, затем применять статус. Хронология применённых версий защищает уже принятый послематчевый результат от более старого прерывания. Фактическое обращение учитывается, а применённые голы, признак окончания, исходные сроки и состояние доставки по такому ответу сохраняются. Проверять штатный контекст при выборе задачи и повторно перед переходом под действующей блокировкой. В диспетчере проверять тот же порядок для Fonbet-алиасов при отборе и перед отправкой. Для уже установленного окончания учитывать время его подтверждающего наблюдения при более поздней доставке противоречащего статуса прерывания.

### 5. Время гола и достоверность результата

Сравнивать точное время события с границей отправки только если источники дают сопоставимые достоверные часы. При минутных отметках использовать период и интервалы времени; та же минута без надёжного порядка — `order_unknown`. Появление гола при более позднем запросе само по себе не доказывает, что он забит после сигнала. Граница не меняется при reminder, merge выбирает первое сообщение.

Основное время определяется периодом, а не условием `minute <= 90`: 90+N входит, 105+N не входит. Число 92 без периодной семантики не считать ни гарантированным regulation, ни ET. Для AET/PEN брать счёт конца основного времени, не итог после дополнительных таймов. Если доступны только AET/PEN без достоверного времени перехода, момент подтверждения завершения фиксировать при обнаружении; не восстанавливать его из расписания.

Полнота требует подтверждённого конца основного времени, полного списка событий, сверки с независимо подтверждённым счётом regulation того же матча, известных обязательных полей и отсутствия неразрешённых конфликтов. `REG_END` от строки «Завершённые» подтверждает окончание. Для достоверного счёта нужно явное значение основного времени или подтверждённая разбивка двух таймов, с выравниванием сторон по canonical identity. Табло того же timeline отдельно не верифицирует список. Если независимый счёт недоступен или отличается, сохранить последний live-снимок и зафиксировать причину неполноты. Пустой ответ не равен полному нулевому результату. `timeline_complete` и `order_unknown_count` независимы: весь список может быть полным, а отношение одного гола к сигналу неизвестно. Отмена/прерывание — отдельный статус.

### 6. Долговечное расписание и наблюдаемость

Для Fonbet создать долговечный этап live-наблюдения сразу при первом подтверждённом сообщении. До 89-й использовать штатный цикл. При первом достоверном контексте второго тайма на 89-й минуте или позже присвоить ближайший минутный слот. Затем назначать не более одного чтения «Хода матча» на матч на минутный слот по времени сервера. Ключ очереди включает канонический матч и слот. Worker хранит ID наблюдения, фазу, минуту с добавленным временем, время снимка, due и факт переноса. Не вычислять 89-ю по времени начала матча. При 90+N и продолжающемся основном времени минутный режим сохраняется. После перезапуска взять ближайший актуальный слот без разового опроса за каждую пропущенную минуту.

В промежуточную минуту планировщик обслуживает концовку. На штатном пятиминутном запуске сначала выбирать допущенные послематчевые задачи, которые ждут от исходного срока не меньше пяти минут. Сортировать их по исходному сроку с устойчивым порядком по ID при равенстве. Затем использовать действующую ротацию концовки и обычных задач. Общие блокировки, ограничения памяти и предел одной браузерной попытки на запуск сохраняются. Продвижение очереди зависит от доступности браузера. Опросы статуса исчезнувшей карточки ограничивать штатным циклом. Подтверждение конца или ET завершает минутный режим, отмена или прерывание закрывают наблюдение со статусом void. Эти этапы существуют только для Fonbet.

Сохранить `primary_due_at` и `review_due_at` как опорные сроки первого обращения и проверки T+24. Исходный срок текущей проверки хранить отдельно от `next_attempt_at`, который задаёт ближайшее время её допуска. При назначении нового этапа или проверки после фактической попытки записывать новый исходный срок. Внутренний перенос обновляет только допуск и причину переноса. При новом запуске возраст определяется исходным сроком текущей проверки даже после нескольких переносов. Диагностика показывает оба времени, возраст и причину. Счётчики live, первичных и суточных попыток ведутся раздельно.

Первичная попытка сразу после подтверждения окончания, чтобы проверить голы после последнего live-снимка; повторы при временном сбое с задержкой 5/15/30 минут, deadline T+1 час. При исчерпании часа сохранить preliminary incomplete и ждать суточную проверку. При доступности источника контролировать SLA, просрочки очереди явно сигнализировать оператору через существующий мониторинг, не объявлять выполненными.

Обязательная проверка T+24 часа даже для полного предварительного результата; при неполноте — семь дополнительных фактических ежедневных проверок. Успешный полный пересмотр завершает цепочку. Фактически начатый запрос, завершившийся внешней ошибкой, фиксируется как выполненная попытка; внутренний перенос до обращения не расходует проверку. После седьмой дополнительной попытки — `incomplete_final`; уже полученные голы остаются. После простоя выполнить одну просроченную проверку с актуальными данными; следующую назначить через 24 часа после фактической попытки. Пропущенные дни не расходуют счётчик: все оставшиеся проверки выполняются, не чаще одной в сутки. Решение пользователя от 2026-11-19 заменяет прежнюю схему фиксированных календарных слотов.

Результат опроса должен явно различать `attempted_success`, `attempted_error`, `deferred_internal`, а также несостоявшееся обращение. Для каждого источника фиксировать, началось ли фактическое I/O, что уже выполнено в текущем этапе и что осталось. Исчерпанный browser/API budget, занятая блокировка и отказ по памяти до обращения — `deferred_internal`, не source_unavailable. Таймаут после начала сетевого обращения может быть attempted_error; классификация зависит от факта I/O, а не одного имени ошибки.

Счётчики первичных и ежедневных попыток изменяются атомарно с результатом только для фактически обработанного послематчевого этапа. Незавершённую попытку отложить на ближайший ресурсный слот, а не на сутки. Пропущенные live-слоты не влияют на эти счётчики. Deadline первичной загрузки сохраняется, просрочка отображается явно.

Убрать общий выход из цикла Fonbet по `client.quota_exhausted` и ранний выход Fonbet по пустому ответу API. Подтверждённый продолжающийся статус отличать от пустого ответа, в том числе при обработке ранее сохранённых API-данных. API-сигнал не создаёт fallback-очередь голов, а уже назначенное наблюдение Fonbet работает независимо от API. При переходе на новый режим закончить несовместимые задачи старой версии без сетевых обращений и без удаления raw наблюдений.

Общий status: `waiting_end/preliminary/review_due/reviewed/incomplete_final/void`, доставка reminder имеет независимый status. В операторском отчёте — pending/reminder uncertain, due/overdue, последние ошибки, полнота/неопределённость порядка по матчу. Новую аналитику назвать явно «после первого сигнала», не менять `goals_after_75` и `alert_hit_rate`.

### 7. Ресурсы и совместимость

Использовать штатные данные опроса для триггеров и определения фазы. Минутный worker читает события только у назначенных сигнальных матчей Fonbet через действующий browser lock, ограниченную очередь и текущие лимиты RAM и времени. Сохранять приоритет сбора для первоначальных сигналов. Независимость от API проверять при отключённом клиенте и исчерпанной квоте. Дополнительный сбор ударов для минутной очереди отсутствует.

## Risks / Trade-offs

- [Fonbet не предоставляет полный timeline] → best effort адаптер, явная неполнота, установленный предел проверок; не считать счёт заменой событий.
- [Точности минут недостаточно] → интервалы и `order_unknown`, отдельные показатели полноты и порядка.
- [Первая отправка и commit не атомарны с Telegram] → сохранить uncertain-политику, не обещать exactly-once при неизвестном внешнем результате.
- [Слабый матчинг либо позднее объединение] → только подтверждённые aliases, merge под lock, аудит ранее доставленного.
- [Добавленные запросы вытесняют live] → batching, приоритеты, квоты и видимый overdue; не расширять память или перезапуски браузера.
- [Локальная версия отличается от production] → перед будущим deployment сравнить версии read-only; документация не удостоверяет состояние серверов.

## Migration Plan

1. Сохранить миграции 030–036 и существующие ID. Совместимость активных API-напоминаний обеспечить ограниченным чтением исторических пар после перехода 035 → 036. Прогон обновления на одноразовой БД должен охватывать открытое напоминание и записи `sent`, `uncertain` и `cancelled`. Режим и сроки послематчевых проверок остаются прежними.
2. Подготовить раздельные флаги reminders/tracking и устойчивый cutoff/version новых сигналов; по умолчанию выключены. Установить workers без отправки/сбора до активации.
3. Проверить на локальных fixtures и одноразовой тестовой БД: сценарии спецификаций, конкуренцию, рестарт, merge, API/Fonbet corrections, 90+ и ET. Проверить неизменность legacy outcomes.
4. Отдельным этапом после запроса пользователя на production выполнить согласованный rollout: read-only сверка версии, миграции, запуск workers, включение для новых сигналов и контроль очереди. Текущий документ не разрешает этот этап.
5. Rollback: выключить флаги и новые задания, отменить неотправленные reminders с причиной; оставить исходный dispatcher, snapshots, registry и legacy settlement. Новые события/аудит сохранить. Не откатывать аддитивные таблицы с накопленными данными автоматически.

## Приёмка после review

Перенести случаи хронологии статуса в основной набор и повторить 20 предыдущих воспроизведений. Проверять состояния после каждого шага, включая порядок обработки и повтор чтения. [Воспроизведения статуса Fonbet](../../../../reports/signal-tracking-review-round-10-2026-11-20/repro_cases.py)

| Последовательность опросов | Что проверить после каждого шага |
|---|---|
| Проверенный опрос API → дубликат или чужие команды → проверенное обновление | Первое решение связано с пригодным опросом. До пригодного текущего контекста состояние ожидания и счётчик отправок сохраняются. Затем в зависимости от подтверждённого окна происходит одна отправка или закрытие. Проверить смену контекста между очередью и отправкой, API-алиас и истечение срока |
| Live-голы Fonbet → протокол с вставленным голом и конфликтом соседнего типа → уточнение спорного события | Независимая пара обновляется на прежнем ID. Спорная строка остаётся среди подходящих кандидатов. Число активных записей и история версий соответствуют подтверждённым событиям |
| Live-наблюдение → более свежая коррекция со спорной частью → старый опрос или его точный повтор → новый однозначный итог | Применённая версия, её ссылка, ревизия и активность сохраняются после старого опроса. Свежий итог продолжает историю. Проверить равные времена, отмену VAR и повтор после неё |
| Пенальти → неполный ответ с теми же часами и счётом, но другим типом → протокол с двумя голами → повтор протокола | Спорная строка с кандидатом появляется до изменения известного гола. На промежуточном шаге сохраняются тип, ссылка и ревизия. После финальной сверки пенальти и гол с игры имеют отдельные ID, подтверждённые счёт и историю. Проверить одиночную строку и однозначный ID источника |
| Снимок Fonbet → объединение алиасов → точный повтор → отличающийся снимок с тем же временем | Точный повтор возвращает исходный архивный ID, в том числе после цепочки объединений. Проверить неизменность числа наблюдений и версий, ссылки, активности и ревизии. Отличающийся снимок получает отдельный ID и проходит действующие проверки |
| Браузерное или штатное live-наблюдение → запоздавшие FT или ABD → свежий FT | Проверить оба направления между браузером и штатным опросом, нулевой счёт, конфликт в одну отметку, неизменность состояния ожидания и расписания, затем однократное подтверждение окончания и закрытие напоминания |

Прогнать локальную приёмку перехода 035 → 036, аналитического снимка 75, доставки и очереди Fonbet. Для API подтвердить использование локального архива без дополнительных сетевых запросов.
